# 劳务供应链交易平台

连接用工方与合规劳务供应商，围绕真实用工需求、应标选标、人员供给、履约确认和结算对账建立可追溯的交易与协作网络。项目当前处于需求整理与产品设计阶段；原有的劳务中介管理 SaaS 能力和代码是建设基础，不代表交易平台全链路已实现。

## 产品定位与边界

- **服务对象**：用工方发起需求并选择供应商；劳务公司应标、组织供给与履约；经纪人和工人按相应授权参与。
- **核心流程**：需求发布 → 应标与中标 → 供给与排班 → 考勤和工时核验 → 结算、对账与回款追踪。
- **平台职责**：提供交易撮合、流程协同与可信数据基础设施，不替代劳务供应商承接履约，也不默认承担付款、放款或担保责任。
- **战略方向**：先交易、再数据、后金融；先验证区域交易闭环和单位经济性，再复制区域及发展可复用数据服务。方向已批准，金融业务仍为后置可选渠道，不属于当前上线或收费批准。

产品范围、收费审批状态与中长期战略分别以[平台 PRD](./docs/02-开发阶段/产品设计/00-产品全景/PRD-v0.1.md)、[商业模式与收费标准](./docs/02-开发阶段/产品设计/03-账单与资金/商业模式与收费标准-v0.1.md)及[产品战略路线与可选增值渠道 v0.2](./docs/02-开发阶段/产品设计/05-战略与实施/产品战略路线与可选增值渠道-v0.2.md)为准。

## 后续工作的七条护栏

以下护栏用于需求评审、产品设计、开发、测试和上线判断；新增功能与变更均须核对，不得以实现便利替代业务责任或审批。

1. **不是劳务公司内部 SaaS**：管理功能必须服务交易和履约，不以传统管理模块的数量替代真实交易价值。
2. **不是只发布需求的撮合网站**：要覆盖履约、资金状态与平台监督，不以需求发布或中标作为业务闭环终点。
3. **不是平台亲自供人、垫工资**：劳务公司的交付与资金责任不能被平台界面吞掉；平台协同、核验或编排不等于承接劳务交付、工资债务或垫资责任。
4. **不是把全部资金收进平台才叫闭环**：线下对公支付也要有账期、凭证、核验和对账；账单、支付指令或上传凭证不等于实际到账。
5. **不是只监督供应商**：用工方、供应商、经纪人及平台自身都需要可核验、可申诉的约束；工人保留本人业务相关的申诉入口，平台不得因获客或收费关系偏袒任何一方。
6. **不是以合规为由抹掉增长需求**：人事经理收益与推荐必须设计合法、可执行的路径，而非只有禁止条款；同时不得把增长方向获批等同于所有人均有个人佣金资格，具体支付路径、参数和合同仍须审批。
7. **不是有文档就算批准、有测试就算上线**：规则批准、开发完成、联调验证、真实启用是不同状态，应分别记录结论和证据；草案、模拟结果、底座测试通过均不能代替业务批准或真实上线许可。

按完整交易链推进，不因分批开发而单方面删减独立 App、履约或资金能力；未来保理能力不因本轮拆包自动进入当前交付范围。具体执行见[项目推进建议](docs/00-项目管理/项目计划/项目推进建议-v0.1.md)和[业务包拆解与首批实施清单](./docs/02-开发阶段/产品设计/05-战略与实施/业务包拆解与首批实施清单-v0.1.md)。

## 本地开发

```bash
git clone https://github.com/jihongxing/LaborAntermediaries.git
cd LaborAntermediaries/backend
mvn test
```

后端环境与启动条件参见 [backend/README.md](backend/README.md)。前端各目录当前不一定具备可执行工程，请勿将规划中的技术栈或功能清单当作已上线能力。
