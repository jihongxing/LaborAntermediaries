# 高精度计价与结算精度契约

按类查阅允许与禁止使用场景，见 [money 包使用指南](../src/main/java/com/company/labor/common/money/README.md)；
本文件维护完整的精度、存储和复算契约。

## 1. 范围与禁止事项

本能力位于 `common/money/`，只提供纯计算和值对象，不实现收费引擎、税务规则、账单审批或支付。

**不预置任何分成比例、收费档位、税率或平台优先规则。** 比例、有效时间、参与方和商业规则由业务模块按当次有效版本提供。
没有比例默认值，没有比例档位枚举，也不把当前产品讨论中的价格和比例写成生产常量。
文中的符号化示例与测试合成数值不代表已发布业务规则。

`Money` 继续表达最终可按最小货币单位表示的金额；不能为了支持单价而放宽最终人民币金额的两位约束。
精确数学计算不代表业务确认、结算批准、付款或退款授权。

## 2. 类型与技术容量

| 类型或参数 | 技术容量 | 行为 |
| --- | --- | --- |
| `UnitPrice` | 30 位整数、8 位有效小数，非负 | 包含币种与显式计价单位，不能直接当作应付款 |
| `UnitPrice.calculate` 的数量 | 18 位整数、8 位有效小数，非负 | 调用方核实单位一致及履约依据；不自动认定实际人天 |
| `CalculatedAmount` | 44 位整数、32 位有效小数，可正可负 | 加减乘不隐式舍入，结果超限直接拒绝 |
| `portion` / 分配比例 | 零到一，最多 12 位有效小数 | 只接收调用方传入值，不推断百分数或配置档位 |
| `CalculationPolicy` | 除法小数位显式指定为 0–32 | 标识、版本、除法与结算舍入模式全部必填，没有默认规则 |
| `Money` | 原有 38 位总精度，按币种最小单位 | 人民币两位；转 long 最小单位仍须检查溢出 |

去除末尾无意义零位不算舍入；超出有效精度时拒绝，不截断。整数、指数和小数位有边界，避免极端指数引发过量内存分配。
加减乘不传 `MathContext` 做隐藏舍入；多步相乘仍可能超过有限容量，这时应报错并重新评估计算设计，不能静默压缩精度。

比例参数统一以 `1` 表示全部。禁止自动猜测 `25` 是 `25%`，也不从 `"2.5/7.5"` 猜测权重。
若业务提供的是权重，业务应先按明确精度策略转换；最大余数工具只接受精确合计为一的比例，不自动归一化近似和。
系数相乘使用 `multiply`，它不是分成专用接口；分配份额使用 `portion` 校验零到一范围。

## 3. 计算与舍入边界

建议由业务按以下顺序编排，但不是对所有合同、税务或账单的统一业务政策：

1. 从可信业务规则加载单价、动态比例、币种、计价单位和规则版本。
2. 使用经业务确认的数量精确计算，保留分以下中间值。
3. 在业务约定范围内汇总，明确是逐人、逐天、逐行、逐项目还是整个结算周期。
4. 需要除法时，显式传 `CalculationPolicy`；循环小数的近似误差须按最大数量和累计次数验证。
5. 在批准的结算节点调用 `policy.settle(calculated)`，形成 `Money`。
6. 涉及多方分配时，显式选择尾差规则并验证守恒，不让各方独立舍入后产生不平账。

同一计算值在汇总前、汇总后舍入可能得到不同总额，底座不会默认选择。
税费的含税关系、拆分顺序、计税范围和舍入口径由适用业务规则决定，本包不提供税率或税务结论。
除法位数不是越大就自动正确；业务必须依据最大汇总数量、计算次数及误差要求选择策略并测试。

`CalculationPolicy.Settlement` 包含舍入前计算值、最终 `Money` 和完整策略，构造时校验内部一致性；
`roundingDifference()` 返回“最终金额减计算值”的差额。它便于留存，但不是完整计费过程或批准证明。

## 4. 动态参数接入示例

以下为业务用例中的编排片段，所有变量都必须由业务显式提供，不是生产默认配置：

```java
UnitPrice unitPrice = new UnitPrice(priceValue, currency, pricingUnit);
CalculatedAmount gross = unitPrice.calculate(confirmedQuantity);
CalculatedAmount share = gross.portion(effectiveRatio);
CalculationPolicy policy = new CalculationPolicy(
        policyKey, policyVersion, divisionScale, divisionRounding, settlementRounding);
CalculationPolicy.Settlement settlement = policy.settle(share);
```

若存在基础费、差额阶梯、比例变化、多人参与或税费，业务在自己的模块内编排，
不得将这些公式写死在 `UnitPrice`、`CalculatedAmount` 或 `MoneyAllocation` 中。
策略 key/version 的有效性与审批由业务负责；值对象不联网查询、不自动登记，也不能证明客户端传来的策略已获授权。

## 5. 尾差分配

### 最大余数分配

`MoneyAllocation.largestRemainder(total, ratios)`：

- `total` 已经形成最小货币单位；比例完全来自本次输入，精确合计必须等于一。
- 按绝对值计算每方应分最小单位，先向下取整，再按余数从大到小补齐剩余单位。
- 相同余数按稳定接收标识升序处理，与输入 Map 顺序无关。采用此规则前业务必须确认同余数排序方式可接受；
  它是显式选择的数学算法，不代表公平性或商业分配的自动批准。
- 不默认优先平台；接收标识应稳定，不使用姓名或银行账号，也不能由不可信调用方任意改名来操纵尾差。
- 单次最多 1000 个接收方，属于资源保护限制，不等同于单笔业务最多 1000 人。
- 返回不可变结果，支持 Money 容量内的大金额，不依赖 long 存储总分值。

### 显式指定余款方

`MoneyAllocation.withRemainder(total, fixed, remainderRecipient)`：

- 已确定各方金额不再重算，剩余金额给显式指定的接收标识。
- 拒绝重复余款方、混币种、与总额方向相反的金额以及超额分配。
- 不默认任何组织拿尾差；固定分配与余款责任必须符合业务约定。

两种工具均保证结果合计严格等于输入总额。负总额按绝对值算法镜像符号，仅提供数学一致性：
实际退款、冲正应引用原分配记录，不能按最新比例重新计算历史退款。
这里的接收标识不是经验证的收款账户；资金流转、扣款授权和付款对象核验仍归业务与支付模块。

## 6. 存储、传输与复算

- `UnitPrice.value`、`CalculatedAmount.value` 的 JSON 使用非指数十进制字符串，不能转 JavaScript `Number` 后再回传。
  比例作为独立业务请求字段时，也必须在其 DTO 上按十进制字符串契约处理，不能误以为任意裸 `BigDecimal` 字段已被全局改写。
- `Money.amount` 沿用字符串契约；币种、计价单位和策略版本必须与数值一起传递，不能仅传一个不明单位的数字。
- 数据库存储使用精确 `NUMERIC`，不能用浮点。注意 `NUMERIC(p,s)` 在检查前可能先按 s 舍入，
  若要求数据库也拒绝超精度直接写入，应使用无 typemod 的 `NUMERIC` 加容量及精度 `CHECK`。

以下只是未来业务表的人民币单价和比例列示例，不是新增的生产计价表：

```sql
unit_price numeric NOT NULL
    CHECK (unit_price >= 0 AND unit_price < 1e30 AND unit_price = trunc(unit_price, 8)),
ratio numeric NOT NULL
    CHECK (ratio >= 0 AND ratio <= 1 AND ratio = trunc(ratio, 12))
```

计算值对应 `abs(value) < 1e44`、`value = trunc(value, 32)`；
最终人民币金额对应 `abs(value) < 1e36`、`value = trunc(value, 2)`，其他币种应采用相应最小单位。
本轮没有擅自新增收费业务表或修改 V1/V2 迁移；临时数据库测试验证上述存储方式。

业务每次计算应保留：

- 原始单价、数量、计价单位、参与方和动态比例。
- 商业规则及计算精度策略的标识、版本、当时参数与适用范围。
- 计算顺序、汇总范围、除法处理、舍入前结果与最终金额。
- 分配算法、明确的余款接收方或稳定排序依据，以及各方最终金额。

可复用受资源授权保护的版本快照，但本包不自动持久化任何输入或个人资料。
策略版本变更不得覆盖历史依据；复算使用历史参数，不使用当前最新比例。

## 7. 兼容与验证

- 原 `Money` 的最终金额约束不变。
- 旧 `MoneyUtil.multiply/divide` 已标记弃用，保留现有两位舍入行为供存量兼容；
  新增计价不得调用它们，改用高精度类型与显式策略。此约束依赖弃用提示和代码审查，不宣称已提供完整静态调用链检查。
- 新增测试覆盖动态比例变化、8/12/32 位边界、循环除法、先汇总与先舍入差异、正负舍入差额、
  大金额、不同币种、稳定尾差、零份额、不可变结果和 JSON 往返。
- 多组动态比例与正负总额循环测试验证逐分守恒；真实 PostgreSQL 临时表测试验证高精度往返与超精度拒绝。
- 完整验收继续使用独立 `_test` 数据库执行 `mvn -B -ntp -Pintegration clean verify`。
