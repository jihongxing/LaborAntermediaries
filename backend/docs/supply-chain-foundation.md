# 劳务供应链平台底座能力与接入契约

## 1. 定位与分层

本轮将通用底座从“单组织内部管理工具”扩展为“组织隔离下可明确授权的多方交易协作支撑”，不是重写业务系统。
业务用语见根目录 [CONTEXT.md](../../CONTEXT.md)，产品方向以 [IDEA.md](../../IDEA.md) 与产品需求文档为依据；
尚未批准的费率、收费资格、资金责任和裁决规则不在本轮固化。

- `common`：稳定错误契约、金额、资源引用、响应和纯工具；新增代码不得访问数据库或依赖业务模块。
- `foundation`：身份、资源授权守卫、审计、版本存储、可靠任务、加密与文件等技术实现。
- `modules/<module>`：组织成员资格、交易参与关系、字段可见性、履约、结算、审批、争议、支付等业务政策。
- “组织”沿用技术字段 `tenant_id`，但平台不是每个组织互不往来的孤立 SaaS；跨组织协作必须逐资源明确授权。
- 平台监督角色不是供应商、签约方、付款债务人或默认超级管理员，不因角色名称获得全平台数据访问权。

## 2. 能力矩阵

| 能力 | 当前实现 | 如何服务供应链协作及边界 |
| --- | --- | --- |
| 可信身份与组织隔离 | 复用 JWT、`ExecutionContext`、令牌撤销与默认拒绝的表隔离 | 不信任请求头的组织身份；当前成员资格仍由业务可信关系复核 |
| 资源级协作授权 | 新增 `ResourceRef`、`ResourceAccessPolicy`、`ResourceAccessGuard` | 精确操作权限与当前资源参与关系同时成立，支持明确授权的跨组织资源访问 |
| 独立复核 | 新增 `requireIndependentActor` | 拒绝经办人复核自己的处理；需回避人员从可信历史加载，不是完整审批流或利益冲突引擎 |
| 稳定错误契约 | 新增 `ErrorDefinition`、`PlatformError`，统一 MVC 与过滤器错误 | 业务码、HTTP 状态、稳定标识分离；并发、重放、越权和完整性异常可区分 |
| 精确计价与金额 | `UnitPrice`、`CalculatedAmount`、`CalculationPolicy`、`Money` 与 `MoneyAllocation` | 区分单价、中间值和最终金额；显式舍入、动态比例与守恒尾差，不预置收费档位 |
| 版本依据保留 | 新增 `VersionedSnapshots` 与 V2 迁移 | 合作条件、计费依据等可追加保存不同版本，禁止服务接口覆盖旧版；不自动判定签约、批准或履约成立 |
| 同库幂等 | 复用 `IdempotentExecutor`，切换到稳定错误契约 | 防止同一组织、操作者、操作范围内请求重放；业务须设计幂等键和重复操作语义 |
| 同库可靠投递 | 在现有队列新增 `enqueueTransactional` | 业务提交与通知任务一起落库；外部交付仍至少一次，不能自动保证外部支付恰好一次 |
| 可追溯审计 | 复用 `AuditRecorder`，快照追加自动同事务审计 | 关联操作者、组织、资源和请求，不保存敏感正文；回滚事务不会留下成功审计 |
| 私有资料与敏感数据 | 复用私有文件、`CryptoService`、脱敏与最小化日志 | 文件默认组织隔离；跨组织业务附件还需单独设计关系、授权和脱敏，不能直接放宽文件 API |
| 可恢复执行 | 复用任务租约、有限重试与失败状态 | 后台处理需实时重新授权、幂等和人工恢复方案，不把历史权限快照当作永久授权 |

不新增通用“万能业务状态”、统一交易大实体或规则引擎，避免再次形成一个基础大包承载全部业务。

## 3. 错误码规范

### 3.1 编码和归属

- 成功响应维持 `code=200`。新增错误使用六位数字码，不再把 HTTP 状态直接作为业务码。
- `100000–199999` 保留给平台通用契约。本轮正式登记 `100001–100015`，见下表。
- `200000–999999` 为业务模块待分配空间，**目前没有正式分配给任何模块**。
  新模块接入前须在本文登记唯一号段、负责人模块和命名空间，并在模块内实现 `ErrorDefinition`，不能往 `PlatformError` 塞业务错误。
- `errorKey` 格式为 `命名空间.错误标识`，均使用大写英文和下划线；不能动态拼入资源号、个人信息或异常文本。
- 已发布的数字码和标识不得回收复用；语义变化应新增错误，旧码退役时保留登记和兼容说明。
- `message` 是可公开提示，不作为程序判断依据；SQL、凭证、银行信息、身份证和原始第三方响应不得回传。
- 错误定义的格式可被运行时校验，但跨模块唯一性仍需登记与测试，不宣称存在全局自动扫描注册器。

| --- | --- | --- |

| 100002 | `SECURITY.UNAUTHENTICATED` | 401 |
| 100003 | `SECURITY.ACCESS_DENIED` | 403 |
| 100004 | `SECURITY.ORGANIZATION_REQUIRED` | 403 |
| 100005 | `COMMON.RESOURCE_NOT_FOUND` | 404 |
| 100006 | `COMMON.DATA_CONFLICT` | 409 |

### 3.2 API 兼容和迁移

例如版本冲突返回真实 HTTP 409，响应字段为：

```json
{
  "code": 100007,
  "message": "版本已变化，请刷新后重试",
  "errorKey": "COMMON.VERSION_CONFLICT",
  "requestId": "请求关联标识"
}
```

Web 错误适配器从 MDC 传递 `requestId`，没有请求关联标识时省略，不保证非 Web 调用自动生成。
原始异常原因不会进入响应；未知异常仅输出安全提示。

这是基础接口错误体的**有意契约变更**：调用方应使用 HTTP 状态处理认证、权限等协议语义，使用 `errorKey` 或已登记业务码细分错误。
不得继续假设 `response.code === 401`、`BusinessException.getCode() == HTTP状态`，服务端应使用 `getHttpStatus()`。

历史 `ErrorCode`、数字版 `BusinessException` 和 `Result.error` 工厂保留用于存量兼容；
历史数字异常在 400–599 内沿用该 HTTP 状态，否则映射为 422，且不提供 `errorKey`。
旧 SaaS 业务错误只表示历史保留，不是新平台的模块规划；新代码使用契约化异常，不能继续增加旧常量。
旧 `MoneyUtil.yuanToFen` 也有行为收紧：分以下非零小数或 long 溢出从静默截断改为异常，调用方不得依赖原截断行为。

## 4. 资源协作授权接入

1. 模块为资源定义稳定 `resourceType`；`resourceId` 必须在该类型下全平台唯一，不能直接使用各组织重复的本地编号。
2. 注册唯一 `ResourceAccessPolicy` Bean；没有策略、关系失效、权限不足一律拒绝，重复类型启动失败。
3. 业务用例调用 `requireAccess(resource, permission)`；不是把资源所属组织写入当前身份以绕过隔离。
4. 策略从可信存储校验当前组织成员、当前交易参与关系、操作范围、用途和字段权限；存储故障应传播，不能捕获后放行。
5. 平台人员也需要明确监督范围；同组织其他成员不自动继承交易资源权限，经纪人或劳动者也不因相关身份获得整份资源内容。
6. 对撤销与写入并发有严格要求时，模块须在同一事务中配合关系锁或版本条件协调授权和业务修改。
   单次布尔策略检查不是对并发撤销的全局串行保证。

`ResourceAccessGuard` 不做字段脱敏。不同参与方可见字段不同时，业务需先构造受限投影或拆分资源；
不能仅因为允许查看某个字段，就通过策略放行包含更多内容的整个快照。

新增能力没有默认生产业务策略或公开快照 HTTP 接口；底座启动成功不表示合同、结算等真实资源已接入授权。
对组织私有表继续使用隔离注册；不得将跨组织业务表或新快照技术表登记为全局共享表来省略授权。

## 5. 金额、版本与投递约束

### 金额

- `Money.cny("12.34")` 表示人民币 12.34 元；使用十进制文本或 `BigDecimal`，禁止先经过 `double`。
- 按币种最小单位统一精度，去除多余零位可以，丢失非零位不可以；技术精度上限 38 位，不等同于业务交易限额。
- `minorUnitsExact()` 精确转最小单位，超出 long 范围抛异常。JSON 的 `amount` 输出十进制字符串，避免前端浮点精度丢失。
- 单价使用 `UnitPrice`，中间值使用 `CalculatedAmount`，除法与最终舍入显式传 `CalculationPolicy`；
  `MoneyAllocation` 提供最大余数和指定余款方两种守恒分配方法。详见 [计价精度契约](pricing-precision.md)。
- 不预置分成比例、收费档次、税率或平台优先规则；比例和商业规则由业务按有效版本提供，汇总范围和税费顺序由业务决定。
- 旧工具除精确转分与并发格式化修复外保留兼容行为；`MoneyUtil.multiply/divide` 已弃用，新计价不能使用其默认两位舍入。

### 版本快照

- `append(resource, expectedRevision, schemaKey, schemaVersion, content)` 首建传 0，此后传当前版本。
  条件更新头版本防止并发覆盖；冲突返回 `COMMON.VERSION_CONFLICT`，调用方应刷新后重新判断业务，不能盲目覆盖重试。
- 快照内容、头版本与追加审计同库事务提交，参与外层事务；首建冲突、后续冲突、回滚不会残留半份版本。
- 单份 JSON 限 64 KiB，schema 必须显式标识及版本；禁止把原始证件、账户、个人敏感信息明文复制入公共快照。
- 读取指定历史版本时重新检查当前资源授权，并核验 SHA-256；组织来源元数据不等于当前所有可读组织。
- 接口无更新或删除历史版本的方法，但数据库管理员仍可修改记录；运行账号最小权限、备份和保留期限必须另行配置。
  摘要不是电子签名、可信时间戳、公证或防数据库管理员篡改的安全承诺。
- 快照不是批准、双方确认、结算生效或实际付款；这些业务状态与版本绑定关系由模块维护。

### 同库可靠任务

- 在业务事务内调用 `enqueueTransactional`，无事务直接拒绝；与业务数据使用同一数据源、事务管理器。
- 任务仅保存最小资源标识，不能把敏感正文和永久权限复制入载荷；消费时根据当前状态重新授权。
- 数据库提交与投递记录原子化不等于外部效果原子化；调用第三方支付、短信等必须设计幂等号、超时未知态、查询核实与补偿。
- 重试不能把“支付状态未知”当“支付失败”立即重复付款；人工重放、审批和恢复权限由业务模块定义。

## 6. 留在业务模块的后续建设

以下需求重要但本轮不以“公共工具”方式伪实现：

- 组织准入、资质有效期、组织成员生命周期、授权签发与撤销。
- 需求与供给匹配、订单参与关系、合作条件确认、履约事实和争议材料。
- 计费资格、规则审批、结算版本确认、分账依据、申诉与独立复核流程。
- 付款指令审批、第三方回执验真、未知态处理、对账与人工核查；结算确认不等于付款成功。
- 风险限制的触发证据、限制范围、解除权限和追溯记录。
- 跨组织附件的业务归属、可见范围、脱敏投影与保留期限。

这些模块应复用本轮底座，而不是继承通用交易父类或向 `common` 塞业务常量。每次接入必须配套业务授权策略、迁移和回归测试。
