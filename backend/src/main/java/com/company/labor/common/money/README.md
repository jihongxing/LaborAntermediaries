# 金额与计价类型使用指南

本目录提供带币种的金额值对象、纯计算和尾差分配工具，不实现收费引擎、合同规则、账单审批、税务政策或支付。
新增计价代码先按本指南选类型；完整精度与存储契约见 `backend/docs/pricing-precision.md`。

**不预置分成比例、收费档位、税率或尾差优先方。** 商业参数必须由业务模块提供，并关联当时有效的规则版本。
能够构造金额、完成计算或分配，并不表示履约已确认、结算已批准或收款方已获授权。

## 1. 快速选型

| 当前需求 | 应使用 | 不允许的用法 |
| --- | --- | --- |
| 表达每人天、每小时等单位价格 | `UnitPrice` | 用 `Money` 存分以下单价；只存数字却丢失币种或计价单位 |
| 单价乘已确认数量 | `UnitPrice.calculate(quantity)` | 自动猜测单位或把未经确认的数量当履约事实 |
| 汇总、差额、系数相乘、尚未结算的份额 | `CalculatedAmount` | 每一步先转 `Money`；用格式化方法作为计算舍入 |
| 按业务提供的比例计算一份金额 | `CalculatedAmount.portion(ratio)` | 写死比例档位；直接传百分数整数或比例描述文本 |
| 除法或将计算值转为最终金额 | `CalculationPolicy` | 使用默认除法精度、隐含舍入方式或未获业务认可的策略 |
| 表达已按币种最小单位确定的金额 | `Money` | 把该对象当成账单确认、付款成功或退款授权凭据 |
| 保存一次舍入的原值、结果和所用策略 | `CalculationPolicy.Settlement` | 把封套当成完整计算轨迹或经过审批的结算单 |
| 将已确定总金额按比例逐分分配 | `MoneyAllocation.largestRemainder` | 各方独立舍入；输入权重或合计不为一的近似比例 |
| 已确定部分金额，余款给明确参与方 | `MoneyAllocation.withRemainder` | 省略余款方；默认把尾差留给平台；超额分配 |
| 包内十进制校验或高精度 JSON 输出 | `DecimalPrecision` / `DecimalTextSerializer` | 将内部校验、序列化工具当作业务金额 API |

即使某个单价恰好只有两位小数，只要语义是“每单位价格”，仍使用 `UnitPrice`；
即使某个中间结果恰好能按分表示，只要尚未到约定结算节点，仍使用 `CalculatedAmount`。

## 2. 每个类型的边界

### `UnitPrice`：单价，不是应付款

- 非负，最多 30 位整数、8 位有效小数；同时携带币种和显式计价单位。
- 单位标识须满足 `[a-z][a-z0-9_.-]{0,63}`，建议由业务统一维护稳定含义，不使用展示文案。
- `calculate` 接收非负数量，最多 18 位整数、8 位有效小数；返回未按分舍入的 `CalculatedAmount`。
- 单位换算、实际人天、计价资格和履约确认由业务负责，类本身不校验数量的业务来源。
- 不用负单价表达退款；退款或调整应在业务确认依据后使用相应金额类型表达。

### `CalculatedAmount`：中间计算值

- 可正可负，最多 44 位整数、32 位有效小数；超限拒绝，不静默截断。
- `add`、`subtract` 只允许同币种；`multiply` 接收显式无量纲系数，不提供默认税率或加价规则。
- `portion` 接收零到一的动态比例，最多 12 位有效小数；它只计算一份金额，不保证多方分配合计守恒。
- `divide` 必须显式传入 `CalculationPolicy`，禁止依赖默认两位除法。
- 不直接作为支付指令金额，不自行认定负值意味着已获退款授权。

### `CalculationPolicy`：显式的精度与舍入策略

- 策略标识、正数版本、除法小数位数、除法舍入方式、结算舍入方式全部显式提供。
- 除法小数位数可为 0–32，但位数越大不等于结果在业务上自动正确；须按数量上限和累计次数验证误差。
- 仅在业务约定的结算范围及节点调用 `settle`；返回 `Settlement`，其中包含最终 `Money`。
- 策略同一标识和版本不得更改语义。是否有效、适用于哪份合同、是否获批，由业务控制。
- 不在该类中加入分成档位、税率、含税公式、收费规则或策略自动审批。

### `CalculationPolicy.Settlement`：一次转换的记录封套

- 构造时校验原计算值、最终金额、策略及币种的一致性。
- `roundingDifference()` 返回“最终金额减原计算值”，可能为正、负或零。
- 可用于持久化舍入依据，但仍需业务补充原始单价、数量、参与方、规则版本、汇总范围和计算顺序。
- 不把舍入差额自动视为平台收入，也不把封套等同于持久化成功或审批成功。

### `Money`：按最小货币单位确定的金额

- 适用于最终结算结果、已确定金额的同币种加减，以及支付适配前的金额表达。
- 人民币固定到分；其他币种使用自身最小单位，不能把所有币种统一当作两位小数。
- 构造器不替调用方舍入；人民币分以下非零小数会被拒绝。需要舍入时先显式使用 `CalculationPolicy`。
- 技术容量为币种 scale 下最多 38 位总精度；`minorUnitsExact()` 返回 `long`，大金额仍可能溢出并抛错。
- 支付通道限额、扣款授权、收款对象及付款状态由业务和支付适配层另行校验。

### `MoneyAllocation`：分配守恒，不是资金流转

- `largestRemainder` 接收非空比例映射；每项在零到一之间、最多 12 位有效小数，精确合计必须为一。
  不接收权重，不自动归一化。不能把循环小数比例简单截断后假定其合计为一。
- 按币种最小单位分配；余数优先，同余数按参与方标识字典序决定，输入 Map 顺序不影响结果。
- `withRemainder` 保留已确定的分配金额，余款交给显式指定且不与已有项重复的接收方。
  所有金额必须同币种、同方向或为零，不能超分；已确定项允许为空。
- 每次最终接收方最多 1000 个；标识满足 `[a-zA-Z0-9:._-]{1,128}`，不得使用姓名、账号等敏感数据。
- 标识和尾差规则应由可信业务确定并保留，不能允许调用方通过改名操纵同余数排序。
- 返回不可变映射，合计严格等于总额；数学上支持负总额的镜像分配，但退款应依据历史原分配处理，
  不能拿当前比例重算后当成原交易的退款依据。

### `DecimalPrecision` / `DecimalTextSerializer`：实现支撑

- `DecimalPrecision` 是包内校验工具，不对业务模块开放；不要复制其逻辑形成另一套不一致的精度规则。
- `DecimalTextSerializer` 供高精度数值字段输出十进制字符串，避免科学计数法及前端浮点精度损失。
  它不校验商业语义，也不改变数值精度。
- 不将此序列化器全局套到所有数字；比例、数量等独立 DTO 字段需要接口层明确约定字符串传输。

## 3. 推荐的接入顺序

以下片段中的参数均由业务显式提供，没有生产默认值或固定分成比例：

```java
UnitPrice price = new UnitPrice(priceValue, currency, pricingUnit);
CalculatedAmount gross = price.calculate(confirmedQuantity);
CalculatedAmount share = gross.portion(effectiveRatio);
CalculationPolicy policy = new CalculationPolicy(
        policyKey, policyVersion, divisionScale, divisionRounding, settlementRounding);
CalculationPolicy.Settlement settlement = policy.settle(share);
Money payable = settlement.amount();
```

该片段只演示类型转换，不是一份通用收费公式。批量结算应先在**业务约定范围**内汇总中间值，再在约定节点舍入；
逐人、逐天、逐行还是整周期结算必须明确，不能为方便实现随意选择。
多方分配时，根据业务规则选择先确定总额再分配，或保留明确金额并指定余款方，不能各方独立舍入后假定账一定平。

## 4. 输入、存储和历史复算

- 从十进制文本构造 `BigDecimal`，不使用 `new BigDecimal(double)`，也不先经 `float` / `double` 运算再转回。
- 比例统一以 `1` 表示全部；接口不得猜测百分数、权重或档位文本的含义，不接受客户端自行替换已批准规则。
- 超精度、币种不同、超分配、非法策略等异常应明确处理，不能捕获后默认为零、截断或换成默认比例。
- 金额和高精度值传 JSON 时使用十进制字符串并保留币种；前端不以 JavaScript `Number` 作为精确计算依据。
- 数据库存储使用十进制类型，不用浮点类型。要求超精度拒绝时，不能只依赖 `NUMERIC(p,s)`：
  PostgreSQL 可能先按 scale 舍入，须参照精度契约使用不预先舍入的 `NUMERIC` 加显式容量和精度 `CHECK`。
- 保存原始单价、数量、单位、动态比例、适用规则、精度策略标识与版本、汇总范围、计算顺序、
  舍入前后结果、分配算法及最终分配。历史复算使用历史输入和版本，不能套用当前比例。
- 本包不自动持久化、不查询最新规则、不校验参与方权限，也不处理汇率或跨币种换算。

## 5. 与旧 `MoneyUtil` 的关系

- 旧工具保留是为了兼容，不表示新增交易计价应继续复用无币种的金额工具。
- 新增单价和中间计算不得调用已弃用的 `MoneyUtil.multiply/divide`；它们保留默认两位舍入，会提前损失精度。
- 展示格式化仅用于显示，不能把格式化结果回写为计价依据；旧人民币元分转换不是多币种转换器。
- 旧工具的加减法虽然保留输入精度，也不提供币种和阶段语义；新计价链优先使用本目录的值对象。

## 6. 后续维护检查

- 业务收费公式放业务模块，不在本目录增加固定价格、比例、税率、平台优先分配或万能交易父类。
- 新增纯计算能力时同步维护本指南、完整精度契约和中文 JavaDoc。
- 至少验证精度上下界、币种、正负与零、显式舍入、汇总顺序、尾差守恒、序列化及历史兼容；
  涉及存储约束时补充真实 PostgreSQL 验证。
- 按 `backend/README.md` 配置独立 `_test` 数据库，执行 `mvn -B -ntp -Pintegration clean verify`，
  不能用跳过测试或降低覆盖门禁替代验证。
