### 🔴 B1：闪电发薪的技术方案（高优先级，阻塞开发）

**问题描述**：
闪电发薪涉及资金流转，技术方案选择直接影响开发难度、成本和合规性。

**技术方案对比**：

| 方案 | 说明 | 优点 | 缺点 | 是否需要牌照 |
|---|---|---|---|---|
| **方案A：虚拟账户+资金托管** | 劳务公司充值到系统账户<br/>平台代发给员工<br/>资金沉淀在平台 | 用户体验好<br/>资金灵活调度 | 需要支付牌照<br/>资金安全责任大 | ✅ 需要 |
| **方案B：第三方支付通道** | 劳务公司充值到第三方支付账户<br/>系统调用API代发<br/>资金不在平台 | 无需牌照<br/>合规简单 | 受限于支付通道<br/>手续费较高 | ❌ 不需要 |
| **方案C：银行代发接口** | 劳务公司在银行开户<br/>系统生成代发文件<br/>银行批量转账 | 成本低<br/>合规性好 | 开发周期长<br/>用户体验一般 | ❌ 不需要 |

**技术团队需要决策**：
1. 我们有支付牌照吗？

   - [ ] 没有 → 只能方案B或C

   - [ ] 银行支付通道（如招商银行一网通）
   - [ ] 第四方聚合支付（如Ping++、BeeCloud）

3. 发薪到账时间要求？

   - [ ] T+1（次日到账，成本低）

4. 手续费由谁承担？
   - [ ] 平台承担（成本高，但用户体验好）
   - [ ] 劳务公司承担（需要明确告知费率）
   - [ ] 按比例分担

5. 日结工每天发薪，手续费压力大，是否需要优化？
   - [ ] 合并发薪（每天固定时间批量发，减少手续费）

### 🟡 B3：工时管理的技术实现（中优先级）

**问题描述**：
工时管理涉及双数据源对比和差异处理，技术实现方案需要明确。

**技术方案对比**：

#### 3.1 工时数据存储策略

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **方案A：双表存储** | 工厂考勤表 + 员工自报表<br/>分开存储 | 数据清晰<br/>便于追溯 | 查询复杂<br/>需要关联 |
| **方案B：单表+来源标识** | 一张工时表<br/>字段标识来源（工厂/员工） | 查询简单<br/>便于对比 | 数据耦合<br/>修改复杂 |
| **方案C：单表+差异调整表** | 以工厂数据为准<br/>差异记录到调整表 | 主数据清晰<br/>调整留痕 | 计算复杂<br/>需要合并 |

**推荐方案**：方案C（便于审计和追溯）

#### 3.2 工时对比算法

```
伪代码：
for each 员工 in 当月员工列表:
    工厂工时 = 从工厂考勤表获取
    员工工时 = 从员工自报表获取
    
    if 工厂工时 == 员工工时:
        状态 = "一致"
    elif abs(工厂工时 - 员工工时) <= 阈值:  # 如相差1小时以内
        状态 = "基本一致"，自动取平均值
    else:
        状态 = "有差异"，触发申诉流程
```

**技术团队需要决策**：
- 差异阈值设为多少？（建议1小时）
- 基本一致时，取哪个值？
  - [ ] 取工厂数据
  - [ ] 取员工数据
  - [ ] 取平均值
  - [ ] 取较大值（对员工有利）

### 🟡 B4：返费计算的技术实现（中优先级）

**问题描述**：
返费规则复杂（多档位、三种模式），需要设计灵活的计算引擎。

**数据库设计建议**：

```sql
-- 返费政策配置表（一个岗位可以有多条规则）
CREATE TABLE rebate_policy (
    id BIGINT PRIMARY KEY,
    position_id BIGINT,  -- 岗位ID
    type ENUM('人头费', '工时费'),  -- 类型
    
    -- 人头费字段
    days INT,  -- 在职天数条件（如3天、7天）
    amount DECIMAL(10,2),  -- 返费金额
    
    -- 工时费字段
    start_days INT,  -- 起算条件（如满30天）
    hour_price DECIMAL(10,2),  -- 每工时单价
    max_months INT,  -- 时间上限（月）
    max_hours INT,  -- 工时上限（小时）
    
    is_active BOOLEAN,  -- 是否启用
    created_at TIMESTAMP
);

-- 返费结算记录表
CREATE TABLE rebate_settlement (
```

```python
def calculate_rebate(employee, position):
    """计算员工的返费"""
    work_days = (now() - employee.join_date).days
    work_hours = employee.total_work_hours
    
    policies = get_rebate_policies(position.id)
    
    result = {
        '人头费': [],
        '工时费': []
    }
    
    # 计算人头费
    for policy in policies where type == '人头费':
        if work_days >= policy.days:
            result['人头费'].append({
                'days': policy.days,
                'amount': policy.amount,
                'status': '达标'
            })
    
    # 计算工时费
    for policy in policies where type == '工时费':
        if work_days >= policy.start_days:
            # 计算工时上限
            if policy.max_months:
                max_hours_by_time = get_hours_in_months(policy.max_months)
            else:
                max_hours_by_time = float('inf')
            
            max_hours_by_limit = policy.max_hours or float('inf')
            
            effective_hours = min(work_hours, max_hours_by_time, max_hours_by_limit)
            amount = effective_hours * policy.hour_price
            
            result['工时费'].append({
                'hours': effective_hours,
                'amount': amount,
                'status': '达标'
            })
    
    return result
```

### 🟢 B8：性能优化点（低优先级，MVP后优化）

**需要考虑的性能瓶颈**：

1. **工资核算**：
   - 5000人月度工资计算，耗时可能较长
   - 方案：异步队列 + 批量处理

2. **返费实时预估**：
   - 1000个经纪人同时查看预估返费
   - 方案：Redis缓存 + 定时更新

3. **日结工发薪**：
   - 每天1500笔发薪，高并发
   - 方案：消息队列削峰 + 批量发薪

4. **工时对比**：
   - 5000人每日工时对比
   - 方案：定时任务 + 增量对比
