## 一、模式调整

| 维度 | v0.2（SaaS 订阅） | v0.3（平台模式） |
|---|---|---|
| 需求来源 | 用工企业线下与劳务公司签约，项目经理在系统里建项目 | 用工方在平台免费发布用工需求，持证劳务公司竞标 |
| 平台收入 | 劳务公司订阅：基础版 5 个项目 + 增值服务 | 按人头/人天后置收管理费，由劳务公司承担 |
| 收费时机 | 前置 | 后置，只从用工方回款中分账扣收 |
| 用工方 | P1 企业端：确认工时、对账 | P0 核心角色：发需求、评标选标、确认工时、通过平台回款 |
| 资金 | 平台不参与；闪电发薪是增值服务 | 结算款和工资都走持牌第三方管控账户，T+0，平台不沉淀资金 |
| 功能开通 | 增值服务和项目配额控制功能可见性 | 不再按订阅和增值服务收费，取消项目配额；借支、发布岗位、发薪不再单独开通（保险代购的收费方式待定） |

设计目标：降低门槛的同时保持严谨，重点通过流程设计规避劳务中介拖欠和坏账。

产品原则：平台不替交易双方定商业条件。结算条件和计费口径由用工方需求和劳务公司应标决定，平台只负责计算、透明和风控。

## 二、角色与资质

| 角色 | 平台模式下的职责 | 准入 |
|---|---|---|
| 用工方 | 发布需求、评标选标、分配配额、确认工时、通过平台回款 | 企业实名认证；需求经平台审核后发布 |
| 劳务公司 | 应标、确认中标、建项目履约、发薪、结算返费 | 必须持证；平台审核通过后才能看到需求和应标 |
| 个人经纪人 | 给劳务公司已发布的岗位补人，拿返费 | 不能应标（一般没有许可证）；返费规则沿用 v0.2 |
| 工人 | 报名、入职、查看工时和工资、确认到账 | 实名，绑定本人银行卡 |
| 平台运营 | 资质审核、需求审核、发分账指令、风控 | 无 |

劳务公司内部角色（管理员、财务、项目经理、驻场、内部招聘专员）沿用 v0.2 第三节。

资质审核采用"平台先行 + 用工方并行"：

- 平台层：入驻时一次性核验营业执照、法人实名、许可证和失信记录。许可证的编号、类型、经营范围、有效期结构化录入，到期前提醒，过期自动停止应标。平台判断"能不能进场"。
- 用工方层：发需求时勾选资质要求，评标时直接看平台的核验标识和履约记录，不重复验真。用工方判断"适不适合这一单"。
- 需求增加"用工形式"字段（劳务派遣 / 劳务外包），它决定要查哪张证：劳务派遣需要劳务派遣经营许可证（注册资本不少于 200 万元）；职业中介和招聘需要人力资源服务许可证；人力资源服务外包据了解是备案制；纯业务外包一般不需要专门许可，但要防"假外包、真派遣"。以法务确认为准。

## 三、竞标（轻量）

竞标只包含发布、应标、截止、选标四个动作，不是完整的招投标系统。

```mermaid
graph LR
    A[用工方发布需求] --> B[平台审核]
    B --> C[持证劳务公司可见]
    C --> D[截止前应标]
    D --> E[截止后用工方评标]
    E --> F[选一家或多家<br/>分配配额]
    F --> G[劳务公司确认中标]
    G --> H[自动创建项目<br/>锁定中标快照]
```

| 规则 | 内容 |
|---|---|
| 可见范围 | 只有平台审核通过的劳务公司可见；不满足该需求资质要求的不能应标 |
| 时间 | 需求有用工开始日期、结束日期和应标截止时间，截止后不能再应标 |
| 应标次数 | 同一劳务公司对同一需求只应标一次，截止前可修改或撤回重投 |
| 多家中标 | MVP 必须支持；用工方给每家分配人数配额 |
| 中标确认 | 劳务公司在限定时间内确认（建议 24 小时），超时视为放弃，用工方重新选择 |
| 候补 | 建议：选标时可指定一家候补，原中标方出问题时由候补接手新增招聘 |
| 流标 | 无人应标或中标方全部放弃时，用工方可延长截止时间或修改需求重新发布 |
| 信息公开 | 沿用已确认规则：中标前只能看到自己的应标；中标后公开中标公司名称和中标金额；未中标方看不到其他公司的应标详情 |
| 已有设计 | [external-integration-confirmed.md](external-integration-confirmed.md) 中的竞标是对接本地临工市场 App 的增值服务；平台模式下改为平台自有能力，两者关系见第十二节 |

## 四、结算条件 = 中标条件

需求写的是用工方的期望条件，应标可以偏离，中标后应标条件存成快照，锁定为该项目的结算条件。例：需求为 500 人、工时单价 ¥25、账期 60 天，劳务公司应标 500 人、¥24、90 天；中标后按 500 人、¥24、90 天结算，结算总金额 = 确认工时 × ¥24。

- 评标页逐项标出应标偏离需求的地方，由用工方取舍。
- 多家中标时每家各锁各的，同一需求下单价和账期可以不同，按项目分别结算。
- 人工费是否随发薪周期支付也是可约定条件，可以写进需求，也可以在应标时提出，平台不设默认值。

中标快照字段：人数配额、中标单价、计量口径（工时 / 人天 / 人头）、账期、付款安排、承诺工价（建议新增）、平台管理费率。

费用链条，每个角色看到的费用都来自同一份确认工时：

```
结算金额 = 确认工时 × 中标单价（用工方应付）
应发工资 = 确认工时 × 承诺工价 + 补贴
实发工资 = 应发工资 − 扣款 − 借支（工人到手）
管理费   = 确认人天（或人头）× 平台费率
返费     = 达标人数 × 返费政策
```

应标风险校验（建议）：应标时同时填写结算单价和承诺工价，平台自动给出两个风险标识。

- 价差倒挂：中标单价减承诺工价，不够覆盖社保等法定成本和管理费。
- 垫资超能力：按账期推算的垫资需求，超过劳务公司经核验的垫资能力（授信额度、存款证明、历史履约）。

两个标识都不禁止应标，超过阈值的在中标确认前须补交保函或缩减人数。评标时用工方只看校验结果，不看具体承诺工价，避免暴露劳务公司的利润空间；中标后承诺工价用于招聘岗位展示，保证工人看到的工价和中标承诺一致。

垫资测算示例（假设每人每月 250 工时、承诺工价 ¥22/时、工资在月末后 15 天发放、500 人，每月工资 ¥275 万）：

| 账期 | 平均垫资 | 峰值垫资 |
|---|---|---|
| 60 天 | ¥412.5 万 | ¥550 万 |
| 90 天 | ¥687.5 万 | ¥825 万 |

单价每降 ¥1，劳务公司每月少收 ¥12.5 万；账期每多 30 天，平均多垫约 ¥275 万。按 ¥24 中标时每工时价差 ¥2，扣掉 ¥0.2 管理费剩 ¥1.8，可能不够覆盖社保等法定成本。

## 五、收费

- 用工方、劳务公司、工人都没有前置费用。
- 平台按人头/人天后置收管理费，由劳务公司承担。
- 管理费只随用工方回款分账扣收；用工方不回款，平台就不收。平台因此承担用工方的信用风险，用工方侧的约束见第七节。
- 计费口径边界（建议）：用工方定结算口径和账期，平台定自己的管理费率，计量单位跟随用工方口径，三方用同一份确认工时对账。
- 平台收入晚一个完整账期到账。按 90 天账期，10 月用工产生的管理费要到次年 1 月底前后到账，平台资金计划要提前考虑。
- 管理费率待定，文中 ¥2/人/天仅为测算占位。

## 六、资金管控

原则：

- 用工方给劳务公司的结算款、劳务公司给工人的工资都走平台，使用持牌第三方管控账户。
- 平台只发分账指令，不持有他人资金；资金始终在各方自己名下的账户之间流动，由持牌机构执行。
- 严格 T+0：回款到账即按顺序全部分完，不为未到期款项预留受限余额。
- 法律上付款方始终是劳务公司，合同、资金、发票三者一致；平台只就管理费开票。

| 主体 | 账户 |
|---|---|
| 用工方 | 照常对公转账到劳务公司的收款账号，不需要额外开户 |
| 劳务公司 | 每个项目一个子账户，项目之间资金隔离；另设保证金子账户（建议） |
| 工人、经纪人 | 绑定本人实名银行卡，不需要另开账户 |
| 平台 | 管理费收入户 |

回款分账顺序（T+0）：

```
用工方结算款 → 劳务公司项目子账户
                  ├─① 未付工资 → 工人银行卡
                  ├─② 到期未付返费 → 经纪人银行卡
                  ├─③ 管理费 → 平台收入户
                  └─④ 余额 → 劳务公司可提现
```

- 发薪：发薪日由平台按工资单从项目子账户代发到工人银行卡。子账户不留底，每期工资由劳务公司在发薪前充入；代发失败记为欠薪，之后任何一笔回款都先补这笔工资。
- 返费：到期时从项目子账户 T+0 扣付，余额不足的部分由返费保障金先赔付一部分（见第七节）。
- 借支：走同一通道打款，发薪时自动扣回；额度和审批规则沿用 v0.2 第四节第 5 部分。
- 可追溯：确认工时生成结算单、工资单、返费单和管理费账单，账单就是分账指令的依据，每条指令都能追溯到确认工时。
- 防绕开平台：中标协议约定结算款和工资必须走平台；到期时用工方在平台上标记"已付 / 未付 / 部分付"，标记已付但平台未收到的，劳务公司须限期补进项目子账户；工资单金额与"确认工时 × 承诺工价"偏差过大时预警。

持牌机构选型需确认的能力：子账户开立与冻结/解冻、对公转账自动识别并入账到对应子账户、收款户名显示劳务公司名称、批量代发到个人银行卡、T+0 执行、通道限额和退票重发。选型和开户审核通常是项目的关键路径，需要与产品设计同时启动。

v0.2 的"闪电发薪"（增值服务）由本节取代，成为默认发薪通道。

## 七、风控

### 7.1 保证金

保证金是劳务公司单独存入、冻结在自己名下的资金，不交给平台，与结算款的分账互不影响。

| 部分 | 用途 | 金额（建议） | 形式 |
|---|---|---|---|
| 防绕开平台 | 绕开平台结算、又未按期补进子账户的，扣保证金并降低信用等级 | 一个结算周期的管理费 | 现金冻结，或银行保函 |
| 返费保障 | 到期返费在子账户余额不足时先行赔付一部分 | 一个结算周期内预计到期返费的 30%，试点后调整 | 现金冻结在劳务公司自己的子账户 |

投标保证金：本地临工市场对接已确认"在线缴纳、中标后退还"；平台自有竞标是否沿用待定。讨论中的备选方案是 MVP 不收现金，中标后放弃的扣信用分、限制应标。

### 7.2 劳务公司侧预警与逾期分级（天数为建议值，试点校准）

| 时点 | 动作 |
|---|---|
| 发薪日前 3 天 | 检查项目子账户余额是否够发本期工资单，不够则提醒劳务公司 |
| 发薪日前 1 天 | 仍不够：通知用工方，冻结该项目新增入职 |
| 代发失败 | 记为欠薪，扣信用分，暂停新应标；之后回款优先补发 |
| 返费到期余额不足 | 返费保障金先赔付一部分，限期补足保证金 |
| 欠薪或返费逾期 15 天 | 经纪人端对该公司岗位显示风险提示 |
| 欠薪或返费逾期 30 天 | 停止新报名（已约面、已录用的照常入职）；通知相关用工方；启用候补中标方；进入催收 |

底线：任何阶段都不冻结在岗工人的工时记录和发薪流程，否则风控本身会造成欠薪。工人在小程序里提前看到工时、应发金额和预计到账日，是否到账以持牌机构回调为准，不由劳务公司填报。

### 7.3 用工方侧约束

平台和用工方之间没有直接的债权关系，只能靠平台规则：

- 用工方的历史回款准时率，对参与应标的劳务公司公开。
- 逾期的用工方在主页和需求页打标；逾期超过一定天数，暂停发布新需求。
- 劳务公司催收时，平台提供确认工时和结算单作为证据。
- 工时确认超时视为确认（时限待定），防止用工方拖延结算。

### 7.4 欠薪立场

平台不垫付工资，只管发薪通道和清偿顺序。这一点要写进协议和产品文案，避免工人以为平台在担保工资。派遣模式下用工方可能承担连带赔偿责任，用工方因此也有动力在平台上关注工资发放（以法务确认为准）。

## 八、账期

| 关系 | 谁来定 | 起算点 | 规则 |
|---|---|---|---|
| 用工方 → 劳务公司（结算款） | 中标条件 | 工时确认后 | 中标后锁定，单方不能改；经平台走账 |
| 劳务公司 → 平台（管理费） | 平台定费率 | 用工方回款时 | 只随回款分账扣收 |
| 劳务公司 → 经纪人（返费） | 劳务公司，写进返费政策 | 达标判定日 | 岗位发布时锁定快照，提报后不能改；逾期对经纪人可见 |
| 劳务公司 → 工人（工资） | 劳务公司，入职时锁定 | 工时确认后 | 发薪日不能因为用工方回款慢而顺延 |

用工方和平台之间没有直接资金往来，只有工时确认时限。

## 十、已有设计核实

本次核实了工时确认和争议处理、返费政策、各角色费用视图三项。

### 10.1 工时确认和争议处理：已完整覆盖，沿用

出处：v0.2 第四节第 3 部分（双数据源、差异处理流程、以工厂数据为初始基准）和第 6 部分（月结人工调整留痕、审批锁定、工资条确认）；[business-flow-diagrams.md](business-flow-diagrams.md) 第 3 节（四类差异场景、申诉、驻场核对、人事审批、锁定）和第 9 节（工资条异议）；[configuration-hierarchy.md](configuration-hierarchy.md) 工时管理配置（以工厂为准、开启申诉、日结工单数据源）。

平台模式下的增量：

- 用工方确认工时从 P1 提到 P0，确认工时是结算单、工资单、管理费和返费的共同依据。
- 多家中标时，用工方按劳务公司分别确认。
- 确认有时限，超时视为确认（时限待定）。

## 十二、待定事项和法务确认

业务待定：

1. 应标是否增加"承诺工价"，以及价差倒挂、垫资超能力两项风险校验的阈值。
2. 计费口径边界是否按第五节的建议划分。
3. 平台管理费率。
4. 返费保障比例（占位 30%）和防绕开平台保证金的金额。
5. 劳务公司垫资能力的核验方式。
6. 用工方逾期分级的天数和动作；工时确认时限。
7. 平台自有竞标是否收投标保证金。
8. 本地临工市场推送的需求与平台自有需求的关系：并存、取代，还是把临工市场作为一个需求来源。
9. 多家中标时同一工人的归属规则：同一需求下报名两家劳务公司是否算撞单，按什么规则判定。
10. 保险代购在平台模式下的收费方式。
11. 持牌机构选型（关键路径）。
12. 合同准备目录（为原客户准备的合同附件）是否一并废弃；报价方案和客户交付包已废弃（原客户因费用放弃），不再重做。

技术决策（已定）：

- 多租户与撮合域的冲突：已在 CLAUDE.md 新增"平台模式下的跨组织协作"规则解决。租户 = 组织（用工方、劳务公司、平台各一个租户）；工人和经纪人通过成员关系访问；跨组织数据由投递服务按字段白名单写入接收方租户，查询仍只读本租户。不放宽租户隔离；投递服务落地前需技术负责人评审。

法务确认（以下是讨论中的方向性判断，未核对官方原文）：

- 分账授权协议：劳务公司授权平台按确认账单发起分账。
- 《非银行支付机构监督管理条例》下平台代收代付的边界（"二清"）。
- 劳务公司子账户被司法冻结的风险：建筑业农民工工资专用账户有法定保护，劳务公司在支付机构开的子账户没有。
- 《保障农民工工资支付条例》第十八条（用工单位使用无派遣许可证单位派遣的农民工，拖欠工资时由用工单位清偿）在工厂派遣场景的适用。
- 《劳动合同法》第九十二条用工单位连带赔偿责任的适用范围。
- 《劳务派遣暂行规定》派遣用工比例不超过 10% 对需求发布的影响。
- 个人经纪人收推荐费是否构成无证职业中介；返费个税由谁代扣代缴。
- 各用工形式对应的许可和备案要求。
