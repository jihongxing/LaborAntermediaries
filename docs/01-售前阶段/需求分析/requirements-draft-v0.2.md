## 一、原始需求提炼

| 原始描述 | 理解 |
|---|---|
| 工作流程标准化 | 核心价值：把靠微信群和 Excel 跑的流程搬到线上 |
| 员工招聘、管理、借支、工资 | 员工从报名到离职的整个周期：报名 → 入职 → 在职 → 借支 → 发薪 → 离职 |
| 财务、驻场、项目经理、招聘专员 | 管理端的 4 类内部角色 |
| 内部人事专员 vs 外部经纪人 | 两类招聘渠道，结算方式不同：内部拿提成，外部拿返费 |
| 发招聘信息让别人报名，显示是谁招来的 | 报名链接带渠道标识，用来确定人头归属和结算返费 |
| 先做一家，再全国推广 | MVP 只服务一家公司，但架构从第一天就按多租户 SaaS 设计 |

## 二、业务全景

**参与方**：用工企业（工厂/客户）、劳务公司（系统的主要用户）、招聘渠道（内部专员和外部经纪人）、求职者/员工。

**业务规模（已确认）**：
- 在职员工：**5000人**
- 外部经纪人：**1000个**
- 合作工厂：**不限制数量**
- 经纪人层级：有二级经纪人，但系统不管理（他们自己内部结算）

**资金流**（三条线）：

```
用工企业 ──(工时×结算单价 / 管理费)──▶ 劳务公司 ──(工时×员工工价 − 借支 − 扣款 − 保险)──▶ 员工
                                           ├──(返费 / 提成)──▶ 经纪人 / 招聘专员
                                           └──(保险费+服务费)──▶ 保险公司
```

劳务公司利润 = 企业结算款 − 员工工资 − 渠道返费 − 运营成本（宿舍、车辆、保险等）。系统要能**按项目**把这笔账算清楚。

**主流程**：

```
企业提需求 → 项目经理建项目/岗位 → 发布招聘（生成专属链接/海报）
→ 求职者报名（自动记录渠道）→ 提报名单 → 安排面试（集合/接送）
→ 入职（建档/合同/购买保险/宿舍）→ 驻场日常管理（考勤/工时）
→ 借支 → 月度工资核算 → 闪电发薪 → 返费结算 → 离职
```

## 三、角色与权限

| 角色 | 职责 | 使用端 |
|---|---|---|
| 老板/管理员 | 全局配置、看数据、最终审批、增值服务开通 | Web 后台 |
| 财务 | 工资核算发放、借支打款、返费结算、企业对账回款、账户充值 | Web 后台 |
| 项目经理 | 对接企业，管理一个或多个项目：用工需求、工价、招聘进度、利润 | Web + 移动端 |
| 驻场 | 常驻工厂：接人、办入职、录工时、核对工时差异、借支初审、办离职、处理员工问题 | 移动端 |
| 内部招聘专员 | 公司员工，发职位、提报名单、跟进面试，按绩效拿提成 | 移动端 |
| 外部经纪人 | 独立中介，用专属链接招人、提报名单，按返费政策结算（人头费+工时费） | 小程序 |
| 求职者/员工 | 报名、查进度、录工时、查工时工资、申请借支、发起工时差异申诉 | 小程序 |
| 用工企业 | 提供工厂考勤数据、确认工时、对账 | Web/小程序 |

**内部专员和外部经纪人的区别**：内部专员能看到全部项目和人才库；外部经纪人只能看到自己招的人和对外开放的岗位。结算上，内部走工资加提成，外部走返费,还要考虑代扣个税或开票。

**企业端账号说明（已确认）**：
- MVP 阶段需要给工厂开账号
- 可能涉及与工厂现有系统对接（待确认具体系统）
- 权限范围：查看本厂员工数据、确认工时、对账

## 三.五、系统端口架构（客户明确要求）

**重要说明**：客户明确要求系统由**Web管理后台 + App + 微信小程序**三端组成，不是单一技术架构的项目。

### 端口与角色分配

| 端口 | 角色 | 核心功能 | 开发优先级 |
|---|---|---|---|
| **Web管理后台** | 管理员、财务、项目经理 | 全局配置、数据看板、工资核算、返费结算、项目管理、增值服务开通 | P0（MVP核心） |
| **App（移动端）** | 驻场、项目经理、内部招聘专员 | 录工时、借支审批、面试管理、入离职登记、驻场日报、实地操作 | P0（MVP核心） |
| **微信小程序** | 外部经纪人、求职者/员工 | 在线报名、工资条查看、借支申请、工时录入、返费查询、招聘链接分享 | P0（MVP核心） |
| **企业端（Web/小程序）** | 用工企业 | 工时确认、对账、员工数据查看 | P1（后续迭代） |

### 各端详细功能分配

#### 🖥️ Web管理后台（PC端，浏览器访问）

**使用场景**：办公室办公，需要大屏幕处理复杂数据

**角色与功能**：

1. **管理员**
   - 组织架构管理（部门、岗位、人员）
   - 账号权限配置
   - 系统全局配置（工资规则、扣款项、返费政策模板）
   - 增值服务开通管理（项目配额、功能开通）
   - 全局数据看板（在职人数、项目利润、应收应付）

2. **财务**
   - 工资核算（批量导入工时、自动计算、人工调整）
   - 工资发放（闪电发薪/导出银行代发文件）
   - 借支审批与打款
   - 返费结算审批与打款
   - 企业对账回款管理
   - 闪电发薪账户充值与余额管理
   - 财务报表（应收应付、项目利润表、资金流水）

3. **项目经理**
   - 项目/岗位配置（工价、返费政策、用工需求）
   - 招聘进度监控（各渠道表现、到面率、入职率）
   - 面试安排与批量通知
   - 提报名单审批
   - 借支审批
   - 项目利润分析
   - 用工需求与实际在职对比

**技术要求**：
- 响应式设计（支持1920×1080、1366×768分辨率）
- 支持Chrome、Edge、Safari浏览器
- 大数据量表格渲染优化（虚拟滚动）
- 支持Excel批量导入导出

### 三端数据同步说明

**核心原则**：
- 所有数据存储在后端统一数据库
- 三端通过API与后端通信，数据实时同步
- 关键操作（如工资发放、借支审批）需要加锁，避免并发问题

**实时同步场景**：
1. 驻场在App录入工时 → 员工在小程序立即可见
2. 财务在Web发放工资 → 员工在小程序立即收到通知
3. 员工在小程序申请借支 → 驻场在App收到审批通知
4. 经纪人在小程序提报名单 → 项目经理在Web看到新报名

**离线与弱网处理**：
- App支持离线录入工时，联网后自动上传
- 小程序在弱网环境下显示缓存数据，提示"数据可能不是最新"

### 三端开发与迭代策略

**MVP阶段（三端并行开发）**：
- Web管理后台：P0功能（工资核算、返费结算、项目管理）
- App：P0功能（驻场录工时、借支审批、入离职）
- 微信小程序：P0功能（员工报名、工资条、借支申请、经纪人返费查询）

**迭代优先级**：
1. 先保证三端的P0功能上线（核心流程跑通）
2. 再逐步补充P1功能（数据看板、驻场日报、企业端）
3. 最后优化体验（性能、交互、离线模式）

**开发资源分配建议**：
- Web管理后台：2-3名前端开发
- App：2名移动端开发（iOS + Android）或1名跨端开发（Flutter/RN）
- 微信小程序：1-2名小程序开发
- 后端：3-4名后端开发（API、数据库、定时任务）
- 测试：2名测试（三端功能测试 + 接口测试）

## 四、功能模块

### 1. 基础管理

- 组织架构、账号、角色权限，按项目隔离数据（比如驻场只能看自己驻的厂）
- 客户（用工企业）档案：企业信息、联系人、合作合同、结算方式、系统对接配置
- 项目/岗位配置：工种、**员工工价**、**企业结算价**、年龄/性别要求、班次、食宿条件、**返费政策**（人头费+工时费混合模式）、保险类别
- **项目配额管理**：基础版限5个项目，超出需开通增值服务

### 2. 招聘管理（MVP 核心）

- **职位发布**（增值服务）：生成职位页，以及带渠道码的分享链接/海报，方便在微信里转发
- **在线报名**：姓名、手机、身份证（支持 OCR 识别）；自动记录是哪个渠道来的
- **提报名单**：手动录入或 Excel 批量导入
- **归属与撞单规则**（劳务行业最常见的纠纷）：
  - 以身份证号作为每个人的唯一标识
  - 先报先得，设保护期（比如 15 天内没面试就释放给别人）
  - 撞单时自动提示，必要时人工裁定，所有操作留记录
- **面试安排**：时间、集合点、接送车辆，批量通知
- **状态流转**：报名 → 已提报 → 待面试 → 通过/未通过 → 已入职/未到岗
- **招聘看板**：按渠道统计到面率、入职率、留存率

### 3. 员工管理

- 档案：身份证、银行卡、紧急联系人、渠道来源、所在项目
- **入职**：合同、体检、工服押金、宿舍分配、**必须购买保险**（入职前置条件）
- 在职：调岗、转项目、黑名单
- **考勤工时**（双数据源）：
  - **工厂考勤**：驻场导入工厂给的考勤表
  - **员工自报**：员工在小程序自己录工时
  - **差异处理流程**：
    ```
    员工发现差异 → 发起工时差异申诉 → 驻场核对 → 人事审批
    → 调整工时记录（保留调整痕迹）→ 最终确认锁定
    ```
  - 大部分情况两个数据源一致，有差异时以工厂数据为初始基准
- 离职：区分正常离职、自离、辞退；离职时自动触发借支清算和返费达标判定
- **人才库**：离职员工可以再推荐。这个行业员工回流率很高

### 4. 保险管理（新增模块）

**业务模式（已确认）**：
- 员工入职必须购买保险，费用由劳务公司出
- 不同工作岗位的保险类别和价格不同
- 系统对接保险公司接口自动购买
- 劳务公司赚取保险差价（成本价 vs 对外服务价）
- **可作为增值服务**：平台提供保险代购服务，收取服务费或差价

**功能设计**：
- 岗位与保险类别关联配置
- 入职时自动触发保险购买流程
- 保险费用自动计入员工扣款或劳务公司成本
- 保险单管理：查看、续保、退保
- 理赔流程记录（工伤出险）

**待确认问题**：
- 保险公司接口是否支持API对接？
- 保险代购是否需要特殊资质？
- 差价部分如何定价和结算？

### 5. 借支管理（增值服务）

**业务规则（已确认）**：
- 流程：员工在小程序申请 → 驻场初审 → 项目经理/财务审批 → 打款 → 发工资时自动扣回
- **额度控制**：由劳务公司自己配置额度比例和次数限制
  - 可借额度 = 已出勤工时 × 工价 × 比例（比如 50%）− 已借金额
- **借支次数和打款时间**：由劳务公司配置决定
- **借支利息**：需要保留接口，未必第一期就做
  - 利息计算方式待确认（按日？按月？）
  - 利息扣除时机待确认（发薪时一起扣？单独还款？）
- 可配置的规则：入职 N 天内不能借、单次和每月上限、借支次数
- 风险点：借支的主要坏账来自员工借完就走。系统要实时显示每个人的"已借 vs 应发"

**功能开通控制**：
- 借款功能属于增值服务，需单独开通
- 未开通时，该功能对所有角色不可见

### 6. 工资管理

**业务模式（已确认）**：
- 工资由劳务公司发放，不是工厂直接发
- 支持多种发薪方式：微信、支付宝、银行转账
- **员工分为两类，发薪周期不同**：
  - **日结工**：当日或次日结算发放（临时工、小时工、短期项目）
  - **月结工（劳务派遣）**：按月发放（长期派遣、稳定项目）

**功能设计**：
- 规则按项目配置：小时工价、加班倍率、夜班补贴、全勤奖、阶梯工价
- 扣款项：借支、住宿、水电、餐费、工服、体检、保险
- **员工类型标记**：岗位/员工需要标记"工资类型"（日结/月结）
- **日结工核算流程**：
  - 每日工时确认 → 自动计算当日工资 → 次日发放
  - 计算公式：当日工时 × 日工价 = 应发工资
  - 一般不涉及复杂扣款（保险、住宿等可能由员工自理）
- **月结工核算流程**：
  - 月度工时汇总 → 自动计算 → 人工调整（留痕）→ 审批 → 锁定
  - 计算公式：月度总工时 × 工价 + 各种补贴 - 各种扣款 = 实发工资
  - 扣款项包括：借支、住宿、水电、餐费、工服、体检、保险
- **工资条**：员工在小程序查看并确认，减少争议
- **闪电发薪**（增值服务，详见第7节）
  - 日结工发薪频次高（每天都有），对系统性能和资金流要求高
  - 月结工发薪集中（每月固定日期），批量处理

**借支规则差异（待确认）**：
- 日结工是否允许借支？（建议不允许，当日即结算）
- 月结工可以借支，扣款规则如第5节

- 充值后，可以通过系统给员工发工资
- 支持发薪渠道：微信、支付宝、银行转账

**关键技术问题（待确认）**：

- 充值方式：银行转账、第三方支付、预充值？

### 8. 渠道结算（返费/提成）

**返费政策（已确认）**：
- 外部经纪人支持三种模式：
  1. **纯人头费**：员工在职满 N 天，一次性给 X 元
  2. **纯工时费**：每工时 X 元，到员工离职或满 N 个月为止
  3. **混合模式**：人头费 + 工时费同时存在
- 每个岗位可以独立配置返费政策
- **达标规则由劳务公司自己配置**，支持多档位设置

**返费达标档次（已确认）**：
- 标准档次选项：**3天、7天、15天、30天、60天、90天**
- 劳务公司可根据岗位特点灵活配置
- **人头费和工时费的结算周期差异**：
  - **人头费**：时间较短即可结算，灵活配置
    - 示例：满3天给¥50，满7天给¥100，满15天给¥200，满30天给¥500
  - **工时费**：一般要求**至少入职满30天**后才开始结算
    - 原因：需要整月结算，避免零散计算
    - 示例：入职满30天后，开始按工时结算，每工时¥2，最多结算3个月

**功能设计**：
- 返费政策按岗位配置：
  - **按人头**（多档位）：
    ```
    满3天给¥50
    满7天给¥100
    满15天给¥200
    满30天给¥500
    满60天给¥800
    满90天给¥1200
    ```
  - **按工时**：
    - 起算条件：入职满 N 天（一般≥30天）
    - 单价：每工时 X 元
    - 结算上限：满 N 个月或累计 N 工时（取先到的）
  - **阶梯人头费**：不同阶段给不同金额，累加发放
  - **混合模式**：人头费（多档位）+ 工时费（满30天起算）并行计算
- **系统自动判定逻辑**：
  - 每日检查员工在职天数，触发人头费档位
  - 每月检查工时累计，计算工时费（需满足起算条件）
  - 生成待结算明细，推送给财务审批
- **经纪人端能实时看到自己招的人、在职状态和预计返费**。这是留住经纪人的关键
  - 可见信息：姓名、岗位、入职时间、当前在职天数、实时工时、已达标档位、预计返费
  - 不可见信息：员工工资、其他经纪人数据、劳务公司利润
- 结算审批、打款、代扣个税

**配置示例（供参考）**：
```
岗位A（流水线工人）：
  人头费：
    - 3天：¥50
    - 7天：¥100
    - 30天：¥500
  工时费：
    - 起算条件：入职满30天
    - 单价：¥2/小时
    - 结算上限：3个月或500小时

岗位B（仓库搬运工）：
  人头费：
    - 7天：¥100
    - 15天：¥200
  工时费：无

岗位C（长期驻厂）：
  人头费：无
  工时费：
    - 起算条件：入职满60天
    - 单价：¥3/小时
    - 结算上限：6个月
```

**待确认问题**：
- 混合模式的两笔返费是分开结算还是合并结算？
- 员工未达标离职（如入职25天，未满30天档位），已达标的档位（如3天、7天）返费是否给？
- 自离（不辞而别）的返费规则是否有特殊处理？
- 工时费的起算条件是否统一为30天，还是允许每个岗位自定义？

## 七、为全国推广提前考虑的设计点

- **多租户**：数据模型从第一天就带租户 ID，MVP 阶段只开一个租户
- **规则配置化**：工价、扣款、返费、借支额度、审批流都做成配置，不写死在代码里。每家公司、每个工厂的规则都不一样
- **地区差异**：各地最低工资和社保政策不同
- **合规**：
  - 劳务派遣许可证、人力资源服务许可证
  - 身份证、银行卡这类敏感信息要加密存储，并按《个人信息保护法》做授权和脱敏
  - 返费的个税处理
  - 经纪人层级不超过两级，避免被认定为多级分销（已确认：系统不管理二级经纪人）
  - **支付牌照**：如果闪电发薪采用资金托管模式，需要支付业务许可证
  - **保险经纪资质**：如果保险代购作为增值服务，可能需要保险经纪/代理牌照
- **经纪人网络**：经纪人通常同时给多家劳务公司供人。推广后，做成平台级经纪人账号（一个账号对接多家公司）会是很强的增长点

## 八、已确认的调研答案

基于 v0.1 的9个待确认问题，现已确认：

- [x] **Q1 业务模式**：工资由劳务公司发放，不是工厂直接发
- [x] **Q2 返费规则**：外部经纪人支持三种模式（人头费、工时费、混合），每个岗位独立配置
- [x] **Q3 工时来源**：工厂有考勤工时 + 员工自己也可以录工时，大部分情况一致，有差异由员工发起申诉，驻场和人事核对
- [x] **Q4 借支**：额度和次数由劳务公司自己配置，打款时间由公司决定，发薪日自动扣回，需预留借支利息接口
- [x] **Q5 规模**：不限制合作工厂数量，在职5000人，外部经纪人1000个
- [x] **Q6 经纪人层级**：有二级经纪人，但系统不需要管理（他们自己结算）
- [x] **Q7 使用习惯**：都用微信，能接受小程序
- [x] **Q8 发薪方式**：必须支持微信、支付宝、银行转账三种方式
- [x] **Q9 企业端**：需要给工厂开账号，可能涉及与工厂现有系统对接

## 九、新增功能需求

基于调研补充的3个新增需求：

1. **保险代购**（第4节新增）
   - 员工入职必须购买保险
   - 不同岗位对应不同保险类别和价格
   - 对接保险公司接口
   - 差价作为增值服务收入

2. **闪电发薪**（第7节新增）
   - 劳务公司账户充值模式
   - 系统内快速给员工发工资
   - 支持微信、支付宝、银行转账

3. **收费模式确定**（第5节新增）
   - 基础版：5个项目
   - 增值服务：项目数超5个、借款、发薪、发布岗位、代购保险
