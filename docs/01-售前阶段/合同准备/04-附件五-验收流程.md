# 附件五：验收流程

**合同附件编号**：附件五  
**文档性质**：合同附件，具有法律效力  
**适用合同**：劳务中介管理系统开发合同  
**项目总价**：¥140万元（方案B）

---

## 🎯 验收目的

本流程用于规范项目各阶段的验收工作，确保：
1. **验收标准明确**：基于《附件一：模块验收标准清单》
2. **验收流程规范**：谁来验、怎么验、多久验完
3. **验收期限刚性**：防止无限拖延验收
4. **验收结果有效**：签字确认后具有法律效力

---

## 📋 验收原则

### 五大原则

| 原则 | 说明 |
|------|------|
| **1. 客观标准** | 以《模块验收标准清单》为准，不以主观"满意度"为标准 |
| **2. 期限刚性** | 每个验收阶段都有明确期限，逾期视为验收通过 |
| **3. 分阶段验收** | 按5个阶段分批验收，不是一次性验收全部 |
| **4. 书面确认** | 验收结果必须书面签字，口头或微信无效 |
| **5. 一次性提出问题** | 验收期内必须一次性提出所有问题，不得反复提 |

### 验收与付款的关系

| 验收阶段 | 验收通过后触发的付款 | 未通过的后果 |
|---------|---------------------|-------------|
| 需求评审验收 | ¥14万（10%） | 不进入开发阶段 |
| 第一期开发验收 | ¥28万（20%） | 不进入第二期开发 |
| 第二期开发验收 | ¥28万（20%） | 不部署生产环境 |
| 上线验收 | ¥21万（15%） | 不开通正式账号 |
| 最终验收 | ¥7万（5%） | 不视为项目完成 |

**注**：首付¥42万（30%）在合同签订时支付，不需要验收。

## 🔄 五阶段验收流程

### 阶段1：需求评审验收

**验收时机**：项目启动后2周

**验收内容**：
- 产品需求文档（PRD）
- 页面原型图（Web/App/小程序）
- UI设计稿（视觉设计）
- 数据库设计文档（ER图、表结构）
- API接口设计文档

**验收标准**：
1. PRD功能描述清晰、完整，覆盖15个模块
2. 原型图交互流程合理，符合业务逻辑
3. UI设计稿风格统一，符合客户品牌形象
4. 数据库设计合理，能支撑业务需求
5. 接口设计清晰，前后端对接无障碍

**验收方式**：
1. 开发方召集需求评审会议
2. 逐一讲解PRD、原型图、设计稿
3. 客户提出修改意见
4. 开发方修改后重新提交
5. 客户签署《功能清单确认书》

**验收期限**：
- 开发方提交文档后，客户有**5个工作日**审阅
- 客户提出修改意见后，开发方有**3个工作日**修改
- 修改后重新提交，客户有**3个工作日**确认

**逾期处理**：
- 若客户在5个工作日内未提出意见，视为验收通过
- 若客户在3个工作日内未确认修改稿，视为验收通过

**验收文档**：《功能清单确认书》（合同附件二）

**重要性**：⭐⭐⭐⭐⭐  
此阶段最关键，确认后即锁定功能范围，后续变更需付费。

**验收文档**：《第一期验收报告》

**重要性**：⭐⭐⭐⭐  
核心模块验收，直接影响后续开发。

### 阶段4：上线验收

**验收时机**：第二期验收通过后1周

**验收内容**：
- 系统成功部署到生产服务器
- 域名和SSL证书配置完成
- 数据迁移完成（如有历史数据）
- 管理员账号开通
- App上架应用市场（iOS/Android）
- 小程序发布到微信平台

**验收标准**：
1. Web后台可通过域名正常访问（HTTPS）
2. App可从应用市场下载安装并登录
3. 小程序可扫码进入并正常使用
4. 测试账号可正常登录三端
5. 核心业务流程可正常操作（如新增员工、录入工时）

**验收方式**：
1. 开发方完成部署后，通知客户
2. 客户实际访问系统并操作
3. 客户填写《上线确认书》
4. 双方签字确认

**验收期限**：
- 系统上线后，客户有**5个工作日**确认

**逾期处理**：
- 若客户在5个工作日内未确认，视为验收通过

**验收文档**：《上线确认书》

**重要性**：⭐⭐⭐  
标志着系统正式交付使用。

---

### 阶段5：试运行验收（最终验收）

**验收时机**：上线后2周（试运行期满）

**验收内容**：
- 系统稳定性（试运行期间无重大故障）
- 性能指标达标（响应时间、并发能力）
- 功能完整性（15个模块全部可用）
- 数据准确性（工资、返费计算正确）
- 文档完整性（用户手册、培训视频）

**验收标准**：
1. 试运行期间系统可用率≥99%
2. 页面响应时间<2秒
3. 支持500并发用户无压力
4. 财务数据计算准确，无重大错误
5. 提供完整的用户手册和培训视频

**验收方式**：
1. 试运行期满后，开发方提交《项目验收申请》
2. 客户组织最终验收会议
3. 客户填写《项目验收报告》
4. 双方签字确认

**验收期限**：
- 试运行期满后，客户有**7个工作日**组织验收

**逾期处理**：
- 若客户在7个工作日内未组织验收，视为验收通过

**验收文档**：《项目验收报告》（最终验收文档）

**重要性**：⭐⭐⭐⭐⭐  
项目正式完成的标志，触发最后一笔验收款支付。

## ⚠️ 验收注意事项

### 给客户的提醒

**✅ 应该做的**：
1. **按时验收**：在规定期限内完成验收，避免被视为默认通过
2. **一次性提问题**：验收期内尽量一次性提出所有问题，避免反复
3. **基于清单验收**：按《模块验收标准清单》逐项测试，不凭感觉
4. **书面记录问题**：用《验收报告》记录问题，不要只口头说
5. **签字慎重**：签字前确认问题已记录完整，签字后不得反悔

**❌ 不应该做的**：
1. **无限拖延验收**：不能以"再试用一段时间"为由拖延
2. **验收后反悔**：签字后不能以"我当时没想到"为由提新问题
3. **主观评价**：不能以"我觉得不好看"、"我不满意"为由拒绝验收
4. **口头验收**：不能只口头说"可以了"，必须书面签字
5. **超范围验收**：不能以《功能清单确认书》之外的功能未实现为由拒绝验收

### 给开发方的提醒

**✅ 应该做的**：
1. **提前通知**：提交验收申请前1周通知客户，让客户有时间准备
2. **提供便利**：提供测试账号、测试数据、操作指南
3. **及时响应**：客户提出问题后，3个工作日内给出反馈
4. **保留证据**：所有验收相关的邮件、报告都要存档
5. **主动沟通**：验收期快到期时，主动提醒客户

**❌ 不应该做的**：
1. **突袭验收**：不能不提前通知就突然提交验收申请
2. **拒绝修改**：客户合理的问题必须修复，不能拒绝
3. **催促签字**：不能为了收款而催促客户仓促签字
4. **隐瞒问题**：不能隐瞒已知问题，等验收后再暴露
5. **口头承诺**：不能口头承诺"验收后再改"，必须先改后验收

## 🚫 验收争议处理

### 常见争议及处理

| 争议类型 | 客户观点 | 开发方观点 | 处理方式 |
|---------|---------|-----------|---------|
| **功能理解不一致** | "这不是我要的" | "清单里就是这样写的" | 查阅《功能清单确认书》，以书面为准 |
| **Bug还是变更** | "这是Bug，应该免费修" | "这是变更，需要付费" | 查阅《功能清单确认书》，清单有=Bug，无=变更 |
| **验收标准争议** | "这个功能不好用" | "符合验收清单标准" | 以《模块验收标准清单》为准，不以主观感受为准 |
| **验收期限争议** | "我还没测试完" | "已经超过验收期限了" | 以合同约定期限为准，逾期视为通过 |
| **问题严重程度** | "这是严重问题" | "这是轻微问题" | 按影响范围判断：影响核心流程=严重，不影响=轻微 |

### 争议升级机制

如果项目经理层面无法解决争议，按以下层级升级：

1. **第一层**：双方项目经理协商（3个工作日）
2. **第二层**：双方公司高层协商（5个工作日）
3. **第三层**：第三方技术专家鉴定（费用双方各半）
4. **第四层**：提交仲裁或诉讼

**原则**：先协商，协商不成再找第三方，最后才走法律程序。

## 📝 附录：常见问题FAQ

### Q1：验收期限到了，但我还没测试完怎么办？

**A**：按合同约定，逾期视为验收通过。如确有特殊原因，可在期限内书面申请延期（需开发方同意）。

### Q2：签字后发现新问题，还能要求修复吗？

**A**：分情况：
- 功能性Bug（清单中有但未实现）→ 维保期免费修复
- 签字时遗漏的问题 → 维保期免费修复（需证明确实是Bug）
- 新需求 → 需走变更流程，另行付费

### Q3：可以只口头说"验收通过"吗？

**A**：不可以。必须签署书面《验收报告》并盖章，口头或微信无效。

### Q4：我可以先不签字，等用一段时间再验收吗？

**A**：不可以。试运行期就是"用一段时间"，试运行期满后7个工作日内必须验收，逾期视为通过。

### Q5：验收时发现的问题，开发方要多久修复？

**A**：
- 严重问题：5个工作日内必须修复
- 一般问题：可约定在验收通过后的维保期修复
- 轻微问题：可约定在维保期修复
