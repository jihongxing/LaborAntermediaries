# 劳务供应链交易平台项目推进建议 v0.1

- 编制日期：2026-10-24。
- 文档状态：推进建议，待项目负责人评审；本次明确要求固化的七条护栏以[根 README](../../../README.md#后续工作的七条护栏)为准。
- 适用范围：自主推进的劳务供应链交易平台，不适用原客户定制合同、报价或历史排期。
- 本次产出：固化护栏、提出推进机制、拆解业务包；不表示业务代码已开发、规则整体获批或真实业务获准启用。
- 执行入口：[业务包拆解与首批实施清单](../../02-开发阶段/产品设计/05-战略与实施/业务包拆解与首批实施清单-v0.1.md)。

## 1. 当前起点与目标

当前产品主线是“真实需求 → 应标中标 → 人员供给与履约 → 计量核验 → 核算与收付对账 → 信用与复购”。管理功能服务这条主线；平台审核、中立监督、投诉复核及自身问责横向贯穿。

截至编制日，通用后端底座具备业务开发准入，但尚无平台业务闭环；前端各端仍为预留目录。底座不提供登录、令牌签发或组织成员管理。现有测试通过只对应底座，不能解释为平台业务验收通过。详见[后端说明](../../../backend/README.md)。

推进目标不是再增加一套泛化功能清单，而是把现有需求变成有责任人、有规则状态、有技术依赖、有正反向验收证据的业务包，并沿完整交易链交付。

## 3. 推进方式：按完整链路分包，不缩减交付范围

| 顺序 | 业务结果与对应业务包 | 放行条件 |
| --- | --- | --- |
| A. 身份与组织基础 | BP-01：可信登录、成员关系、平台岗位与业务组织权限可运行。 | 身份方案、成员与授权规则获批；服务端隔离、撤权及越权测试通过。 |
| B. 用工方源头 | BP-02、BP-03：两类组织入驻；用工方需求可补正、审核、发布和变更。 | 组织准入与需求准入分离；未审、暂停、越权或版本失效不能开放应标；必要审核申诉同步可用。 |
| C. 应标中标 | BP-04、BP-05：合格供应商应标，用工方选标和分配配额，双方确认后幂等建立项目。 | 应标承诺、配额、撤回、版本和确认规则获批；平台不代选标或代确认。 |
| D. 供给与现场履约 | BP-06～BP-08：三类供给来源、招聘入职、排班打卡与工时复核形成可追溯事实。 | 供给责任、必要授权、人员关系、现场权限及有效计量规则明确；App、小程序与 Web 交接验证通过。 |
| E. 核算与资金闭环 | BP-09～BP-11：工资、返费、分类账单、账期、支付与回款核验闭环。 | 核算规则、合同、收费收取及适用通道安排获批；模拟与真实环境隔离，未知结果、部分收付和冲正可恢复。 |
| 横向同步 | BP-12～BP-14：平台治理、交易信用事实及贡献/推荐增长随相关业务落地。 | 不能统一留到主链末尾；具体展示、奖励付款等按各自门禁放行，尚未批准部分不冒充生效功能。 |
| F. 完整交付评审 | BP-15：多端全链路及运营接手。 | 全链路业务、平台治理、权限、资金、数据保护和恢复演练通过，外部依赖及启用审批证据齐备。 |

这些顺序表达依赖，不代表必须全部串行。Web、独立 App、工人/经纪人小程序按相应角色任务一起设计和实现；不采用“先内部闭环、资金另算、暂缓 App”的缩减方案。

分包完成只证明对应能力达到其验收状态，不等于可以在真实业务中局部启用。是否启用须检查实际业务链的全部依赖，不以本表阶段名称替代审批。

## 4. 四条并行工作线

1. **经营与客户发现**：识别用工方需求经办人与采购决策人，验证真实需求、采用门槛、供应商参与意愿、账期与保证金诉求；使用获授权的脱敏案例，不承诺尚未验证的效果。
2. **规则与产品设计**：优先处理首批业务包决策；同步调研后续供给、计量、资金及增长规则，避免界面做完才发现无权操作或无法结算。
3. **工程与测试**：按业务包完成领域对象、状态、跨组织投递、各端任务、接口、迁移和回归测试；复用底座，不重新建设与业务无关的通用平台。
4. **外部依赖与运营准备**：从现在核实身份签发、支付机构产品、账户与资金权属、合同授权、数据保护和审核复核人员安排；用机构证据约束设计，不假定目标通道必然可用。

具体资金模型参见[资金闭环与账期分析](../../02-开发阶段/产品设计/03-账单与资金/资金流转闭环与账期模型分析-v0.1.md)和[支付与保理架构建议](../../02-开发阶段/产品设计/05-战略与实施/未来平台支付与保理资金架构建议-v0.1.md)。支持线下对公回款不等于资金能力取消；真实收付仍需凭证核验、账期、对账与责任主体。

## 5. 每个业务包的标准工作流

1. **收集依据**：关联 FR、专项章节、角色、业务问题与前置业务包；与历史文档冲突时回到当前唯一来源。
2. **做决策**：记录待决项、可选方案、影响、角色负责人、正式决策人与证据；未指定人员或日期就填写“待指定/待排定”，不推断已批准。
3. **形成可开发合同**：明确领域对象、业务状态、版本、确认权、跨组织可见性、接口契约、技术依赖和异常恢复；未决部分只做隔离原型或设计验证。
4. **实现纵向切片**：按一个可观察的角色任务打通前后端与数据，不以数据库表或页面数量作为交付单元；同步实现必要审核、申诉和审计。
5. **验收并留证**：执行正向、拒绝、重复、并发、越权、版本变更及故障恢复场景，记录规则版本、构建版本、环境、结果和证据。
6. **单独评审真实启用**：核对合同、机构、授权、人员、运维与完整链路依赖；未满足不启用，不能用隐藏按钮或“测试通过”代替服务端限制。

## 6. 分开记录四类状态

| 维度 | 可使用的状态 | 证明材料 |
| --- | --- | --- |
| 规则批准 | 待决策 / 部分批准 / 已批准 / 已变更 | 决策人、日期、适用范围与规则版本；未批准子项明确阻断。 |
| 开发完成 | 未开始 / 设计中 / 开发中 / 待验收 / 已完成 | 代码或变更、迁移、接口和包内测试；文档完成不算业务开发完成。 |
| 联调验证 | 未验证 / 模拟通过 / 真实依赖验证通过 / 不通过 | 对应端、组织、机构、环境与用例证据；模拟通过不等于真实机构通过。 |
| 真实启用 | 未申请 / 受阻 / 待审批 / 已批准启用 / 已停用 | 业务、财务/合规及运维等必要签收，启用范围、配置与回退责任。 |

这些是分别维护的维度，不压成一个“完成百分比”。业务包可能规则部分批准、设计可继续，但资金启用仍受阻。任何维度无证据时，标记未证实，不自动补齐。

## 7. 责任与评审节奏建议

- 项目负责人：确认优先级、决策责任和启用范围；不以项目排期覆盖专业硬性阻断。
- 产品负责人：维护需求来源、角色流程、规则版本及可观察验收；不自行替审批人决定收费和资金。
- 技术负责人：评估方案、依赖、工作量、隔离与恢复；具体业务实现不得混入非业务底座。
- 测试负责人：把业务规则转为用例并检查证据，尤其跨组织、资金及申诉复核。
- 业务运营及财务/合规：验证需求与资质、岗位回避、账务与支付路径、合同和必要外部意见。

以上为职责分工，不假设已有完整团队；实际承担人待指定。小团队可兼任，但受限制事项的独立复核不得由原经办自行完成。

建议每完成一个可评审业务包就做规则/设计或验收评审；每周核对阻断项、依赖、风险与下一个可交付切片。只有在规则范围和外部依赖清楚后再估算工期，不沿用旧合同周数。

## 8. 下一步立即执行

1. 以业务包文档中的 BP-01～BP-03 作为首批评审对象，确认 DP-01～DP-08 的责任人、方案及批准范围。
2. 产品、技术和测试共同走读“注册 → 加入/建立组织 → 组织审核 → 需求补正与审核 → 发布”的主流程及拒绝场景。
3. 优先闭合身份签发与成员授权方案；在其约束下准备迁移、接口与 Web 首批任务，不开放免认证或默认超级管理员捷径。
4. 按放行子项实施首批业务切片，同时继续准备后续 App、小程序、支付与现场规则；未放行部分保留设计和评审任务。
5. 更新业务包的四类状态与证据后，再推进应标、中标、履约和资金，不靠新写一份总结宣称进度完成。

## 9. 观察什么结果

过程关注决策阻断是否消除、业务包是否有验收证据、跨端/组织交接是否完整。真实启用后再观察有效需求、合格应标、有效履约人天、账单确认、真实收付、复购、每有效人天综合成本和服务费实收。

贡献与推荐增长观察真实引荐到合格服务收入实收的转化、实际奖励成本及争议；平台治理观察核验依据、回避复核、执行反馈和纠错同步，而不是只看关单速度。

不将注册数、页面数量、文档数量或历史市场预测当作飞轮成立的证据，也不在缺乏经营基线时设定未经验证的增长目标。
