# 用户账号与手机号认证技术方案 v0.1

> **状态：已批准实施。** 负责人已批准第 2 节产品基线、第 12 节技术决策定稿建议和第 15 节实施步骤。按 Step 0 至 Step 8 顺序实施，每一步必须通过自身门禁后才能进入下一步；真实短信、微信业务适配及工人/经纪人业务仍遵守本文范围边界。

## 1. 目标

在现有公开门户、组织审核和组织工作空间基础上，建立正式的全平台用户账号能力，覆盖手机号注册、登录、密码找回、平台组织审核、成员加入审批和组织空间准入。账号身份需要能够被 Web、小程序及后续独立 App 使用；各端业务范围按阶段启用。当前阶段使用 Mock 短信，不接入真实短信供应商。

本方案将个人账号、手机号验证、组织认证和组织成员授权分开建模。用户完成登录不代表其组织已通过认证，也不代表其已获得组织内业务权限。

## 2. 已确认基线

以下六项已经负责人确认，是后续补充方案必须保留的产品规则：

1. 登录以短信验证码为主，密码为备用方式；注册时设置密码，找回密码时通过手机短信验证后重置。
2. 一个手机号只能对应一个账号；一个账号可以加入多个组织。
3. 手机号验证成功后账号立即进入 `ACTIVE`；进入组织业务空间仍须组织审核通过且成员关系有效。
4. 普通账号不做人工资格审核。人工审核针对组织准入和组织成员；账号只设置锁定、禁用和安全事件。个人实名认证或账号人工审核若纳入范围，必须另行定义状态、材料和审核流程。
5. 工人和经纪人可以只用微信完成首次低风险使用；涉及银行卡、合同、支付和申诉时，必须先绑定手机号或完成后续批准的等效高强度恢复因子。仅微信身份不能直接执行这些敏感操作。
6. 微信身份无法取得 `unionid` 时，不能自动跨小程序关联；用户必须先登录已有账号，再显式绑定新的小程序身份。

以上基线已确认，但不等于整份技术方案已经批准。第 12 节的技术决策定稿建议需要与实施范围一起整体确认。

## 3. 当前系统现状

当前后端是 Spring Security Resource Server，验证外部 RSA JWT；没有账号表、手机号身份、凭据、注册/登录/找回端点、Refresh Token 会话或本地 JWT 签发能力。`ExecutionContext.Identity` 从 JWT 取得 `actorId`、可选 `tenantId` 和权限集合。

现有组织模块已经实现组织申请、补正、提交、平台审核、组织加入申请和管理员审批。其审核身份来自可信 JWT。现有前端门户和组织工作空间仍是演示/联调状态，账号中心尚未接入真实身份服务。

因此方案建议新增认证模块并复用现有组织和成员审核能力，不重建组织审核状态机。

## 4. 目标架构建议

首期将认证能力放入现有 `backend` 部署单元，并在代码职责上独立于组织业务模块。这样可以沿用当前数据库事务和部署流程，同时保留未来拆分身份服务的边界。认证服务是多端共用的身份入口，不代表所有角色都使用 `web-admin`，也不代表首期要同时交付所有端。

```text
浏览器
  ├─ 注册 / 登录 / 找回
  └─ 选择当前组织
          │
          ▼
backend
  ├─ auth：跨端账号、手机号、凭据、短信挑战、会话、JWT 签发
  ├─ identity：组织审核、成员关系、组织内角色授权
  ├─ workforce：工人个人档案、本人求职及履约关系（后续业务范围）
  ├─ recruitment：经纪人合作关系、渠道授权及归属（后续业务范围）
  └─ business：需求、应标及其他交易业务
          │
          ├─ MockSmsGateway（local/test）
          └─ PostgreSQL
```

认证模块签发 RS256 JWT，业务接口继续通过 Resource Server 验证。私钥只供签发组件读取，资源服务器只需要公钥。JWT 的 `sub` 为账号 ID；`tenant_id` 表示当前选定的组织上下文，可为空；`permissions` 必须由服务端按账号状态、成员关系、组织状态及权限规则计算，不能由客户端提交。

JWT 令牌签发、Refresh Token 轮换及浏览器存储方式按第 12 节技术决策定稿建议执行，整体批准前不得进入实现。

### 4.1 统一账号主体与多端边界

建议平台只维护一套全局认证账号。用户从 Web、小程序或后续 App 登录时，使用同一个账号主体和手机号唯一约束；端之间不复制账号表，也不以“Web 用户”“工人用户”或“经纪人用户”建立互不相通的登录身份。

```text
auth_account（全局登录主体）
  ├─ auth_phone_identity（全局唯一手机号）
  ├─ auth_credential（密码备用凭据）
  ├─ organization_membership（组织及组织内角色）
  ├─ worker_profile / worker_relationship（工人资料及本人与业务关系）
  └─ broker_affiliation（经纪人身份及经授权的合作范围）

Web / 工人小程序 / 经纪人小程序 / 后续 App
  └─ 使用同一账号认证；每次请求按端入口、业务关系和资源权限单独授权
```

账号表只回答“谁在登录、账号能否登录”；它不直接承载 `WORKER`、`BROKER`、`EMPLOYER_ADMIN` 等汇总角色字段。权限来自独立的组织成员关系、工人个人档案与本人关系、经纪人合作授权，以及具体业务资源的授权检查。一个自然人可同时是工人和经纪人，但两种关系分别建立、分别审查；员工推荐朋友也不会自动授予经纪人合作权限。

工人不因注册账号就自动生成完整员工档案、入职关系或劳动关系。只有用户开始相应流程并提供必要资料后，才创建或关联对应业务资料；身份证、银行卡、协议等个人敏感信息不进入认证账号表。经纪人也不因创建账号就取得渠道权限；经纪人合作关系应由适用劳务供应商或授权责任方建立，并限定组织、岗位、有效期和可见字段。经纪人账号不默认成为供应商组织成员，也不因此取得供应商 Web 工作空间权限。

认证账号的 `tenant_id` 不能被解释为个人当前或历史所属组织。用工方和供应商 Web 可在选定组织后使用组织上下文；工人本人数据应按 `account_id` 与本人业务关系授权查询；经纪人数据应按有效合作授权范围查询。工人和经纪人可能跨项目、跨组织持续使用同一账号，不能把其账号固定归属到单一供应商租户来绕过或破坏隔离规则。

建议认证会话绑定发起登录的客户端/端类型，且令牌中不得因客户端自报名称授予权限。客户端标记只用于审计和策略约束，最终授权仍由服务端核验账号状态、组织成员关系、经纪人授权、人员本人关系及目标资源。具体端标识和令牌声明待会话方案评审。

### 4.2 双网络与不同登录入口

项目需要同时维护两套业务网络，但不应维护两套互不相认的账号系统：

```text
全局账号主体
       │
       ├─ 网络 A：用工方组织 ⇄ 劳务供应商组织
       │       组织成员、需求、应标、选标、项目和结算授权
       │       主要入口：供应链 Web；供应商成员可复用账号进入供应商 App
       │
       └─ 网络 B：劳务供应商 ⇄ 经纪人／渠道
               合作授权、岗位范围、人员归属、返费和合作结算
               主要入口：供应商 Web/App + 经纪人小程序

工人个人关系：通过工人小程序访问本人求职、入职、排班、工时和工资，
不因为登录就成为供应商组织成员，也不自动拥有网络 B 的经纪人权限。
```

网络 A 的边由组织和组织成员关系授权；网络 B 的边应由独立的 `supplier_broker_affiliation`（名称可在业务包设计时调整）表达，至少包含供应商、经纪人账号或经纪人主体、合作状态、岗位/区域范围、有效期、归属规则版本和可见字段。它不是 `business_membership` 的别名，经纪人不能因建立合作关系而取得供应商 Web 的组织管理员权限。

工人的 `worker_profile` 和 `worker_relationship` 也不应直接复用经纪人合作关系。工人可以由本人报名、供应商招聘或经纪人推荐进入某次业务关系；来源、本人资料、入职/派驻关系和经纪人归属分别留存。这样才能处理同一工人跨供应商、跨项目复用账号，同时限制每个角色只能看到必要字段。

### 4.3 统一账号，多种登录身份

建议把“账号”与“登录身份”拆成一对多关系：

```text
auth_account
  ├─ PHONE（可选绑定，手机号全局唯一）
  ├─ WECHAT_MINIPROGRAM（provider + subject 唯一）
  ├─ WECHAT_OPEN_PLATFORM / APP（provider + union key 唯一）
  └─ 其他经过评审的身份提供商
```

新增 `auth_login_identity`（或将其作为 `auth_phone_identity` 的统一上位表）保存 `provider`、提供商主体摘要、必要的加密展示信息、绑定时间和状态。微信 `openid`、`unionid` 等值由服务端通过授权码向微信服务端换取，客户端提交的值不能直接作为身份依据。不同小程序的 `openid` 可能不同；能够取得微信开放平台 `unionid` 时，优先把它作为跨端关联键，否则必须通过已认证账号完成显式绑定。

供应商成员使用手机号短信或密码登录 Web，也可以在供应商 App 使用同一账号；这只是不同客户端入口，不会创建第二个供应商账号。工人和经纪人可以先用微信登录建立轻量账号，再按业务需要绑定手机号。绑定手机号后，手机号仍遵守“一号一账号”；若该手机号已有账号，系统不能静默新建或自动合并，必须要求用户先完成原账号认证，再执行双重确认绑定。

没有手机号的微信账号可以登录低风险的个人功能，但不能因此获得找回密码能力。需要密码登录、敏感个人资料变更、银行卡/支付绑定、合同确认或争议申诉时，应先完成手机号绑定或其他已批准的高强度恢复因子。微信账号被注销、无法找回或提供商关系变化时，恢复流程只能依赖已绑定的手机号或后续批准的恢复方式。

账号合并永不依据姓名、证件号码片段、设备或“看起来是同一个人”自动完成。两个登录身份归并到同一 `auth_account`，必须由已登录旧账号发起、验证新增身份，并记录不可篡改的安全事件；发现登录身份已绑定其他账号时应停止流程，进入受控找回/人工处理，不覆盖原关系。

### 4.4 令牌上下文不能替代两套网络关系

基础 Access Token 只标识账号和会话。`tenant_id` 仅在服务端确认用户选择了有效的用工方/供应商组织成员上下文时使用，不应把工人或经纪人的账号永久归入某个供应商租户，也不应把多个供应商租户同时塞进一个 JWT。

推荐的上下文规则是：

| 场景 | `tenant_id` | 额外授权依据 |
|---|---:|---|
| 供应商/用工方 Web 或供应商 App | 当前组织 ID | 有效 `business_membership`、组织状态、具体权限 |
| 工人小程序访问本人事项 | 为空 | `account_id` 等于本人，并且存在有效 `worker_relationship` |
| 经纪人小程序访问合作事项 | 通常为空 | 有效 `supplier_broker_affiliation`、岗位范围、期限和字段白名单 |
| 经纪人进入某个供应商的受控协作空间 | 仅在明确授予组织上下文时填写 | 经纪人合作授权不能自动升级为组织成员权限 |

如果后续需要把某个供应商合作范围固化为短时会话，应增加服务端生成的关系范围上下文或短期 scoped token；不能信任客户端传来的供应商编号，也不能仅靠前端路由隐藏其他供应商。

## 5. 账号与组织状态

### 5.1 账号状态

```text
PENDING_PHONE_VERIFICATION ──手机验证成功──► ACTIVE
PENDING_IDENTITY_VERIFICATION ──提供商验证成功──► ACTIVE
                                                   ├─安全策略触发──► LOCKED
                                                   └─平台禁用──────► DISABLED
```

- `PENDING_PHONE_VERIFICATION`：注册流程已开始但手机号尚未验证。
- `PENDING_IDENTITY_VERIFICATION`：微信等外部提供商的授权交换尚未完成，不能建立正式会话。
- `ACTIVE`：手机号或已批准的外部登录身份完成验证，可以建立登录会话；手机号注册路径仍遵循第 2 节已确认基线。
- `LOCKED`：达到登录安全策略后暂时禁止认证，恢复条件待确定。
- `DISABLED`：平台禁用账号，恢复需要具备权限的人工操作。

微信/其他提供商完成验证后，可以让工人或经纪人先拥有 `ACTIVE` 的轻量账号，但账号可能只有提供商恢复能力。没有绑定手机号或其他批准的恢复因子时，不开放需要强恢复能力的操作；这不改变手机号注册“验证成功后立即 `ACTIVE`”的已确认基线。

### 5.2 组织准入和成员授权

```text
账号 ACTIVE
  ├─创建组织申请
  │    DRAFT ──提交──► PENDING_REVIEW
  │                         ├─► APPROVED
  │                         ├─► NEEDS_CORRECTION ──补正并重提──┐
  │                         └─► REJECTED                       │
  │                                                            └─► PENDING_REVIEW
  └─申请加入已批准组织
       PENDING_MEMBERSHIP ──管理员审批──► ACTIVE / REJECTED
```

手机号验证、组织审核和成员审批是不同的门槛。工作空间访问至少要求账号 `ACTIVE`、组织准入 `APPROVED`、成员关系 `ACTIVE`，并且当前操作权限有效。

## 6. 注册、登录和找回流程

### 6.1 注册

1. 用户提交手机号和注册请求。
2. 服务端规范化手机号，创建用途为 `REGISTER` 的短信挑战并调用 Mock 网关。
3. 用户提交验证码、密码和必要的账号资料。
4. 服务端原子校验挑战并消费验证码，创建 `ACTIVE` 账号、手机号身份和密码凭据。
5. 注册成功后建立登录会话，用户进入账号中心；组织业务资格仍由组织流程决定。

注册开始响应不透露手机号是否已注册。手机号唯一约束负责处理并发注册；重复注册应引导用户登录或找回，不能返回账号敏感信息。

### 6.2 登录

短信验证码为主路径，密码为备用路径：

```text
短信登录：发起 LOGIN 挑战 ──验证验证码──► 建立会话
密码登录：手机号 + 密码 ──校验凭据─────► 建立会话
```

两种路径都必须检查账号状态。错误提示统一，不区分手机号不存在、密码错误、账号锁定等可用于枚举账号的细节；账号持有人在完成验证后可以在安全页面看到具体状态。

### 6.3 找回密码

```text
发起 PASSWORD_RESET 挑战
  ──短信验证──► 一次性重置凭证
  ──设置新密码──► 消费重置凭证并更新凭据
                   ├─撤销已有登录会话
                   └─记录安全事件
```

找回开始接口统一响应，不暴露手机号是否注册。重置凭证必须短时有效且只能消费一次。密码找回不能修改组织成员关系或组织审核状态。

## 7. Mock 短信边界

通过 `SmsGateway` 抽象短信发送能力；首期提供 `MockSmsGateway`，未来可在另行评审后接入真实服务商。

Mock 短信只允许在 `local` 和 `test` profile 启用。开发人员可从本地 Mock 收件箱或本地日志取得挑战验证码；测试直接读取测试替身。验证码不得由生产 API 返回，也不得在生产日志、异常或审计记录中出现。生产 profile 若装配 Mock 网关，应用应启动失败。

验证码使用随机 6 位数字，按用途绑定，有效期 5 分钟，验证最多尝试 5 次，重发冷却 60 秒；手机号和来源 IP 按第 12.3 节限流。数据库只保存挑战验证码的带密钥摘要，不保存明文。

挑战状态：

```text
ISSUED ──验证成功──► VERIFIED ──业务消费──► CONSUMED
   ├──超过有效期─────────────────────────► EXPIRED
   ├──超过最大尝试次数───────────────────► LOCKED
   └──新挑战替代或主动作废───────────────► CANCELLED
```

建议用途枚举为 `REGISTER`、`LOGIN`、`PASSWORD_RESET`、`PHONE_CHANGE`。首期不开放换绑手机号，`PHONE_CHANGE` 只是未来扩展，不代表当前范围。

## 8. 数据模型建议

认证表属于跨组织共享数据，不设置 `tenant_id`，并在项目共享表清单中显式登记。组织业务表仍按现有租户隔离规则管理。

| 表 | 职责 | 主要安全约束 |
|---|---|---|
| `auth_account` | 账号状态、展示名、时间戳、失败计数及凭据版本 | 不存储明文密码或验证码 |
| `auth_login_identity` | 账号与手机号、微信或其他提供商身份的绑定 | `provider + subject` 全局唯一；提供商主体由服务端换取并保存摘要 |
| `auth_phone_identity` | 若仍作为独立子表，保存账号与手机号的唯一绑定 | 手机号加密保存，使用带密钥摘要做唯一查找 |
| `auth_credential` | 密码凭据 | 使用成熟 PasswordEncoder 保存慢哈希 |
| `auth_verification_challenge` | 短信验证码挑战、用途、尝试次数和时限 | 原子消费、摘要存储、过期清理 |
| `auth_password_reset_ticket` | 找回验证成功后的短时一次性重置凭证 | 只保存凭证摘要，单次消费，不能直接授予业务权限 |
| `auth_refresh_session` | Refresh Token 会话及轮换/撤销状态 | 只保存 Token 哈希，记录会话族和重放 |
| `auth_security_event` | 匿名认证事件和结果 | 不写入密码、验证码、完整手机号或 Token |
| `auth_consent_record` | 用户协议和隐私告知的版本接受记录 | 只追加版本和时间，不保存协议正文或敏感内容 |

以下不是认证核心表，但必须与认证账号保持一对多或多对多的独立关系，不能把业务资料塞进 `auth_account`：

| 业务关系 | 作用 | 账号获得该关系的条件 |
|---|---|---|
| `worker_profile` / `worker_relationship` | 工人个人资料、求职、入职、派驻和本人履约关系 | 通过对应业务流程建立，账号注册本身不自动创建劳动或入职关系 |
| `broker_affiliation` | 经纪人合作组织、授权岗位、有效期、归属和可见字段 | 由适用劳务供应商或授权责任方建立和撤销，账号注册不自动取得渠道权限 |
| `business_membership` | 用工方、劳务供应商或平台组织内的成员角色 | 组织审核通过、加入申请获批并满足组织权限规则 |

工人和经纪人可能不是 `web-admin` 用户，但仍应使用同一全局账号体系，以便手机号唯一、找回密码、安全事件和跨端本人访问保持一致。是否首期实现其业务关系表和小程序入口，属于对应业务包，不属于本认证方案的实现授权。

如果采用 `auth_login_identity` 统一表，`auth_phone_identity` 可以作为手机号专用视图或后续兼容结构，不应形成两套独立的手机号唯一约束。提供商身份记录需要保留绑定和解绑历史，解绑前必须保证账号仍有可用的登录/恢复方式。

手机号建议采用 E.164 规范化。首期是否只支持中国大陆号码需要产品范围确认。手机号密文可复用项目 `CryptoService` 的用途隔离加密；用于唯一查询的 HMAC 密钥需要独立配置并定义轮换策略。

密码使用 Spring Security `PasswordEncoder`，具体算法、参数和密码政策按第 12 节定稿建议执行，整体批准前不得实现。

数据库迁移应遵循当前 Flyway 统一序列，认证结构建议以新的连续版本迁移实现。具体版本号、约束、索引、保留期限和清理任务在设计补充后确定。

## 9. API 草案

以下是契约草案，不是已批准或已实现的接口：

| 方法与路径 | 用途 |
|---|---|
| `POST /auth/register/start` | 发起注册短信挑战 |
| `POST /auth/register/verify` | 验证手机号并创建账号 |
| `POST /auth/login/sms/start` | 发起短信登录挑战 |
| `POST /auth/login/sms/verify` | 验证短信并登录 |
| `POST /auth/provider/{provider}/exchange` | 服务端交换微信等提供商授权码；已绑定身份直接登录，未知身份进入受控建号或绑定流程 |
| `POST /auth/login/password` | 手机号密码登录 |
| `POST /auth/password-reset/start` | 发起密码找回 |
| `POST /auth/password-reset/verify` | 验证找回短信并取得一次性重置凭证 |
| `POST /auth/password-reset/complete` | 设置新密码并撤销旧会话 |
| `POST /auth/token/refresh` | 轮换会话并刷新 Access Token |
| `POST /auth/logout` | 撤销当前会话 |
| `GET /auth/csrf` | 为 Web Cookie 会话取得短时 CSRF Token |
| `GET /auth/me` | 读取当前账号摘要 |
| `GET /auth/organizations` | 读取当前账号的组织和成员状态 |

认证端点需要匿名访问；业务端点保持认证要求。认证错误使用稳定 `errorKey` 和真实 HTTP 状态，响应不得回显验证码、密码、Token 或完整手机号。端点是否使用 `/api/auth/...` 需遵循当前 API 前缀，并在接口评审时确认。

## 11. 安全、审计与失败处理

- 验证码按用途、手机号和挑战 ID 绑定；校验、尝试次数递增和消费必须支持并发安全。
- 对注册、登录和找回使用统一外部响应，避免账号枚举。
- 注册通过手机号唯一约束处理并发；相同挑战重放必须失败。
- 登录连续失败按第 12.3 节临时锁定；平台禁用和延长锁定必须走受控安全操作。
- 密码找回后撤销所有旧 Refresh Session，并让旧 Access Token 尽快失效；采用会话版本还是短时 JWT + 撤销表，待令牌方案确认。
- 组织上下文由服务端查询成员和组织状态生成，客户端不能自报 `tenant_id` 或权限。
- 登录、登出、密码修改/重置、锁定、禁用和组织权限变更需要记录不含秘密的安全事件。
- 数据库、密钥或会话状态不可用时认证失败关闭，不降级为匿名业务访问。
- 私钥、手机号 HMAC 密钥、加密密钥通过受保护的部署配置提供，不能提交仓库。
- CORS、Cookie、CSRF、反向代理速率限制和安全响应头必须按第 12 节定稿建议落地，不能只在前端做限制。

## 12. 技术决策定稿建议

本节把前文待补充事项收敛为可实施的技术基线。它们不是代码已经实现的事实，仍需负责人整体批准；批准后不再在实现过程中临时改变安全语义。

### 12.1 令牌、浏览器会话与 CSRF

1. Access Token 使用 RS256 JWT，有效期 15 分钟；继续使用 `sub`、可选 `tenant_id`、`permissions`、`iss`、`aud`、`exp`、`jti`，增加 `session_id`、`context_type` 和可选 `context_id`。
2. Refresh Token 使用 256 位以上随机不透明值，有效期 30 天，数据库只保存哈希；每次刷新轮换旧值。旧值重放时撤销整个会话族并要求重新登录。
3. Web 端 Access Token 只放内存；Refresh Token 使用 `HttpOnly` Cookie，生产环境 `Secure=true`、`SameSite=Strict`，开发环境也不允许脚本读取。
4. 所有依赖 Cookie 的变更接口（刷新、登出、绑定手机号等）同时校验精确 `Origin`、CSRF Token 和会话状态。新增 `GET /auth/csrf` 取得短时 CSRF Token，前端通过 `X-CSRF-Token` 回传；`allowCredentials` 只对配置的明确来源开启。
5. Web 会话与未来 App/小程序会话属于同一账号但各自拥有 Refresh Session。退出当前设备只撤销当前会话，退出全部设备撤销账号全部会话；密码找回、账号禁用和平台强制退出撤销全部会话。

### 12.2 手机号、密码和 Mock SMS

1. 首期只接受中国大陆手机号，输入统一规范化为 `+86` E.164；非法区号、重复号码和无法规范化的输入统一返回参数错误。
2. 注册最小资料为手机号验证码、密码、用户协议/隐私告知版本接受；显示名可选，身份证、银行卡、真实姓名等资料延后到业务流程采集。
3. 密码使用 Spring Security Argon2id `PasswordEncoder`，长度 8–128 个字符；不强制脆弱的字符组合规则，服务端拒绝常见测试密码和控制字符。若最终运行环境无法提供 Argon2 原生支持，才切换到 BCrypt，并记录算法版本和参数。
4. Mock SMS 只在 `local`/`test` profile 装配。验证码放入仅内存的 `MockSmsMailbox`，默认保留 10 分钟；本地可通过仅监听回环地址的开发查询接口按 `challengeId` 查询，测试直接注入收件箱，不写生产日志。
5. 生产 profile 发现 Mock SMS Bean、固定验证码或开发查询接口时启动失败。验证码永不出现在正式 API 响应、审计事件、异常消息或生产日志。

### 12.3 限流、失败和账号状态

1. 首期使用 PostgreSQL 持久化挑战和窗口计数，不引入 Redis；达到多实例容量或需要分布式限流时再单独引入 Redis 方案。
2. 同手机号同用途短信发送间隔 60 秒，每小时最多 5 次；同 IP 每小时最多 20 次；单挑战最多验证 5 次。超限返回统一的稍后重试提示，不泄露账号存在性。
3. 密码登录在 15 分钟窗口内累计 5 次失败后锁定账号 15 分钟；成功密码找回并完成手机号验证后可解除临时凭据锁定。`DISABLED` 是平台状态，不能自行解除。
4. 账号、手机号和 IP 的安全事件只保存摘要和结果，不记录密码、验证码、完整手机号或 Token；严重重复失败可由平台按安全流程延长锁定。

### 12.4 即时失效与外部 JWT 兼容

1. Access Token 15 分钟内有效；密码找回、退出全部设备、账号禁用和高风险权限撤销立即撤销 Refresh Session，并将会话/账号安全版本纳入 Token 校验。现有 JWT 撤销表继续作为失败关闭的基础。
2. 组织成员撤销和组织状态变化必须由业务授权服务在每次组织写操作重新查询；不能只依赖 JWT 中已有的 `permissions`。
3. 本地账号发行方使用独立 RSA 私钥，资源服务器使用对应公钥。外部 JWT 不自动转换成 `auth_account`，也不把外部 `sub` 直接当作本地注册账号。
4. 外部 JWT 兼容只在 `local`/`test` 或明确的迁移开关下开启；生产启用前必须建立逐条外部身份映射和审计记录。没有映射的外部身份不能获得本地账号能力，兼容窗口结束后关闭多发行方验证。

### 12.5 统一账号和多端身份

1. 全平台采用一套 `auth_account`，工人档案、经纪人合作关系和组织成员关系单独建模；不在账号表添加不可变的 `WORKER`/`BROKER`/`SUPPLIER_ADMIN` 角色字段。
2. 供应商成员可用同一账号登录 Web 和供应商 App；工人/经纪人可通过微信身份首次建立轻量账号，低风险范围按第 2 节基线开放，敏感操作先绑定手机号或等效恢复因子。
3. `auth_login_identity` 对 `provider + provider_subject` 建立唯一约束。微信服务端通过授权码取得 `openid/unionid`；有 `unionid` 时用于跨端关联，没有时必须先登录已有账号再显式绑定，不能自动合并。
4. 提供商身份解绑前必须确认账号仍有有效登录/恢复方式；同一微信身份已绑定其他账号时停止绑定并进入受控找回，不覆盖原账号。

### 12.6 工人、经纪人入口和业务关系

1. 工人/经纪人首次微信登录接受用户协议和隐私告知后创建 `ACTIVE` 轻量账号；不能因登录自动创建入职关系、劳动关系或经纪合作关系。
2. 工人业务由 `worker_profile`/`worker_relationship` 表达；经纪人合作由 `supplier_broker_affiliation` 表达。供应商邀请，经纪人确认后关系进入 `ACTIVE`；平台风险或合同要求时再进入平台审核，不默认把经纪人加入供应商组织成员。
3. 经纪合作关系默认状态为 `INVITED`、`PENDING_ACCEPTANCE`、`ACTIVE`、`SUSPENDED`、`ENDED`；岗位/区域范围、有效期、归属规则版本和可见字段必须随关系保存。
4. 关系终止后禁止新增岗位提报和新合作动作，但保留本人已形成的归属、应付、申诉和必要历史查询。

### 12.7 ExecutionContext 和数据保留

1. 基础身份仍使用 `actorId=auth_account.id`；`tenantId` 只表示当前选定的组织上下文。工人本人上下文使用 `context_type=PERSONAL`，经纪合作使用 `context_type=BROKER_AFFILIATION`，均不能伪造供应商 `tenant_id`。
2. Token 上下文只作为服务端授权输入的一部分；每次敏感操作仍重新查询账号、组织成员、工人关系或经纪合作关系，不能只信任 `context_id`。
3. 挑战和重置凭证在过期/消费后保留 24 小时，已撤销/过期会话保留 90 天，安全事件默认保留 2 年；有效账号身份和必要审计按适用隐私、财税和争议保留要求保存。
4. 清理任务只删除超过期限且不再关联未结案件的技术数据；清理失败必须可重试并记录，不删除业务事实或已形成的支付/争议凭证。

## 13. 验证和验收建议

实现阶段至少需要覆盖：

- 注册、短信登录、密码登录、找回密码的成功与错误流程。
- 用户协议/隐私告知版本接受、Cookie 会话 CSRF 校验和明确 Origin 校验。
- Mock SMS 在 `local/test` 可用，在 `prod` 无法装配或启动失败。
- 验证码过期、重放、用途串用、并发消费和最大尝试次数。
- 同手机号并发注册只有一个账号成功，外部响应不泄露账号存在性。
- 密码找回后所有旧会话不可继续刷新。
- Refresh Token 轮换、复用检测和登出撤销。
- 一账号多组织、跨组织越权、组织未通过审核和成员被撤销场景。
- 认证 API 不在日志或响应泄露验证码、密码、完整手机号和 Token。
- 提供商身份绑定冲突、无 `unionid` 显式绑定和解绑后恢复能力检查。
- PostgreSQL 集成测试、API 安全测试和浏览器注册到工作空间准入流程。

业务实现验证按 `backend/README.md` 执行，并使用独立 `_test` PostgreSQL。验证结果只能说明实现符合已批准基线，不代表生产身份迁移或真实短信服务已就绪。

## 14. 暂不纳入本轮

- 真实短信服务商接入。
- 邮箱登录、企业微信、SSO。
- 微信真实登录适配器、小程序登录页面和工人/经纪人业务流程；本方案只定义其作为登录身份提供商的接入边界。
- MFA/TOTP、设备指纹和复杂反欺诈。
- 个人实名认证、政府数据核验或普通账号人工准入审核。
- 账号合并、生产身份迁移。
- 完整消息通知中心。
- 工人档案、报名、入职、排班、考勤、工资和支付业务。
- 经纪人合作签约、岗位提报、归属、返费和奖励业务。
- 与账号认证无关的履约、人员、资金和结算模块。

若后续补充使这些事项进入范围，应更新本方案并单独评估业务规则、数据和安全影响。

## 15. 分阶段实施步骤

### 15.1 实施原则

认证实现按“共享身份底座 → 手机号认证闭环 → JWT/会话 → 组织上下文 → Web 入口 → 外部身份扩展”的顺序推进。每一步都必须先通过本步骤的验收门禁，再进入下一步；任何前端页面完成都不代表后端授权完成。

首个可交付纵向切片只覆盖：手机号注册、短信登录、密码备用登录、短信找回、账号会话、组织状态查询和 Web 账号入口。工人/经纪人业务关系、真实微信登录、小程序页面和真实短信供应商不进入首个切片。

### 15.2 实施前必须冻结的技术决定

第 2 节六项产品基线和第 12 节技术决策定稿建议构成实施前的完整冻结清单。负责人批准本方案后，以下值作为首期实现合同；实现过程中如需改变，必须先更新本文并重新评审，不得在代码中隐式改变安全语义。

| 决定 | 当前建议基线 | 验收依据 |
|---|---|---|
| 登录身份表 | 统一 `auth_login_identity`；手机号、微信等按提供商建模，`provider + subject` 唯一，手机号唯一约束只保留一份 | 迁移约束、绑定冲突测试 |
| Access Token | RS256 JWT，15 分钟；保留现有 Claims，增加会话和上下文声明 | Resource Server 验证和过期测试 |
| Refresh Session | 30 天、随机不透明 Token、只存哈希、每次轮换；重放撤销会话族 | 轮换、重放、登出集成测试 |
| Web 存储与 CSRF | Access Token 内存；Refresh Token `HttpOnly` Cookie；生产 Secure/SameSite=Strict；变更接口校验 Origin + CSRF Token | Cookie/CSRF/API 浏览器测试 |
| 手机号范围 | 首期只接收中国大陆 E.164（`+86`）号码 | 格式化和唯一性测试 |
| Mock SMS | 只装配 `local`/`test`；内存收件箱保留 10 分钟；生产发现 Mock Bean 即启动失败 | profile 启动失败和日志扫描测试 |
| 限流与锁定 | PostgreSQL 计数；短信 60 秒/小时 5 次/IP 小时 20 次；单挑战 5 次；密码失败 5 次/15 分钟后锁 15 分钟 | 并发、暴力尝试和恢复测试 |
| 外部 JWT | 本地发行方独立密钥；外部 JWT 只在明确迁移开关下接受并须有身份映射 | 双发行方/关闭兼容回归测试 |
| 微信适配 | 本轮只实现提供商 SPI、身份绑定模型和显式绑定契约，不接真实微信 | 适配器契约测试，生产无 Mock/假微信 |
| 多端上下文 | `tenant_id` 只表示组织成员上下文；工人个人和经纪合作使用独立上下文类型 | 个人/合作越权及跨组织测试 |
| 数据保留 | 挑战/重置 24 小时，会话 90 天，安全事件 2 年；清理不影响未结业务证据 | 清理任务和保留期测试 |

### 15.3 具体步骤与交付物

#### Step 0：冻结认证契约和安全配置

1. 将已确认产品基线和第 12、15.2 节的技术决定登记为实现合同。
2. 定义 `auth` 模块边界、错误码、匿名接口清单、审计事件清单和客户端类型枚举。
3. 定义私钥、公钥、手机号 HMAC 密钥、Mock SMS 开关及生产启动检查。
4. 保留外部 JWT 资源服务器的声明结构，明确本地账号 ID 与现有测试/迁移身份的映射策略。

**门禁：** 无未决的安全高风险决定；生产配置不能启用 Mock SMS；接口错误不能泄露账号存在性。

#### Step 1：认证共享底座和数据库迁移

1. 新增连续 Flyway 迁移，创建 `auth_account`、`auth_login_identity`、`auth_credential`、`auth_verification_challenge`、`auth_password_reset_ticket`、`auth_refresh_session`、`auth_security_event` 和 `auth_consent_record`。
2. 认证表登记为共享表，不添加伪造的 `tenant_id`；组织业务表继续使用现有租户隔离。
3. 为手机号摘要、提供商主体摘要、挑战状态/过期时间、会话族和撤销状态建立唯一约束和索引。
4. 实现手机号 E.164 规范化、带密钥摘要、密码慢哈希、验证码摘要、随机 Token 和时间注入接口。
5. 实现 `SmsGateway`、`IdentityProvider`、会话仓储和审计事件接口；Mock 实现仅由 `local/test` profile 装配。

**门禁：** Flyway 在独立 `_test` PostgreSQL 上通过；密码、验证码、手机号和 Token 明文不落库；并发唯一约束测试通过。

#### Step 2：手机号注册和 Mock SMS 纵向切片

1. 实现 `POST /auth/register/start` 和 `POST /auth/register/verify`。
2. 实现 `REGISTER` 挑战的过期、重发冷却、最大尝试次数、原子消费和统一匿名响应。
3. 验证成功后原子创建账号、手机号登录身份、密码凭据和安全事件，并允许建立首个会话。
4. 同手机号并发注册只允许一个账号绑定；重复注册不暴露已有账号。

**门禁：** 注册成功、验证码过期/重放/串用、并发注册、日志脱敏和 Mock profile 测试全部通过。

#### Step 3：登录、找回和账号安全状态

1. 实现 `LOGIN` 短信登录、密码备用登录和统一认证失败响应。
2. 实现密码找回三段流程：发起挑战、验证挑战、消费一次性重置凭证。
3. 实现失败计数、临时锁定、账号禁用、密码版本变化和安全事件记录。
4. 找回成功后撤销全部 Refresh Session；旧会话不能再次刷新。

**门禁：** 登录枚举、验证码暴力、密码哈希、找回重放、旧会话失效和账号锁定测试通过。

#### Step 4：本地 JWT 签发和会话轮换

1. 实现本地 RS256 JWT 签发，保留现有 Resource Server 的必需 Claims 和撤销失败关闭行为。
2. 实现 Refresh Token 哈希存储、轮换、会话族、重放检测、登出和过期清理。
3. 调整安全配置，仅放行认证和健康检查匿名接口；其余业务接口继续要求可信 Bearer JWT。
4. 明确本地发行方与外部发行方的兼容窗口；兼容关闭后，外部 JWT 不能继续获得本地账号权限。

**门禁：** Resource Server 验证本地令牌、过期、撤销、刷新并发、Token 重放、登出和兼容开关测试通过。

#### Step 5：组织上下文和现有业务接入

1. 将 JWT `sub` 映射为现有 `ExecutionContext.Identity.actorId`，不改由客户端传入身份。
2. 实现 `GET /auth/me`、`GET /auth/organizations` 和组织上下文选择接口。
3. 服务端检查账号 `ACTIVE`、组织 `APPROVED`、成员 `ACTIVE` 和具体权限后，才签发带 `tenant_id` 的组织上下文令牌。
4. 组织审核中、成员未激活、账号锁定或禁用时，只允许账号中心和必要的历史/申诉入口，不开放工作空间业务写操作。
5. 保留现有组织审核、成员审批和业务表隔离规则，补充账号禁用、成员撤销后的访问测试。

**门禁：** 一账号多组织、组织待审核、成员拒绝/撤销、跨组织读取和组织上下文越权测试通过。

#### Step 6：Web 认证入口和账号中心

1. 在门户增加 `/login`、`/register`、`/password-recovery` 和正式 `/account` 路由。
2. `session` 改为内存 Access Token + Refresh Cookie 的会话模型，401 只自动刷新一次，失败后回到登录页。
3. 移除用户路径中的 JWT 粘贴入口；开发联调控制台继续只在 `DEV` 构建注册。
4. 根据账号、组织和成员状态显示账号中心、审核进度或对应工作空间，不用前端隐藏替代后端授权。
5. 固定使用 `127.0.0.1:3000`，浏览器验证前先检查并复用本项目旧服务，不自动递增端口。

**门禁：** Web 注册、短信登录、密码找回、会话刷新、退出、组织状态和未授权跳转 Playwright 测试通过；生产构建不包含开发控制台。

#### Step 7：提供商身份扩展准备

1. 固化 `IdentityProvider` 接口和 `auth_login_identity` 的提供商唯一约束。
2. 设计微信小程序授权码交换、`openid/unionid` 服务端解析、显式绑定票据和绑定冲突错误契约。
3. 保留工人/经纪人低风险账号、手机号绑定和高风险操作升级路径的接口草案。
4. 本步骤不接入真实微信、不创建工人/经纪人业务关系、不实现小程序页面；这些必须等待对应业务包批准。

**门禁：** 提供商身份绑定状态机和安全测试完成；没有 `unionid` 时必须登录已有账号显式绑定，不能自动合并。

#### Step 8：完整验证、迁移和交付

1. 在 Podman 独立 PostgreSQL 测试环境执行 Flyway、单元、MockMvc、并发和跨组织集成测试。
2. 执行 Web Playwright 流程测试和生产构建检查。
3. 检查安全日志、配置、密钥来源、Mock SMS 装配、CORS、Cookie、CSRF 和 API 错误响应。
4. 形成迁移记录、已知限制、失败场景、回滚开关和上线前配置清单。
5. 只有所有门禁通过后，才允许将认证能力从本地/测试 profile 提升到目标环境；真实短信、微信和工人/经纪人业务仍需单独批准。

### 15.4 数据迁移、回滚与兼容策略

- Flyway 迁移只前进，不执行破坏性回滚脚本；异常时通过关闭认证入口、保留旧发行方兼容和修复后续迁移恢复。
- 新认证表初期为空，不把现有外部 JWT 的 `sub` 直接当作已注册账号；需要映射时建立明确的外部身份关系和审计记录。
- 认证功能使用配置开关分阶段放量，关闭开关不能删除账号、挑战或会话数据。
- 禁用本地发行方后，已签发 Access Token 按短时效自然过期，Refresh Session 可统一撤销；数据库不可用时认证和令牌刷新失败关闭。
- 不删除组织审核、成员和业务事实；账号禁用、成员撤销和组织状态变化通过服务端门禁阻止新的业务动作，必要的历史查询和申诉仍按授权开放。
