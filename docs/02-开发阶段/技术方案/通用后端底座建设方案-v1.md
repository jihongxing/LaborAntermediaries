# 通用后端底座建设方案 v1

日期：2026-10-23。状态：流程及范围已获用户批准，先文档后代码；实现和验证结果在文末更新。

## 1. 目标与范围

将历史劳务中介 SaaS 的公共代码建设为劳务供应链平台可直接接入业务开发的模块化单体底座。不实现注册、组织成员、资质审核、需求、应标、履约、结算、支付或保理流程，不创建相应实体、数据表和生产演示接口。

底座负责执行机制，业务模块负责资格、权限授予、状态规则及计算规则。身份提供方负责成员关系验证和权限撤销；底座不能从请求头直接相信用户或租户，也不能把平台管理员等同于全租户访问者。

## 2. 建设原则与决策

- 保持 Java 17、Spring Boot、MyBatis Plus、PostgreSQL 的模块化单体，不引入微服务、Redis 或消息队列的强制依赖。
- 不为每个实现创建接口；只在授权策略、后台任务处理等确有调用方扩展需求的位置设置接入点。
- 安全默认拒绝；缺少身份、隔离范围、权限或必要配置时明确失败，不使用 `tenant_id=-1` 伪装成功。
- 生产代码不包含固定密码、加密密钥或测试身份入口。开发模式未配置认证公钥时也不接受令牌。
- 身份认证采用外部签发的 RSA JWT 验证，校验签名、发行者、受众、有效期和令牌标识；不提供签发、登录或组织切换产品流程。组织身份只能来自已经验证的令牌，令牌签发方必须先验证成员资格。
- 令牌撤销通过持久化撤销记录检查，令牌权限失效由身份提供方主动撤销关联令牌；本轮不声称已实现组织成员变更联动。
- 数据表分为显式注册的隔离表和共享表；未知 MyBatis 表拒绝访问。跨组织投递规则留给业务模块，不提供全局跳过隔离开关。
- 基础设施内部 JDBC 查询必须自行显式限制作用域，不能把 MyBatis 拦截器视作全数据库安全策略。
- 持久化任务采用至少一次执行，处理器必须幂等；不承诺外部副作用恰好一次执行。
- 技术审计为追加记录机制，不等同于防数据库管理员篡改的合规证据系统。
- 不建设万能审批、状态机、业务规则引擎或通用 CRUD 框架。

## 3. 逻辑模块与调用约定

| 模块 | 责任 | 调用方必须明确的事项 |
|---|---|---|
| common / web | 响应、HTTP 异常、参数校验、JSON、请求编号 | 文件、健康检查和协议接口不强制包装 Result |
| foundation.context | 不可变执行身份、作用域及确定性清理 | 身份来自可信认证链；任务显式恢复上下文 |
| foundation.security | JWT 校验、撤销检查、权限检查 | 不负责授予角色、验证组织成员或审批权限 |
| common.config / persistence | 迁移、隔离插件、分页与乐观锁 | 隔离表必须注册，原生 SQL 必须显式授权和限域 |
| foundation.crypto | AES-GCM、外部密钥、版本化密文 | 密钥配置是 Base64 编码的 AES 密钥，轮换保留旧版本 |
| foundation.audit | 最小化操作审计 | 不提交密码、令牌、完整证件或任意请求体 |
| foundation.reliability | 数据库唯一编号、幂等执行 | 幂等作用域含组织及操作者；重复键不同请求须冲突 |
| foundation.tasks | 持久化任务、租约、有限重试、状态查询 | 类型注册、任务体最小化、处理器幂等和超时控制 |
| foundation.storage | 私有文件、元数据、受控下载与流式读取 | 存储权限不替代业务对象权限，下载每次重新授权 |
| observability / test | 健康、指标、请求关联、集成验证 | 不将测试替身误认为生产通道 |

## 4. 分阶段执行与验收

### 阶段一：工程纠偏

- 修复 BCrypt 依赖及 TenantLineHandler 用法，核对 Boot 3 starter。
- 添加启动类、外部化配置、Flyway 技术表、PostgreSQL 本地依赖配置。
- 统一异常 HTTP 状态、请求编号、分页约束、序列化与输入限制。
- CI 使用 PostgreSQL，明确单元测试、集成测试与覆盖率执行。
- 验收：Java 17 编译、单元测试、打包成功；真实 PostgreSQL 环境可执行迁移和启动。

### 阶段二：安全与持久化

- 使用 Spring Security Bearer 认证；公开范围默认仅健康检查，其余接口需认证。
- 上下文在每次请求 finally 清理；用户/租户标识不接受客户端头覆盖。
- MyBatis 未注册表拒绝、隔离表缺少组织拒绝；配置分页上限和乐观锁。
- 去除固定 AES 密钥，禁用请求体/返回体日志；独立 JSON 工具失败不静默返回 null。
- 验收：匿名 401、无权 403、篡改令牌拒绝、无组织拒绝隔离查询、请求结束无残留、密文篡改无法解密。

### 阶段三：可靠执行

- 数据库序列提供跨实例唯一编号；旧进程内编号不再作为可靠分布式单号。
- 幂等请求在同一事务内执行数据库操作并保存结果；唯一键包含作用域，校验请求摘要。
- 后台任务存储执行身份、状态、重试次数及租约，通过行锁领取，崩溃后可恢复。
- 审计显式记录动作、资源、结果、身份和请求标识。
- 验收：重复执行返回相同结果、请求内容变化冲突、失败回滚、任务超限失败、租约恢复与执行身份清理。

### 阶段四：文件、接入与交付

- 私有目录保存随机标识文件；用户文件名不参与路径拼接，禁止路径穿越。
- 文件访问检查当前身份和组织，外加可扩展资源授权；默认不向未授权主体提供下载。
- 上传失败清理临时文件；下载流不暴露存储路径，附件响应使用安全文件名。
- 更新 README、运行配置、扩展示例和验证结果；示例模型仅位于测试代码。
- 验收：越权下载拒绝、路径穿越无效、体积限制生效、每次读取重新鉴权。

## 5. 测试与质量门禁

1. 原有工具类测试必须执行；安全升级允许移除不安全旧接口，但同步修改所有调用方和测试。
2. 新增单元测试覆盖上下文、HTTP 错误、JWT、加密、参数边界和失败路径。
3. PostgreSQL 集成测试验证 Flyway、实际 SQL、隔离、幂等并发、任务租约和文件元数据。
4. CI 集成测试连接真实 PostgreSQL，不使用 H2 替代其事务、序列和锁语义。
5. 无 PostgreSQL 的机器可以运行纯单元测试，但必须明确集成测试未运行，不伪报完整通过。
6. 检查格式和覆盖率报告；不通过跳过全量检查掩盖已有或新增问题。
7. 审查生产代码中不存在业务模型、认证绕过、固定密钥、请求敏感值日志。

## 6. 运行与生产限制

- PostgreSQL 是实际运行的必需依赖；Flyway 负责创建 `foundation_*` 技术表，不创建业务表。
- 生产环境必须提供数据库凭据、JWT 公钥/发行者/受众、加密活动版本和密钥、文件私有目录。
- 本地磁盘适配器仅适合单机或受控共享卷，不伪称支持多实例独立磁盘。对象存储适配器按实际部署需求再实现。
- 任务处理器不得无限阻塞；租约到期可能重复执行，外部操作必须自行提供幂等键和查询恢复。
- 数据库幂等只保证同库事务效果，不包裹远程调用来承诺原子性。
- 备份恢复演练、生产容量、安全审计、依赖漏洞评估及密钥托管属于上线门禁，不能仅凭本轮测试宣称生产就绪。

### 7.3 首轮自检：规范与方案分开判断

**Standards**

- 新增代码遵循构造注入、模块职责内聚及接口级验证；未新增业务模型、空壳适配器或通用工作流引擎。按主线程执行规范/方案两条检查轴，未擅自启动子代理。
- 原规范文档存在旧 `IdGenerator` / ECB / 参数日志等过时强制示例，已在 `CLAUDE.md`、`QUICK_REFERENCE.md` 和贡献指南增加当前底座依据及替代指引。
- 未关闭存量缺口：整个后端覆盖率仍未达到贡献指南 80% 的目标；当前保留报告，不伪造达标或通过排除类提高数字。

**Spec**

- 方案要求的非业务基础实现与新增场景验证已落地；任务只保证至少一次，数据库幂等不保证远程原子性，文件只实现本地私有适配器，身份成员关系及业务 ACL 未越界实现。
- 未关闭验收缺口：全量单元测试仍有 7 项存量失败，完整 CI 门禁不可通过。因此本轮交付为“基础设施实现与新增验证完成，整体质量门禁待消除存量阻塞”，不是“已可无条件进入业务开发/生产上线”。
- 已明确运行边界：没有任务续租/强制中断，文件硬崩溃可能遗留孤儿，失败事务审计随事务回滚，幂等记录无默认过期策略，生产补丁/漏洞评估及备份恢复未在本轮验证。

两轴汇总：规范轴 1 项存量覆盖率缺口；方案轴 1 项完整测试门禁阻塞。详细运行配置、兼容性调整与部署限制统一维护在 `backend/README.md`，不另立重复接入文档。

- 测试边界：既有工具类公开方法、响应与分页契约，以及现有基础设施公开接口；不通过私有方法反射或排除低覆盖类制造达标。

- 完整验证：无测试筛选、无跳过、无忽略失败地执行 `mvn -B -ntp -Pintegration clean verify`，必须包含真实 PostgreSQL 集成测试、Checkstyle、打包与覆盖率检查。
- 开发准入：上述质量门禁全部通过、接入契约可查、隔离与权限默认拒绝、非业务边界保持完整后，才确认可以开始业务模块开发。

### 8.3 当前准入结论与边界

**结论：通用底座质量门禁已通过，可以进入业务模块开发；不等于可直接生产上线。**

| 开发准入条件 | 本次判定 |
|---|---|
| 无筛选的全部单元与真实数据库集成测试通过 | 满足，134 项无跳过 |
| 全项目行覆盖至少 80%，并可自动阻断退化 | 满足，86.43%，Maven verify 强制检查 |
| 数据隔离、权限、安全输入和可靠执行有回归保障 | 满足，原有 18 项真实数据库集成测试持续通过 |
| 运行配置、扩展接口及限制有文档 | 满足，统一维护于 `backend/README.md` |
| 不引入具体业务模型与闭环 | 满足，仅修复通用断言并补齐测试 |

业务模块接入时仍必须提供：可信身份与组织成员关系、具体权限与资源 ACL、隔离表注册、任务实时授权及幂等、数据库迁移和越权回归测试。不得将底座通过误解为业务授权自动完成。

生产上线另行评估密钥托管、依赖安全与补丁、容量与超时、备份恢复、私有存储部署及运维权限；任务至少一次、无续租、文件崩溃孤儿、审计事务回滚等既有边界未改变。

自检两轴：规范轴——公共接口测试、最小实现变更、无忽略失败/排除类；方案轴——原测试阻塞与 80% 行覆盖缺口关闭，保持非业务范围。未执行提交或创建分支。
