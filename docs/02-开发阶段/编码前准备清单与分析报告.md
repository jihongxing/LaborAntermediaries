### 3.2 核心概念术语对齐

#### 数据库相关术语

| MySQL术语 | PostgreSQL术语 | 当前文档状态 | 建议 |
|-----------|---------------|------------|------|
| Master/Slave | Primary/Standby | ✅ 已对齐 | 保持 |
| AUTO_INCREMENT | SERIAL/BIGSERIAL | ✅ 已对齐 | 保持 |
| DECIMAL | NUMERIC | ✅ 已对齐 | 保持 |
| TIMESTAMP | TIMESTAMPTZ | ✅ 已对齐 | 保持 |
| InnoDB | - | ❌ 仍提及InnoDB | 删除 |
| CHARACTER SET utf8mb4 | ENCODING 'UTF8' | ❌ 部分未更新 | 更新 |
| ENGINE=InnoDB | - | ❌ 仍提及ENGINE | 删除 |

#### 索引相关术语

| MySQL术语 | PostgreSQL术语 | 说明 |
|-----------|---------------|------|
| INDEX | INDEX | 一致 |
| UNIQUE INDEX | UNIQUE INDEX | 一致 |
| FULLTEXT INDEX | GIN Index + tsvector | 不同，已说明 |
| - | BRIN Index | PostgreSQL特有，已说明 |

#### 复制相关术语

| MySQL术语 | PostgreSQL术语 | 说明 |
|-----------|---------------|------|
| 主从复制 | 流复制（Streaming Replication） | 已对齐 |
| 二进制日志 | WAL（Write-Ahead Log） | 已对齐 |
| Replication Slot | Replication Slot | 一致 |

- 员工：`employee`（不是`worker`、`staff`）
- 工资：`salary`（不是`wage`、`payment`）
- 返费：`rebate`（不是`commission`、`kickback`）
- 项目：`project`（不是`job`、`task`）

**建议**：
创建 `docs/02-开发阶段/API设计/terminology.md` 统一术语表。

### 3.4 前后端数据类型对齐

| 业务概念 | 数据库类型 | Java类型 | TypeScript类型 | 说明 |
|---------|-----------|---------|---------------|------|
| 主键 | BIGSERIAL | Long | number | ✅ 一致 |
| 金额 | NUMERIC(10,2) | BigDecimal | string | ⚠️ 前端用string避免精度问题 |
| 日期时间 | TIMESTAMPTZ | LocalDateTime | string (ISO 8601) | ✅ 一致 |
| 布尔 | BOOLEAN | Boolean | boolean | ✅ 一致 |
| 枚举 | VARCHAR(20) | Enum | string | ✅ 一致 |

**重要**：金额类型在前后端传输时必须用**字符串**格式：
```typescript
// ✅ 正确
interface SalaryRecord {
  grossSalary: string;  // "5500.00"
  netSalary: string;    // "5000.00"
}

// ❌ 错误
interface SalaryRecord {
  grossSalary: number;  // 会有精度问题
}
```

立即安排数据库架构师完成表结构设计和SQL脚本编写。

#### 风险2：API设计未定义

**描述**：
- 前后端接口契约未定义
- 错误码未统一
- 数据结构未对齐

**影响**：
- 前后端并行开发困难
- 联调时大量返工
- 预计延期：**3-5天**

**建议**：
组织前后端负责人进行API设计评审，输出接口清单。

#### 风险3：工程配置缺失

**描述**：
- 后端缺少pom.xml，无法启动项目
- 前端缺少package.json，无法启动项目
- Docker Compose缺失，本地环境无法搭建

**影响**：
- 开发人员无法搭建环境
- CI/CD无法运行
- 预计延期：**1-2天**

**建议**：
立即创建最小化可运行配置，验证环境可用。

### 5.2 质量风险（🟡 中风险）

#### 风险4：文档版本管理混乱

**描述**：
- 需求文档有v0.1、v0.2，但没有演进说明
- 不清楚哪个是当前正式版本

**影响**：
- 开发可能基于过时的需求
- 需求变更无法追溯

**建议**：
整理需求文档，明确当前正式版本，建立版本演进记录。

#### 风险5：术语不一致

**描述**：
- backend/README.md仍使用MySQL术语
- GOVERNANCE.md中有MySQL示例

**影响**：
- 开发人员混淆
- 文档可信度下降

**建议**：
全面检查文档，统一为PostgreSQL术语。

### 5.3 协作风险（🟢 低风险）

#### 风险6：IDE配置缺失

**描述**：
- 缺少.vscode/settings.json等配置
- 团队成员编辑器配置不一致

**影响**：
- 代码格式不一致
- 可能产生无意义的diff

**建议**：
在编码开始后统一配置，问题不大。

## 💡 七、行动建议

### 7.1 立即行动（本周内完成）

1. **召开技术启动会**（1小时）
   - 参与人：项目负责人、架构师、前后端负责人
   - 议题：确认编码前准备清单，分配任务

2. **数据库设计评审**（4小时）
   - 负责人：数据库架构师
   - 产出：表结构设计文档、SQL脚本

3. **API设计评审**（4小时）
   - 负责人：后端负责人 + 前端负责人
   - 产出：API接口清单、错误码定义

4. **工程配置创建**（4小时）
   - 负责人：后端负责人 + 前端负责人
   - 产出：pom.xml、package.json、docker-compose.yml

5. **文档语义对齐**（2小时）
   - 负责人：技术负责人
   - 产出：更新后的文档

### 7.2 编码阶段建议

1. **采用迭代开发**
   - 第一迭代：核心功能骨架（员工管理CRUD）
   - 第二迭代：复杂业务逻辑（工资计算、返费计算）
   - 第三迭代：扩展功能（报表、统计）

2. **前后端并行开发**
   - 前提：API接口清单已定义
   - 后端：先完成接口，Mock数据
   - 前端：使用Mock数据开发

3. **每日站会**
   - 时间：每天早上9:30，15分钟
   - 内容：昨天完成、今天计划、遇到的问题

4. **每周Code Review**
   - 时间：每周五下午，2小时
   - 内容：本周代码Review，提出改进建议

### 7.3 文档维护建议

1. **文档与代码同步更新**
   - 代码变更必须同步更新文档
   - 接口变更必须先更新API文档

2. **文档Review机制**
   - 重要文档必须经过Review
   - Review人：相关负责人

3. **定期文档审查**
   - 频率：每月一次
   - 内容：检查文档是否过时、遗漏、错误
