## 1. 结论摘要

市场调研及补充材料补齐了现有 PRD 的重要内容：

1. **产品战略**：从“劳务中介管理 SaaS”转向连接用工单位和合规劳务公司的交易平台；核心价值是组织真实交易，依靠标准化、可核验履约数据和运营自动化提高交易效率，而非平台亲自经营劳务交付。
2. **收费方与计量原则**：平台管理费/服务费由履约方承担、用工方原则上不付平台费。费率及计费定义以[《商业模式与收费标准》](../03-账单与资金/商业模式与收费标准-v0.1.md)为唯一依据，不在本战略稿重复维护；不默认从用工方回款中扣收。
3. **平台责任边界**：平台掌握交易、履约核验、计费、对账和结算状态，但数据或账本状态不等于真实资金；平台不默认是用工方、派遣单位、工资义务人、垫资方或资金池。
4. **履约操作模型**：在中标和项目创建后增加“履约方案与供给计划”，将总需求分配至劳务公司自身、个人经纪人/招聘渠道和其他合规劳务公司协同来源，再通过候选、入职、到岗、考勤、有效人天、账单和评价追踪真实交付。
5. **买方采用动因**：调研观察显示，用工方采用劳务派遣/外包的动因除用工主体与责任边界安排外，还可能包括由劳务服务方承担工资支付形成的结算账期，以及供应商为履约向用工方提供保证金。该观察用于验证买方价值主张，不表示平台或任一供应商已承诺垫资、保证或担保。
6. **买方决策链与平台变现假设**：用工方需求发布人（常见为人事经理）与供应商选择/采购决策人可能不是同一人；前者负责需求入口与信息，后者影响选标和持续使用。应分别设计获客触达和决策价值，不把联系方式视为个人营销授权。以人事经理个人为收款方的销售佣金、以及从工人人天平台服务费中向决策人个人分成，均仅是调研提出的商业假设，不得作为默认产品功能或付款规则；须先核实组织授权、利益冲突、披露、合同、税务及适用合规要求。未经书面合规确认，不向客户员工个人支付与其采购决策挂钩的利益。

### 2.1.1 买方价值假设与双角色运营

- 用工方价值主张应围绕真实业务结果表达：责任主体与管理边界清晰；依合同安排由劳务服务方承担工人工资发放及相应资金安排，可能为用工方形成账期；供应商可提供约定的履约保证金。账期长短、工资责任、付款义务及保证金均以交易合同和实际资金安排为准，平台不作普遍性承诺。
- 用工方需求联系人（如人事经理）是需求采集、发布和平台获客触点；用工方决策人是供应商选择、预算/采购批准或续用的关键角色。系统应支持分别记录组织角色、授权范围、联系许可、线索来源和决策流程，不因某一联系人提交需求就推定其有权代表组织作全部商务决定。
- 供应商选标须基于公开、可解释且版本化的需求条件和应标承诺。销售佣金或推荐奖励只能作为独立商业方案评估，不得影响供应商排序、中标结果或平台审核。
- 平台人天管理费/服务费由履约方承担，是履约方为使用平台履约管理与监督服务支付的平台费用；用工方原则上不付平台费。该费用不自动等同于可向用工方员工个人分配的佣金。任何推荐费、渠道费或合作费用应由适格主体依据真实服务、授权和书面合同收付，并完成利益冲突披露；不得以“分成”名义向采购决策人员个人输送利益。

### 2.1.2 履约保证金与工资账期边界

- 用工需求可按项目风险启用供应商应标保证金/履约保证金；用工方发布时应明确金额或计算方式、缴纳主体、收款账户主体、缴纳截止时间、有效期、退还条件、可扣/没收的具体触发条件、争议处理和凭证要求。应标前向供应商完整展示并确认。
- 应标信息需记录保证金承诺金额、实际缴纳金额、缴纳状态、收款方及账户信息快照、凭证、退款/扣划记录。未缴纳属于资格门槛还是中标后履约条件，必须由需求明确，不允许平台隐式推定。
- 平台可记录和核验状态，但在没有明确合同、资金通道、授权和必要合规审查前，不代收、保管、划转、担保或承诺保证金到账；需求公开的收款账户须经过授权核验并采取最小披露和变更审计。
- 工资支付责任、工资实际付款方、劳务公司资金垫付与用工方账期是不同事实。系统分别记录合同约定、账期起算事件、工资付款凭证/状态和供应商结算状态，不以“由劳务公司发薪”推定工资责任转移或平台垫资。

### 2.1.3 商业模式文档引用

收费方基线、收费项目、价格、计费依据和收益分配审批事项统一维护于[《商业模式与收费标准》](../03-账单与资金/商业模式与收费标准-v0.1.md)。本文件只维护战略与履约原则，不复制其中的商业规则。

## 2. 已确认方向及建议采纳的产品原则

### 2.1 战略定位与价值

- **客户定位的演进与调研缺口（2026-10-21）**：项目最初定位为劳务中介 SaaS，目标客户是劳务中介和经纪人；转向劳务供应链交易平台后，核心需求发起方和买方转为用工方。此前调研未识别用工方是关键目标客户，说明原有客户发现存在盲区。后续市场验证应直接覆盖用工方需求发布经办人、人事经理及采购/用工决策角色，并分别验证需求真实性、采用动因、采购决策链和付费意愿；不能将过去对劳务中介/经纪人的访谈直接外推为用工方验证。
- 平台服务劳动密集型企业的用工供需交易，连接用工单位、合规劳务公司及供给渠道。
- 标准化需求、供应商选择、履约核验、工时工价记录、计费及对账形成交易基础设施。
- 这不是对劳务公司管理 SaaS 的更名：SaaS 的核心是向单家劳务公司提供内部管理工具；本平台的核心是组织用工单位与多家合规劳务公司的交易，并为交易履约和结算提供共同规则与基础设施。
- 招聘、人员档案、考勤、工资核算、返费和项目管理等能力继续服务于交易发生、履约成功、数据可信、费用结算及单位服务成本改善，不再作为脱离交易主线的独立产品方向。
- 长期规模效应来自真实需求、合格供应商网络、实际履约数据、标准化与自动化的共同作用。更多交易有机会改善匹配效率并降低单位服务成本；真实订单、履约质量、复购和成本数据是飞轮成立的验证依据，注册量或功能数量不是。
- 每个新增模块均应说明其如何帮助交易发生、提高履约成功率、提升数据可信度、降低单位服务成本或支持可持续收费；不能仅因其是传统劳务 SaaS 的常见功能而优先建设。
- 主要价值面向劳务供应侧：降低订单获取、项目协作和履约对账成本；平台不以功能数量或注册数证明价值。
- 双边增长观察真实需求、应标意愿、真实成交和有效履约人天、复购、履约质量及单位服务成本；注册量只作为运营参考。
- 履约方承担平台管理费、用工方原则上不承担平台费；价格和计量依据统一见[《商业模式与收费标准》](../03-账单与资金/商业模式与收费标准-v0.1.md)。

### 2.2 平台与各方责任

平台承担产品层面的交易组织、信息和规则结构化、供应商资格及需求资料审核、数据核验、进度与异常记录、计费计算、账单对账、服务费记录及评价依据管理。

用工单位定义需求、选择供应商，并依据约定确认相应履约事实。劳务公司依实际合同安排组织供给并承担相应人员与履约责任。个人经纪人及渠道帮助劳务公司获得人员供给，不因此自动成为供应商或用工责任主体。工人的法律关系和报酬权利依真实安排与适用规则确定。

平台**不默认**：

- 与劳务公司争夺同一订单的实际劳务交付利润；
- 成为实际用工方、劳务派遣单位或工人工资义务人；
- 承担工资垫资或企业客户账期融资；
- 接管全部招聘、日常现场管理和交付工作；
- 吸收、沉淀、划转客户资金，或以内部账本状态冒充真实到账。

以上为产品责任设计边界，不凭产品名称、协议文案或开关状态取代对实际合同、运营、资金路径及合规要求的核验。

## 3. 对既有 PRD 的变更清单

| 既有表述/假设 | 补充材料带来的变化 | PRD 处理 |
|---|---|---|
| 历史口径：平台管理费由劳务公司承担且仅从用工方回款分账扣收 | 已确认履约方承担平台管理费/服务费、用工方原则上不付；不默认从用工方回款分账扣收 | 收费方基线已确认；价格及商业细则以唯一商业模式审批文档为准 |
| 资金流转必然涵盖平台账户、工资备款代发和回款分账 | 平台不默认承担工资融资或资金托管；掌握计费、对账信息优先 | 将账户、指令、代发、分账视作依商业合同及合规账户方案确认的可选通道集成，账本与真实资金分层 |
| 工资、工资支付是平台自身必须履行的交易义务 | 劳务公司/相应合同主体承担义务，平台可计算、核验、对账，是否提供支付接口另行约定 | PRD 用“提供管理和通道集成能力”表达，不把平台记账作为付款或清偿 |
| 中标后直接招聘 | 先制定履约和供给计划，明确来源、责任、目标、时间，再实际招募 | 在核心流程和项目数据中新增阶段及独立状态 |
| 供给只有中标劳务公司和个人经纪人 | 补充自有供给、个人经纪人/招聘渠道、其他劳务公司协同供给三类 | 三类来源均入数据模型；实际参与边界和责任分别建模 |
| “计划人数”“招聘人数”“到岗人数”容易混用 | 明确候选、录用、到岗、在岗、有效履约/计费的阶段不同 | 供给计划、人员状态、履约和有效计费人天分别保存，不能互相替代 |
| 考勤仅由工厂考勤导入或人工登记形成 | 增加平台排班与工人小程序上/下班打卡，平台自建原始事件、工时计算、补正/复核和确认记录 | 外部考勤保留为独立比对来源；原始打卡不可覆盖；工时确认后按各自规则分别进入计薪、供应商结算和平台有效计费人天 |
| 多端只有技术形态，没有产品职责边界 | 明确 Web 管理/批量工作台、独立 App 现场履约、工人/经纪人小程序个人自助/供给协作 | 三端共用服务端权限与业务数据；不能由外部系统替代工人打卡，端侧交互进入后续原型 |
| 中标配额到岗即形成交付 | 超配必须审批；不足必须显示风险；补员不得覆盖未履约事实 | 配额门禁、补员任务与原始差异保留 |
| 公司间供给协同等同于多家中标 | 区分用工单位直接选多家供应商，与主供应商承接下再协同供给 | 直接多中标沿既有规则；主供应商分包/协同必须先确认合同关系、用工与工资责任、审批和资质，不由平台记录自动授权 |
| 服务商履约评价可作为信用 | 评价应有实际数据支撑、可解释及申诉；自动推荐属建议 | 先记录可核验指标与异议，不把一次异常自动转成永久限制或未验证信用分 |
| “第一版可分阶段开放” | 与负责人已确认完整平台、履约及资金不做范围拆分可能冲突 | 只把它保留为材料作者的实施建议；本 PRD 不据此移除任何既有完整范围。可以先排序开发任务，但最终平台能力和端范围不因此取消 |

## 4. 劳务公司履约生命周期

在既有中标确认之后，按九个阶段跟踪责任、状态、数据和交接条件：

| 阶段 | 核心活动 | 阶段交接依据 |
|---|---|---|
| 1. 中标确认与项目建立 | 发送中标通知、接受/拒绝、建立项目及负责人 | 接受的中标版本、配额、岗位、责任人、合同与实际用工/报酬安排 |
| 2. 履约方案与供给计划 | 将总配额拆成来源、批次、节点和责任人 | 每个供给计划有来源、目标量、时间、负责人及确认状态 |
| 3. 人员供给和缺口补足 | 自有储备、经纪人/招聘渠道、合规协同供应商；监测缺口 | 去重后的可追溯人员及相应供给责任/授权 |
| 4. 候选筛选与入职准备 | 联系、筛选、录用、必要资格/资料/合同/保险/培训 | 入职前置材料和岗位资格完成 |
| 5. 到岗与正式履约 | 实际到岗确认并关联项目、岗位、来源、供给责任方 | 人员身份、时间、岗位、责任主体和实际安排明确 |
| 6. 日常考勤、异常与补员 | 平台排班；工人小程序上下班打卡；工时计算、异常补正/复核；外部考勤差异比对；缺勤、替补和缺口恢复 | 排班、平台原始打卡、其他来源分别留痕；工时依据可复算，补录/更正不覆盖原始记录 |
| 7. 工价核算与有效计费人天 | 工人报酬核对、供应商费用核算、平台计费分别处理 | 原始出勤、规则版本、有效性、确认和争议明细 |
| 8. 对账、收费与结算确认 | 工人报酬、用工方业务账、平台服务费分账单 | 适用合同/主体、计量、费率、争议与确认状态 |
| 9. 项目结束与履约评价 | 人员退出、未清事项跟踪、完成/终止原因及评价 | 人员、履约、账单与争议分别有终态，不把未收款误标为已清偿 |

项目、供给计划、人员、工时/履约、计费和账单使用独立状态；不能只用单一“项目已完成”替代。计划、承诺、候选、录用、到岗、在岗和有效计费记录均为不同事实。

## 5. 供给计划和三类供给来源

### 5.1 供给计划必备字段

- 关联中标快照、标项、岗位和劳务公司配额；
- 供给来源类型及来源组织/渠道/经纪人；
- 计划人数、已确认供应能力、候选人数、录用人数、到岗人数、当前在岗人数和有效履约人数，彼此独立；
- 分批日期、批次目标、实际数及缺口；
- 对每一供给任务指定责任主体、负责人、合同或授权依据和状态；
- 缺口、迟延、取消、补足及其原因、责任方、证据与处理过程。

计划量和供应商自报能力不等于已识别人员；同一人不能因为出现在多个渠道或供应商名单中而重复计入可用供给。涉及敏感身份信息去重应按最小必要和授权边界执行，不得向其他组织泄露人员记录。

### 5.2 三类来源

| 来源 | 允许的产品动作 | 责任边界 |
|---|---|---|
| 劳务公司自身供给 | 关联候选人、筛选、录用、准备并登记实际到岗 | “自有来源”只说明获客/招聘渠道，不自动决定工人法律关系 |
| 个人经纪人或招聘渠道 | 劳务公司创建补员任务；在授权项目/岗位范围内接收任务或提交候选人；记录来源、时间和归属争议 | 不因推荐成为供应商或实际用工主体；佣金/返费依独立约定，与平台人天服务费分账 |
| 其他合规劳务公司协同供给 | 记录供应方、实际人员/岗位/批次、关系、授权、责任和独立/关联结算方式 | 合规资质及合同审批齐备后才能进入正式供给；一条平台记录不能替代必要许可、合同和用工安排 |

### 5.3 公司协同两种模式

1. **用工单位直接选多家供应商**：沿用竞标模块，分别形成中标关系、配额、责任、项目（或履约子项目）与账单；配额变化需相应参与方确认。
2. **中标劳务公司主承接，其他公司协同供给**：主承接公司承担哪些合同责任、协同方与谁签约、工人由谁组织/雇用/付酬、考勤确认、费用及违约责任，需在供给正式生效前明确；同时核验用工单位批准、项目合同限制及所需资质。缺项时只能保存为待确认计划，不能计入有效供给、到岗责任主体或平台收费依据。

不得把两个模式合并成模糊的“供给合作”，不得对相同人天重复计平台服务费。

## 6. 人员、履约和计费状态区分

建议提供可解释的人员流程状态：

`待联系 → 已联系 → 待筛选 → 筛选通过/未通过 → 待录用确认 → 待入职 → 已入职/未入职 → 实际履约中 → 已退出`

### 6.1 平台工时闭环与多端职责

工时数据链路为：项目人员在平台 Web 编制并发布排班 → 工人通过微信小程序对本人班次上班/下班打卡 → 平台保存不可覆盖的原始打卡事件并依据排班和规则计算工时 → 工人查看本人记录并可申请漏卡补正/异议 → 劳务公司授权项目人员通过独立 App 或 Web 核验异常 → 用工方按项目约定查看差异并确认相应履约/结算量 → 工资计薪量、供应商业务结算量及平台有效计费人天分别按各自规则形成。

Web 面向平台/组织管理、复杂配置和批量处理；独立 App 面向项目经理、驻场的现场任务和异常处理；工人小程序承担本人班次、上下班打卡、工时查看及补正申请；经纪人小程序仅承担授权岗位分享/人员提报和本人归属/返费查询。各端共享服务端规则和同一业务记录，页面交互在 PRD 配套原型中细化。

平台原始打卡、驻场补录、用工方/工厂考勤导入是不同数据来源。外部考勤只用于补充核验和差异对照，不可覆盖平台事件；漏卡补正、手工调整均须保留申请/处理人、理由、证据、前后值、时间和规则版本。单次上下班打卡不自动证明全部实际工作时间，也不自动等于确认工时、工资或平台计费人天。

根据岗位添加所需环节，但不虚设全岗位统一的面试、体检或技能测试要求。

必须分别记账的数量：

- 招聘/推荐人数；
- 去重后的候选人数；
- 录用人数；
- 实际入职人数；
- 在具体日期和班次实际到岗人数；
- 经双方确认的有效工作时间或服务量；
- 符合项目合同计费条件且经核验的有效计费人天。

有效计费规则须在履约开始前确定，至少说明适用项目/人员、日期、实际出勤条件、半日或异常计法、来源数据、确认方、调整方式、重复计费防护及争议处理。平台费基数不是“中标人数 × 项目天数”的静态推测。

同一人同项目同日是否形成一个或多个计费单位，应受明确业务规则约束；同一有效人天不得因自有供给、渠道来源、主供应商/协同方各自记录而重复计费。

## 7. 三套账与支付边界

### 7.1 三类账单必须区分

| 账单 | 依据与义务主体 | 平台能力定位 |
|---|---|---|
| 工人报酬或其他个人应付款 | 具体劳动/服务安排与实际责任主体 | 可记录规则、计算结果、核验与状态；是否提供支付通道取决于合同与合规方案，不默认成为债务人 |
| 用工单位—劳务公司业务对账 | 双方实际合同、经确认数量及中标条件 | 可计算、对账、争议记录；不因生成账单就成为债权人或债务人 |
| 平台管理费/服务费 | 用工方主导选择费率档位；按《商业模式与收费标准》已批准的费率及分账规则、履约方适用的平台服务合同执行 | 向履约方形成独立账单；用工方原则上不付平台费；供应商应标前知悉费率并纳入项目经济账，账单保留合同、规则版本、计费依据、税务口径、争议和收款状态 |

### 7.2 资金状态不可互相替代

- “已计算/已核验/已出账/已确认/待付款/处理中/已收款”是不同状态；账本记录、工人确认查看、用工方标记付款都不等于真实资金到账。
- 平台管理费/服务费由履约方承担，用工方原则上不付平台费；用工方主导选择商业模式文档定义的固定档位，供应商应标前知悉；计费事件、账期、收取通道由适用合同和获批规则细化，不默认只能从用工方回款中扣除。
- 资金若经第三方通道或专户处理，记录真实付款方、收款方、操作授权、机构流水及对账结果；平台不自行吸收、沉淀或转划客户资金。
- 工资支付义务依适用合同与法律关系确定，不因企业回款晚于工资日期就自动顺延；本原则不等于平台承诺替责任方垫付。
- 失败、未知、部分付款及争议金额单独表示；不能因部分到账标成结清。

## 8. 供应商履约评价和双边验证

评价候选指标必须可追溯至明确批次、版本和经确认事实：

- 各分批承诺量与实际到岗量差异；
- 首次到岗及时率；
- 人员留存、主动退出及补员效果；
- 缺口响应时长；
- 工时记录准确率和对账差异；
- 争议数量、原因、响应及解决状态；
- 完成/提前终止、未完成原因及双方责任。

展示原始事实、口径、归属项目和观察窗口；供应商可查看、说明、申诉。一次异常不自动形成永久封禁或公开失信标签；排序、信用分和自动推荐的具体规则仍需负责人批准。

双边飞轮及经营验证指标：

| 假设 | 建议观察指标 |
|---|---|
| 用工方持续发布真实订单 | 需求发布至审核通过率、需求撤回率、重复发布及复购 |
| 劳务公司认为竞标有价值 | 合格供应商应标率、重复参与率、选标成交率 |
| 撮合能转化为真实履约 | 中标至供给计划、到岗及有效计费人天转化 |
| 各方持续使用履约和对账 | 考勤确认率、异常解决时长、对账完成率、差异率 |
| 标准化和规模改善经济性 | 每有效计费人天服务成本、自动处理率、单位争议成本 |
| 服务费可持续 | 适用合同下服务费应收、实收率、坏账与单位贡献利润 |

有效计费人天与人时、自然日、人员累计到岗数为不同口径。若合同约定从工时折算人天，必须显式记录每日阈值、部分出勤、舍入及异常，不得静默用某个小时数默认折算。

注册数仅为漏斗指标，不单独视作飞轮已成立。

## 10. 仍需单独评审的冲突和决定

1. **履约方平台费合同**：收费方基线已确认为履约方、用工方原则上不付平台费；收费价格和收益分配审批统一记录在《商业模式与收费标准》，合同及落地流程按其审批结果细化。
2. **平台费计量/收取时点**：有效履约人天是计量基数，但费用在哪个事件形成债权、每期如何结算/收取仍需明确；不得把人天计量误推导为“等用工方回款才收费”。
3. **平台是否代发及机构账户模式**：补充战略不默认工资垫资、资金池；v0.3 仍有持牌第三方代发/子账户方案。需按实际合同、机构能力及平台应承担的角色决定是支付通道集成、仅账单对账或多模式兼容。
4. **劳务公司对外包人员供给的责任/权限**：自有、经纪渠道、协同供应商的履约责任及合同结构要落到业务动作；本平台不在表单上替代法律关系判断。
5. **评价数据的申诉与公开**：先确认仅供内部筛选、对供应商可见、用工方可见或用于排序的各自权限，再建立相应治理流程。
6. **经营假设参数**：有效人天定义、目标地区和劳务类型、费率、综合成本、坏账与目标利润必须用真实项目与运营数据验证；示例价和成本假设不成为默认配置。
7. **第一版实施顺序**：工程拆分可另行评审，但不得误写为“只交一笔交易/延期履约资金/缩减端”。负责人已确认的完整范围优先。
8. **考勤确认规则**：工时确认/争议时限、超时效力、补卡证据及复核权限仍待确认；不能据此回退到只依赖用工方外部考勤的模式。

以上不是要求阻塞后续产品需求整理；如具体规则尚未确认，应以配置显式待定、禁止静默使用默认值的方式进入设计。

### 一、战略方向与验证框架重要信息

- 战略定位：劳动密集型企业劳务供需交易基础设施，目标是让劳务公司以更低成本、更高效率完成合规交易。
- 平台负责交易、供应商准入、履约数据、有效人天、对账、收费及争议基础设施，不默认承接具体人员交付、工资债务或资金融资。
- 平台管理费/服务费由履约方承担、用工方原则上不付；商业模式与收费规则以《商业模式与收费标准》为唯一依据。
- 人天管理费固定档位、基准费率及超额分账规则以《商业模式与收费标准》为唯一依据；平台单位服务成本和实际贡献利润仍需结合经营数据验证。
- 飞轮由真实订单、合格供给、真实履约、较低单位成本和复购构成，注册量不是成功证明。

### 二、劳务公司履约流程重要信息

- 九阶段：中标确认和建项目；履约及供给计划；供给组织/补缺；筛选录用及入职准备；到岗；日常考勤异常；工价和有效人天；对账收费结算；项目结束和履约评价。
- 三类供给：劳务公司自身、个人经纪人/招聘渠道、其他合规劳务公司协同。
- 供给计划人数、确认能力、候选、录用、到岗、在岗和有效履约必须分别记录、去重。
- 公司协同有“用工单位直接选多家”及“中标公司作为主承接方再协同”两种结构；后者需明确批准、合同、供给及用工资格、人员、工资和违约责任。
- 有效计费人天是从确认出勤推导的平台服务费数据，须在项目开始前明确规则，防重复计算；与工人工资、供应商结算分账。
- 评价基于实际履约，规则可解释并有申诉，异常不应自动永久限制供应商。
- 原材料第一版范围及“可分阶段开放”属于材料作者建议；与本负责人既有完整范围决定不一致时，以负责人在当前对话确认的完整平台范围为准。
