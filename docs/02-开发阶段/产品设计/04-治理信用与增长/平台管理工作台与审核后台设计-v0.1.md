## 1. 设计目标与边界

平台管理后台服务于实际审核和治理岗位，是劳务供需平台的内部工作空间。它与公共门户、用工方组织空间、供应商组织空间使用同一 Web 应用和品牌体系，通过独立的 /platform/... 路由承载平台职能。

本设计优先解决目前已经形成的组织入驻和需求发布审核断层：平台人员有受控入口查看待办、核验申请、要求补正、提交审核意见，并让申请方查看结果。它不把平台后台做成数据库控制台或可任意查询所有组织的“超级管理员”。

**本稿的设计范围：**

- 平台账号权限及其与普通账号、组织成员身份的关系；
- 组织入驻与用工需求审核队列、详情页和申请方结果反馈流程；
- 材料清单、真实性来源核验、补正、版本和审计要求；
- 依据当前接口能力明确实现缺口，并提出首期审核纵向切片。

**批准的首期实施范围：**正式平台路由与工作台布局、受控的平台授权建立和服务端授权上下文、组织/需求审核及其异议复核队列与详情、按岗位自主认领/主动释放、审核/复核意见、申请方结果反馈，以及覆盖该切片所有业务操作的审计事件、“平台独立监察员”跨组织只读检索/事项历史页面和全模块审计覆盖页。除平台岗位管理页面、投诉案件办理和交易监督外，本切片须能让监察员查看组织/需求审核各版本与各处理人的完整历史。认领、释放、平台岗位授权上下文、异议复核、正式路由、完整操作审计及监察页面均为待建能力，不能视为已有实现。后续任何平台业务模块在对外启用前均须接入同一审计事件契约；不能因本次首期切片未包含该模块而免于留痕。

本稿列出的高影响措施双人审批、独立申诉复核等治理规则适用于相应类型的治理事项；它们不把组织/需求普通审核改成双人审批，也不把投诉、限制措施或案件办理带入本次首期范围。

**本版不展开：**投诉案件办理、交易全程监督、限制措施、收费/支付后台、全局规则发布、人员或工人管理。这些能力仍按各自专项评审范围、实现和启用条件；其治理原则遵循已批准的 D-17～D-19 基线，不因有了审核后台而默认批准。

| 申请材料 | 组织表单传递材料编号/引用；目前没有受控的材料上传、私有存储和审核预览流程 | 引用号只能帮助定位核验，不能等同于材料已提交或真实性已验证 |
| 操作审计 | foundation_audit 目前记录操作者、租户、操作/资源标识、结果和 HTTP 请求 ID；只覆盖显式调用审计记录器的操作，并参与业务事务，回滚时记录也会回滚；未形成按申请事项/版本串联的完整历史 | 当前底座审计不能满足“所有平台操作留痕”或独立监察查询要求；需补齐业务事项/版本关联、读写及拒绝事件、失败事务审计、历史视图和受控的跨组织审计查询 |

因此，测试验收不得仅以“账号登录成功”“令牌中有权限字样”或“菜单可见”为通过；必须先建立受控的平台授权来源、签发/续期/撤销机制，再验证无平台授权的账号不能读取队列和材料，且所有审核写操作仍由服务端许可校验。测试中直接构造的权限上下文只能验证门禁逻辑，不能证明真实账号授权流程已经完成。

## 3. 身份与岗位权限设计

### 3.1 身份模型

建议沿用已建成的个人账号，不另建平台员工账号表来重复保存手机号和登录凭证。平台权限作为独立的工作人员授权关系授予个人账号：

- 个人账号、平台岗位、组织成员关系是三种不同关系。
- 组织管理员、用工方成员或劳务供应商成员不会因此继承平台权限。
- 平台工作人员如同时属于某个业务组织，在组织空间中仍按该组织成员权限操作；平台工作台权限不意味着可以任意跨租户查询。
- 平台授权不开放自助申请。首个平台授权管理员的受控建立方式尚未确定；在该方式完成设计并实现前，不开放平台审核入口，不配置默认、硬编码或可公开触达的管理员账号。后续岗位授予/撤销须有受控流程并记录授权人、对象、权限范围、原因、时间和结果。
- 不设置可绕过职责分离、证据权限和审计的“超级管理员”。技术运维权限也不等于业务审核权。

高权限岗位的初始建立和授予流程、岗位兼任的具体配置须在 G0/G3 实施门禁中落实。平台授权管理员本身也不得绕过职责分离或以技术运维身份读取审核材料、代替审核或复核。风险措施的双人审批、原审核人与利益相关人回避、独立复核及无人可复核时保持待复核并升级，已由 D-17～D-19 决策基线确认；适用事项须与本次组织/需求审核切片区分。

### 3.2 岗位设计

以下岗位集合是本次已批准的平台审核后台设计基线。人员编制、具体账号授权和技术强制方式在对应实施门禁中落实。

| 岗位 | 主要职责 | 默认不可做 |
| --- | --- | --- |
| 平台授权管理员 | 授予、变更、撤销平台岗位权限；复核授权记录 | 默认不查看申请原始材料、不审核组织或需求、不改业务状态 |
| 组织审核员 | 从组织审核待办中认领任务，核验申请及适用资质，提出审核结论或补正 | 不审核本人或关联组织的申请；不越权开通其他业务能力；不认领其他岗位的任务 |
| 需求审核员 | 从需求审核待办中认领任务，核验需求真实性、字段完整性、授权关系和发布条件 | 不代替用工方修改商业条件、选标或决定供应商报价；不认领其他岗位的任务 |
| 独立复核员 | 从待复核事项中认领任务，对决定和必要材料进行独立复查 | 不复核本人首次处理过的任务；不扩大到无关组织资料；不认领其他岗位的任务 |
| 平台独立监察员（原审计观察员） | 独立、只读地监察平台已纳入审计的组织、事项、平台人员操作、系统操作和版本历史；检查审计覆盖缺口，形成监察发现并跟踪回应 | 不认领业务审核任务，不授予平台岗位，不编辑/删除业务或审计历史，不直接改变业务状态；高敏原件按用途受控访问；不得自批自身的敏感访问或导出 |

平台独立监察员是平台运营主体内部、组织职责上与被审业务处理线分离的监督岗位，不是“超级管理员”，也不因此成为法定监管机构。其工作汇报关系不得隶属于被审审核岗位；任命、续期、权限缩减和撤销须有两名不同的授权人确认，监察员不得自批自己的授权。监察员不得兼任组织/需求审核、独立复核、平台授权管理或业务执行岗位。系统强制方式、授权责任人和工作汇报落实方式在实施门禁中确定。未完成受控授权前不得开放监察权限。

其审计范围覆盖所有已接入审计契约的平台业务事项、人员操作和系统操作，不受组织成员关系或被审任务岗位过滤；该权限通过专用的平台审计查询服务显式授权，不得通过切换租户上下文、关闭租户隔离或直接查询无范围限制的业务表实现。监察员可以查看授权记录及自身操作产生的事件，但自身的权限授予、撤销、敏感信息展开和导出须由其他授权人审批，并由另一名有监察权限的人复核；监察员有利益冲突时必须回避，由其他监察员从岗位队列自主认领。监察员可新增监察发现和审计注记，但只能追加、不能覆盖原记录；任何发现均不得直接变更原审核结论、组织状态或交易状态。

本工作台不设审核分派员，也不由平台人员手工把任务指派给某位审核员。每类审核任务由具备对应岗位权限且不存在回避冲突的人员自行认领；同一岗位有多名审核员时，认领竞争由服务端原子裁定。认领是任务处理权的占用，不等于审核结论或业务批准。平台独立监察员不参加业务任务认领；其监察发现记录在独立监察事项中，后续回应与复核仍按岗位队列自主认领。

一项任务在同一对象版本上只能有一个有效认领人。认领请求具备幂等性：同一认领人重复提交可返回其已有有效认领，不重复创建占用或重复变更任务；不同人员并发时仅一人成功，其他人收到任务已被认领的结果，不获得该任务的材料访问权。组织审核、需求审核和独立复核分别按岗位权限认领，不能跨岗位争抢。

认领成功后，任务保持由认领人处理直至提交审核结果或复核意见。认领人可说明原因后主动释放，任务回到原岗位队列。账号禁用、岗位撤销、系统故障或长期未处理时，具备独立任务恢复权限的人员可解除占用并退回队列；该权限不包含材料读取、审核结论或指定接手人。`platform:tasks:reopen` 是本设计确定的权限标识，尚未实现为权限或接口。首期不自动按时间到期释放；长期未处理的内部升级阈值根据试点数据配置，例外恢复行为留痕且不重置总历时。任务恢复权限配置在对应实施门禁中落实。

申请人、投诉人、被投诉人、其关联组织人员、已参与任务处理者和其他存在直接利益关系者须回避。回避后立即撤销该任务的详情、材料和写入权限。普通组织/需求审核由一名审核员处理；高影响措施按已批准基线由提议人与批准人分离并双人审批，申诉由未参与原处理且无利益冲突的独立复核员处理。无人可复核时保持待复核并升级，不自动通过或生效。高影响措施流程不属于本次审核切片。

认领的幂等范围建议绑定“认领人账号 + 任务类型 + 对象及版本 + 幂等键”。幂等重试只返回原认领结果，不重复生成认领记录。申请方提交新版本后，旧版本任务及其认领失效并保留历史；新版本作为新任务重新进入相应岗位待认领队列。

| 批量导出 | 否 | 否 | 否 | 否 | 默认否；经独立审批后按事项、字段和用途导出并记录审批与下载事件 |

监察员的跨组织读取是显式的平台审计授权，不豁免服务端资源授权或组织隔离，也不等于任意业务人员可以跨组织查询。监察查询、详情读取、敏感字段展开、材料预览、监察注记和导出均记录操作者、审计目的、对象范围、结果和时间；监察员自己的活动同样可由其他监察员复核。表中“本人有效认领任务”由后端接口、材料访问服务及审计共同实施；隐藏菜单或前端过滤不构成访问控制。认领状态和权限必须在读取详情、查看材料及提交结论时重新校验。具体权限码、字段清单、敏感访问审批者和角色兼任矩阵需在实施评审阶段形成可测试合同。

## 4. 页面信息架构与路由

### 4.1 视觉与布局

沿用当前站点品牌、字体、颜色、表单和反馈组件（如现有青绿色 #176b68、浅色中性背景），但平台工作台采用适合连续审核的操作布局：

- 顶部显示平台名称、当前工作人员、当前岗位/权限提示、账号菜单和退出入口。
- 左侧导航按待办任务组织：工作总览、组织审核、需求审核及异议复核；平台独立监察员使用单独的只读审计入口查看跨组织事项历史和操作事件。授权管理页面仍不纳入首期，不呈现未实现入口。
- 主区区分“待认领”“我已认领”“已处理”等状态，显示版本号、认领状态、最后更新时间和下一步动作；已认领任务显示当前认领人，不产生手工分派或改派能力。
- 详情页采用“申请事实与版本 / 材料与核验 / 处理历史 / 审核操作”分区，审核结论在提交前展示影响说明。
- 不出现 API 调试、令牌粘贴、数据库表、虚构统计或演示数据。没有真实数据时显示空队列，不以预置假任务营造已运行状态。

### 4.2 路由建议

以下正式路由设计已通过评审，当前并未全部注册：

| 路由 | 用途 | 最低权限 |
| --- | --- | --- |
| /platform | 平台待办概览，仅聚合当前账号可访问的队列 | 任一平台岗位 |
| /platform/reviews/organizations | 组织申请审核队列 | platform:organizations:review |
| /platform/reviews/organizations/:organizationId/versions/:applicationVersion | 某组织指定申请版本的审核详情 | 本人有效认领及相应字段权限 |
| /platform/reviews/demands | 需求审核队列 | platform:demands:review |
| /platform/reviews/demands/:demandId/versions/:revision | 某需求指定版本的审核详情 | 本人有效认领及相应字段权限 |
| /platform/reviews/appeals | 组织/需求审核异议复核队列 | 独立复核权限；权限标识为 platform:appeals:review，尚未实现 |
| /platform/reviews/appeals/:appealId | 某项异议复核详情及原决定关联 | 本人有效认领、独立复核权限及相应字段权限 |

| /platform/audit/requests/:reviewCaseId | 查看一项组织/需求审核事项的连续处理历史与关联版本 | 平台独立监察权限；只读；所有历史和访问动作留痕 |
| /platform/audit/coverage | 查看各平台模块的审计事件目录、接入状态、记录延迟和已知覆盖缺口 | 平台独立监察权限；只读；不允许通过界面将未接入模块标记为已覆盖 |
| /platform/audit/findings | 监察发现及回应跟踪队列 | 平台独立监察权限；首期范围；不直接改变业务状态或指定接手人 |

未登录访问平台路由时转到登录页，并保留原目标路由；已登录但无对应平台授权时显示明确的无权页面和账号状态，不将其误导到组织空间，也不加载任何平台数据。直接请求 API 同样返回拒绝结果并记录必要安全事件。

### 4.3 队列页

组织、需求和异议复核队列按岗位分开，支持状态、提交时间、认领状态和版本等筛选。审核人员可以查看本岗位可认领的待办和自己已认领的任务；其他审核员的任务仅显示已认领状态，不显示申请材料或无关个人信息，也不提供认领入口或详情访问。首期不承诺固定办理时限；可展示已等待时长和“待申请人补正 / 待外部核验 / 待审核员处理”等事实状态，但不可用未批准的 SLA 文案催办或惩罚审核人员。

队列列表只展示识别和认领任务所需的最小摘要。原始证照、个人身份证明、完整联系方式、报价及其他无关商业资料不出现在列表。多个审核员同时认领时由服务端原子裁定；获胜者取得该版本任务的唯一有效认领，其他请求收到已被认领的状态，页面刷新后显示最新认领状态。

### 4.4 详情与审核操作

详情页顶部固定展示对象编号、当前申请/需求版本、提交人或组织的最小必要摘要、业务状态、当前认领人（仅已认领时）、任务状态和版本更新时间。未认领任务不显示负责人或指定接手人。内容按对象类型呈现：

- **组织申请：**主体类型与登记标识、申请业务角色、经办人授权关系、该角色适用的资质项、主体/角色状态及材料差异。按用工方和劳务公司规则显示不同清单，不要求所有主体提交同一套证照。
- **需求申请：**用工主体/授权关系、岗位与服务范围、地点、人数、报酬或计价模式、履约及确认条件、需求版本差异和已完成的组织准入状态。审核页不展示未授权的供应商应标、报价或其他组织私密信息。
- **核验操作：**对每项要求分别选择核验状态、填写核验依据和记录来源；遇到渠道不可用可保留“待核验”，不能假定通过或直接认定申请人造假。
- **审核操作：**按后端当前允许的领域状态提供通过、要求补正或不通过等操作；每次提交必须有结构化理由与申请人可理解的说明。不能从平台页面直接改数据库或跳过原领域接口。
- **版本冲突：**若申请人已提交新版本，旧详情只读并提示“此版本已被新版本替代”；旧任务不能提交结论或解锁新版本。
- **处理历史：**认领成功后可查看该审核事项的完整版本链和处理时间线，包括此前经手岗位/人员、认领与释放、核验事实及来源、补正理由、内部处理记录、审核结论、通知结果、未解决问题和当前版本差异。历史记录帮助下一位处理人理解前因并决定后续操作，但不自动替代其独立判断；申请人只看到已批准披露的状态与对外说明，不看到内部监察意见或无关人员/组织信息。

## 5. 页面流程

| 步骤 | 工作台行为 | 规则与反馈 |
| --- | --- | --- |
| 1. 登录与授权 | 工作人员登录，进入目标 /platform 路由 | 无平台授权时显示无权说明，不加载队列数据 |
| 2. 查看待办 | 进入组织、需求或异议复核队列，按岗位权限查看摘要、状态和认领状态 | 组织审核、需求审核和独立复核权限独立；列表不展示无关敏感材料，不展示未认领任务的“负责人” |
| 3. 自主认领 | 审核员从本岗位待办中认领任务 | 无分派员或手工指派；服务端原子且幂等地确保每个对象版本只有一个有效认领人 |
| 4. 打开对象版本 | 认领成功后查看审核所需字段、材料列表、历史版本与已有处理记录 | 服务端检查认领人、岗位、对象版本、字段和利益冲突关系 |
| 5. 核验材料 | 逐项记录材料完整性、真实性来源、有效性及结论 | 渠道故障进入待核验，不等同于通过或造假 |
| 6. 补正或处理 | 说明缺项、冲突、依据与需要的补充；或提交审核意见 | 申请方只看到可披露的补正原因；提交时再次检查版本 |
| 7. 形成结论 | 提交通过、补正或不通过等当前领域允许的结果 | 记录理由及审计；组织/需求普通审核按单人处理。双人审批仅适用于基线所指的高影响措施，该类措施不属于本次审核切片；申诉由未参与原处理且无冲突的人员独立复核 |
| 8. 门禁回执 | 后端更新领域状态并反馈申请方 | 决定、业务门禁执行和通知分别记录；失败不能显示已完成 |
| 9. 新版本处理 | 申请方补正并提交新版本，形成新审核任务 | 旧材料与决定保留；旧任务不能解锁新版本 |

### 5.1 申请方看到的闭环

申请方从账号中心/组织空间查看当前状态、被审核版本、逐项补正原因、所需材料说明和下一步操作。平台方的内部备注、工作人员个人信息和其他组织资料不对申请方显示。

补交资料应产生新申请版本；页面要保留旧版本与补交差异，避免覆盖原审查依据。审核通过只说明指定组织角色或需求版本通过平台当前审核，不是政府背书、能力担保或自动授予该组织所有成员权限。需求通过后是否需要用工方进一步发布，沿用既有需求流程。

对组织准入或需求审核结论提出异议时，申请方可进入独立复核流程，关联原申请和审核版本；原审核人及存在利益冲突者不得认领该复核。复核意见、业务执行和通知分别留痕。适用事项的法定答复/申诉期限须由专业法律评审确认；内部处理目标与对外服务承诺须由运营另行评审。未确认前不在页面中预设具体天数或承诺服务时限，也不承诺平台结论属于司法或行政终局裁决。

### 5.2 平台独立监察流程

1. 监察员以独立平台岗位进入审计工作台，查询范围覆盖平台已接入审计契约的组织/需求审核事项，不以其组织成员身份或审核队列认领状态过滤结果。
2. 监察员从组织概览进入具体审核事项，先核对版本链、经手岗位和人员、处理结论、证据来源引用、访问记录及待处理问题；查看原件或展开敏感字段时填写具体监察目的并触发相应审批/审计。
3. 如发现处理缺口或权限/流程异常，监察员创建只追加的监察发现，关联到具体事项、版本和事件，并选择需要回应的问题；系统向相关岗位的回应队列发出事项，不指名派给个人。
4. 被监察岗位提交回应和佐证后，未参与原处理且无冲突的监察员自主认领复核；未确认问题是否成立前不得将发现显示为违规结论。
5. 监察发现关闭只表示监察跟进完成。需要更正审核决定、变更组织/需求状态或采取高影响措施时，另走对应领域及已批准的职责分离流程。

## 6. 材料提交与真实性核验

### 6.1 先区分“有材料”和“核验通过”

每个材料项分别记录下列事实，不把它们压成一个“已审核”勾选框：

1. **提交状态：**未提交、已提交、已替换；
2. **完整性：**缺失、格式可读、字段齐备、需补正；
3. **来源核验：**未核验、核验中/待核验、与可查来源匹配、不匹配、无法核实；
4. **有效性：**当前有效、已到期、已撤销/失效、状态待确认；
5. **审核使用结果：**支持本项结论、不足以支持、与申请内容有冲突。

外部查询不可用或信息不公开时记录“无法核实/待补证”及具体原因。只有证据足以支持的事实才能写成已核验；渠道失败不能写成申请人造假。

### 6.2 角色适用的材料清单

材料清单由申请主体类型、申请角色和实际业务能力决定：

- 共同核验主体合法设立信息、申请人与组织的关系、经办人身份/授权及联系方式；
- 用工方核验实际用工主体与经办授权；不因是普通用工方而统一索要人力资源服务或劳务派遣许可证；
- 劳务公司按已确认的合规外包范围核验实际服务内容、适用备案和其他确实相关的资格；营业执照名称、外包备案或其他单个证件都不自动证明全部业务能力；
- 分支机构、事业单位、个体工商户等使用与主体类型匹配的证明和授权关系；
- 只要求与当前申请及准入判断直接相关的材料，不默认收集银行账户、完整员工名册、税务明细、人脸视频或全量身份证件。

执行标准以[入驻与资质审核需求细化第 4～8 节](../01-身份与需求交易/入驻与资质审核需求细化-v0.1.md)为准；该文件未批准的建议不得被后台字段强制执行。

### 6.3 建议核验方法

| 核验对象 | 建议方法 | 结果证据 |
| --- | --- | --- |
| 登记主体、名称/统一社会信用代码、主体状态 | 通过适用的政府登记公示来源、可验证电子证照或经授权的人工渠道交叉核对 | 来源/渠道名称、查询时间、检索标识、匹配字段、状态和记录人；保存必要结果，不抓取无关资料 |
| 经办人身份及组织授权 | 检查授权对象、代表人/经办人关系、授权事项和期限；必要时使用适用的身份核验方式 | 核验方式、材料版本、授权范围/有效期、核验结论和需要说明的差异 |
| 外包备案、许可或其他资格 | 先判断实际申请业务需要何种资格，再通过发证/备案机关公开信息、可验证电子证照或人工核实 | 证照主体、类别、适用范围、有效状态、来源与时间；不将无法联网误记为已联网验证 |
| 需求事实及用工授权 | 对照组织已核验信息、需求申报字段和授权材料；有疑点时要求申请方补充说明或凭证 | 逐项记录核验事实、来源、冲突点和补正要求，不代替用工方作采购/选标决定 |

外部核验接口尚未接通时，界面须显示人工核验及其真实来源，不得使用“联网认证”“官方认证”等误导文案。规则和材料标准更新后，旧申请继续绑定提交时的规则/清单版本，除非经过正式流程重新要求补充。

### 6.4 附件与敏感信息保护建议

当前系统没有安全附件预览能力。建议正式开放审核之前增加私有材料存储和任务授权预览：

- 附件存放在私有存储；业务数据只保存不可公开访问的文件引用及元数据。浏览器不能得到永久公开 URL。
- 上传后校验允许的文件类型、大小和内容格式，进行恶意文件扫描；未完成安全检查的文件不向审核员开放。
- 预览或下载前，服务端验证账号状态、平台岗位、当前任务、对象/版本、字段敏感级别和授权有效期；使用短时受限访问凭证。默认采用在线预览，导出/下载须另有权限和理由。
- 证件号、手机号、个人住址等字段默认掩码。确需展开时按字段授权，并记录查看者、对象、材料版本、时间、用途和结果。列表、普通通知、应用日志和审计摘要不得记录文件内容或完整敏感字段。
- 保存材料原版本、哈希/校验值、提交者、时间、替换关系、核验记录和访问审计。补交不覆盖旧材料；纠正或撤销应形成新记录。
- 各类材料的留存/删除期限、法律保全方式及处理依据，须按资料类别经专业法律、隐私和安全评审，并与 D-12、D-16、D-19 一并确认；本稿不设具体天数，也不把留存期限当作可自行填写的产品参数。下载能力、数据驻留和恢复策略另按技术/安全评审确定。

如果首期无法提供上述安全能力，对外上线前应限制材料类型和平台审核范围，并把不具备安全核验条件的事项保留为待补证/待核验；不应将公开网盘链接或未受控的本地文件夹作为替代。

## 7. 操作留痕、审核事项历史与独立监察

### 7.1 两类记录及关联标识

平台需要同时提供**操作审计事件**和**事项处理历史**。审计事件回答“哪个人员或系统身份在何时、基于什么授权，对哪个对象做了什么、结果如何”；事项历史把同一请求的版本、任务、核验、决定、对外沟通和事件串成下一位处理人可理解的时间线。事项历史是业务记录、版本记录和审计事件的关联视图，不替代业务对象本身的状态记录，也不以审计日志重放来决定当前状态。平台工作人员的工作台操作必须留痕；申请方提交、补正、撤回等改变事项状态的操作也进入同一事项历史，便于后续处理人判断下一步。

建议使用下列稳定关联标识；这些是待实现的数据契约，不是现有字段：

- **组织编号 (`organization_id`)：**标识业务组织，用于其已授权的事项索引；组织编号本身不等同于一项申请。
- **审核事项编号 (`review_case_id`)：**标识同一项组织入驻申请或需求审核事项，从首次提交贯穿补正、再次提交、审核决定和结案；每次提交/更正产生独立版本并保留前后关联。新的组织入驻申请或另一项需求创建新的事项编号，不把不同事项的历史混成一条。
- **复核事项编号 (`appeal_case_id`)：**标识对某一审核决定提出的独立复核事项，并链接原审核事项、原决定及涉及版本；不得覆盖原事项的处理记录。
- **监察发现编号 (`finding_id`)：**标识一项独立的监察跟进，关联触发发现的审核事项/平台对象、事件和证据引用；监察发现不替代原审核事项或原决定。
- **处理任务编号 (`task_id`)：**标识某岗位对指定事项/版本的处理任务；认领、释放、例外恢复、回避和提交均关联该任务，不表示有人被指派。
- **审计事件编号 (`event_id`)：**标识一次追加式操作事件。按适用范围关联审核/复核事项或监察发现、组织、对象/版本、岗位、授权来源和处理任务；无具体事项的队列查询或平台授权操作不得伪造事项编号。
- **请求/关联编号 (`request_id` / `correlation_id`)：**`request_id` 关联一次技术请求，`correlation_id` 可关联同一业务动作触发的多个请求或异步处理；两者都不同于事项编号。重试、重复提交、失败和并发冲突均保留其请求结果并可追溯至相关事项。

### 7.2 必须留痕的操作范围与事件字段

凡影响业务状态、访问范围、处理判断或证据可见性的工作台操作均留痕，包括成功、拒绝、失败和并发冲突。至少覆盖：平台身份验证及进入/切换岗位上下文；平台授权授予、续期、变更和撤销；队列、搜索、历史查询和详情读取；认领/认领冲突/释放/例外恢复/回避；核验记录、内外部意见、版本补交/替换/撤回、审核及复核决定、状态门禁、通知发送与回执；监察查询、覆盖状态查看、字段展开、材料预览/下载/导出、监察发现及回应；以及服务账号、异步任务对上述事项实施的操作。相应失败、拒绝、重试和系统异常也记录。不得只记录“最终审核通过/拒绝”。

每条事件至少包含人员/服务操作者标识、当时岗位及授权来源、动作、对象与版本、适用的事项/处理任务编号、服务端发生时间、结果及结构化原因码、必要理由或工单依据、前后状态或版本引用、证据引用、请求/关联编号。对字段变更记录字段名及受控差异/版本引用，不把完整身份证件、手机号、附件正文、验证码、令牌或其他不必要的敏感值复制进审计事件。未提交的键盘输入、悬停等不影响业务和安全的界面细节不记录。审计覆盖目录列出平台全部模块及预期事件，包括尚未实现或尚未接入审计的模块，并分别显示未实现、待接入、已接入或存在异常；不把“当前没有事件”误判成“没有操作”。

详情读取、搜索、监察查询、敏感字段展开和附件访问也属于审计事件；查询事件记录查询人、筛选范围、监察目的（适用时）、结果状态与时间，不复制查询结果正文。事项时间线应明确显示处理人/岗位、操作、版本、核验来源、处理理由、对外答复、尚未解决的问题及后续动作；内部说明、申请方可见内容和受限证据分别标注并按权限显示。后续处理人可据此理解前序判断，但必须基于当前有效版本独立作出决定。审计查询本身同样受控并留下可由其他监察员复核的记录。

成功的业务状态变更与其成功审计事件必须原子提交，或通过可恢复的可靠交付保证最终一致，并在返回成功前确认事件已可靠接收；拒绝/失败事件须在业务事务回滚后仍能持久保存，不能依赖随失败事务一起回滚的同事务记录。审计服务不可用时不得静默放行或谎报成功；所有受审计门禁保护的写操作和敏感读取须停止，直到事件可被可靠记录，并通过独立监控/持久化通道记录故障窗口，恢复后核对及补记。技术评审须明确独立失败事件通道、恢复补记与对账办法，并验证无事件丢失或重复业务副作用。

### 7.3 同一事项的历史处理规则

- 首次提交生成事项编号及首个版本；补正、重提或更正生成新版本和关联事件，不覆盖旧申请、旧材料、旧意见或旧决定。旧版本标为被替代但仍可追溯。
- 每个处理人按时间线查看前序认领/释放、核验来源与结果、补正依据、内部处理说明、对外答复、决定和未结问题；界面突出“上一处理结果”“当前有效版本”“仍待核实项”和“建议后续动作/依据”，让不同人员能基于记录继续判断。建议动作仅作交接提示，不自动批准、拒绝或替代处理人的判断。
- 内部工作说明、监察注记、申请方可见的补正/决定理由分开存储和展示。向申请方发送的内容必须经过明确的对外披露字段/模板，不因其存在于时间线就自动公开。
- 录入错误、错误决定、撤回或更正通过新事件/版本说明原因、关联原记录及实际纠正结果；原记录不可静默抹除。审计历史与源业务状态不一致时标记为异常并留待核查，不由监察员直接改写任一方。
- 同一组织的多个独立申请在组织审计页可分别列出并相互关联，但处理人必须先进入具体事项编号，避免把不同需求、不同申请或不同法律/业务目的的资料混作同一个案件。

### 7.4 平台独立监察员的审计范围与权限

平台独立监察员可以跨组织、跨处理岗位和跨版本检视本平台已纳入审计契约的事项、人员操作、系统操作及结果；不依赖其组织成员关系，也不以被审岗位的任务认领状态限制审计范围。其页面至少支持按组织、事项编号、对象/版本、处理人/岗位、动作/结果和时间筛选，查看单项事项完整时间线、授权访问记录和事件目录覆盖状态，并能够辨认记录缺口、模块未接入、异常延迟、重复处理、未说明差异、越权拒绝、异常访问和版本错配。监察范围必须如实展示覆盖边界；未接入审计的模块不能呈现为“已完成监察”。

监察员拥有只读业务权限，可以对具体事项新增**监察发现**：关联事件/版本、描述可验证的问题、记录依据与建议后续核查方向。监察发现有独立编号和跟进状态，须区分“待回应”“核查中”“已回应”“已关闭”等流程状态与是否确认违规；发现本身不等于事实认定。被监察岗位可在关联事项上提交回应；后续复核由无冲突的监察人员从岗位队列自主认领，不指名分派。监察发现的提出、回应、认领、复核和关闭均形成新事件；监察员不能直接更改审核结论、撤销组织准入、暂停需求或处分账号。需要业务纠正或高影响措施时，须转入对应领域的授权流程；双人审批等基线继续适用。

“审计全部”指覆盖平台已接入模块的操作事件和相关事项历史，不表示可不留痕地读取或导出全部个人信息、证件原件、供应商私密报价或平台外数据。默认按最小必要展示并脱敏；确有监察需要时按事项说明用途、临时展开授权字段，敏感原件访问和下载/导出按 D-19 单独控制并记录。不得以审计员身份关闭组织隔离、绕过对象级授权或批量复制无关数据。

审计事件应追加写入，普通业务/监察页面不得修改或删除；更正以新事件及引用关系表达。技术运维人员不得以日常业务权限改写历史；审计写入身份、审计查询身份和数据库管理身份应分离，紧急维护须经受控审批并产生独立记录。另须通过定期完整性核对和恢复演练发现被绕过或破坏的记录；具体防篡改技术不在本稿假定已经具备。监察员及其授权管理操作同样纳入他人可查看的审计记录。原件、核验记录、审计元数据及派生数据的处理依据、留存/删除期限和法律保全要求，按类别经法律、隐私和安全专业评审确认；不设置未经确认的期限，也不以“监察需要”作为无限期保存个人信息的依据。

## 8. 首期验收条件建议

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| PW-01 | 已登录但没有平台岗位权限访问页面/API | 显示无权说明；服务端拒绝队列/详情/材料数据，不因知道路由或编号取得数据 |
| PW-02 | 普通组织成员访问平台后台 | 组织成员权限不能兑换平台审核权限；两种空间的数据范围不串用 |
| PW-03 | 无平台权限的账号调用组织或需求审核 API | 服务端拒绝并记录必要的安全审计，前端隐藏按钮不作为验收依据 |
| PW-04 | 审核人员尝试认领或审核本人/关联组织申请 | 服务端按回避规则拒绝并保持任务在原岗位待认领；不允许通过另一个平台页面绕过 |
| PW-05 | 需求版本已更新后旧审核页提交 | 服务端拒绝旧版本结论，旧任务保持可追溯并显示已替代 |
| PW-06 | 证照格式齐全但未核验真实性 | 不显示核验通过，不开放依赖该项资格的业务能力 |
| PW-07 | 外部查询失败或无公开接口 | 显示待核验/无法核实及原因；不自动通过、不判为造假 |
| PW-08 | 申请人收到补正并提交新版本 | 逐项补正原因可见；旧版本、原材料和旧决定保留，新版本进入新审核任务 |
| PW-09 | 审核员查看敏感附件 | 仅任务授权范围可预览；未授权访问被拒绝并记录，列表与日志不泄露原始值 |
| PW-10 | 组织或需求审核通过 | 只执行该领域批准状态转换；不代替成员授权、需求发布、选标或其他后续业务授权 |
| PW-11 | 同岗位多人并发认领同一对象版本，或获胜者重试认领请求 | 并发时仅一人取得有效认领；获胜者重试返回同一认领结果且不重复占用；其他人不能查看材料或提交结论 |
| PW-12 | 无对应岗位权限、存在回避冲突或认领已属于他人的审核员尝试认领/读写任务 | 服务端拒绝认领、详情、材料访问和结论提交，并记录必要审计 |
| PW-13 | 因账号禁用、岗位撤销、系统故障或长期未处理而解除认领 | 有独立任务恢复权限者只能解除占用并退回本岗位队列；不能读材料、审批或指定接手人；记录理由、通知并保留原历时 |
| PW-14 | 高影响措施或审核申诉进入复核 | 高影响措施由提议人与批准人分离并按基线完成双人审批；申诉复核人未参与原处理且无冲突；无人可回避时保持待复核并升级 |
| PW-15 | 查看平台投诉或高敏保护证据、下载受控材料 | 仅按独立授权查看，默认脱敏在线预览，下载单独批准；涉事人员不能访问受保护材料；各次访问均有审计 |
| PW-16 | 数据留存期限尚未完成专业审查 | 不把任意天数写成法定期限；按经批准的数据类别、目的和留存规则执行，支持保全、到期复查和删除审计 |
| PW-17 | 申请方和平台人员完成一项申请、补正、认领、核验、审核及通知；其中包含失败和拒绝尝试 | 事项历史按版本显示各方的状态变更、经手人/岗位、核验来源、处理理由、结果及未结问题；拒绝/失败可查但不混成成功业务事件，敏感正文不复制进审计摘要 |
| PW-18 | 不同申请人/处理人先后处理同一组织的多项申请，或同一事项产生新版本 | 后续处理人能看到该事项从首次提交开始的完整历史、当前有效版本、前序结果和仍待核实项；相互独立的申请各有编号，不串案、不覆盖旧版本 |
| PW-19 | 工作台搜索、详情查看、审计查询、敏感字段展开、附件预览及导出 | 每次访问均记录操作者、岗位、对象范围、目的（适用时）、结果和时间；不得把返回的敏感正文写入普通审计事件 |
| PW-20 | 平台某模块尚未接入审计，或接入模块漏发、延迟、改变事件类型 | 审计覆盖页列出平台全部模块及事件目录、未实现/待接入/已接入/异常状态、延迟和已知缺口；不得把无日志误判为无操作，未完成接入的模块清楚标为不可监察 |
| PW-21 | 业务写操作成功，或拒绝/失败事务回滚 | 成功状态与成功事件可靠关联并共同提交或可靠交付；失败/拒绝事件独立持久化，不随业务事务回滚丢失；重试可关联原请求且不重复业务副作用 |
| PW-22 | 审计服务或持久化通道不可用时发起受审计的写操作或敏感读取 | 请求失败关闭，不应用未留痕的状态变化或披露；独立监控/持久化通道记录故障窗口，恢复后能核对并补记结果，不静默宣称审计完整 |
| PW-23 | 首次授予、续期、缩减或撤销平台独立监察权限 | 由两名不同且无利益冲突的授权人确认；申请人不能批准自己的授权；所有变更及审批人均进入可供其他监察员查看的审计历史 |
| PW-24 | 监察员访问其本人权限变更、敏感信息审批或其有利益冲突的事项 | 本人不能审批自己的敏感访问/导出或改写其权限历史；冲突事项转由其他无冲突监察员认领；操作在事后可由另一监察员查见 |
| PW-25 | 监察员创建发现、被监察岗位回应并请求业务纠正 | 发现、回应和复核追加到历史；发现状态不自动变为违规结论；监察员不能通过关闭发现直接变更审核/组织/需求状态，纠正走原领域授权流程 |
| PW-26 | 申请方或平台人员纠正已记录的材料、核验结论或审核决定 | 原记录保留；新版本/新事件引用并解释更正缘由和实际结果，历史完整性核对能标识未授权修改或记录断裂 |

PW-01～PW-13、PW-17～PW-26 和 PW-14 中关于申诉独立复核的部分构成本次已批准纵向切片的实施验收基线；PW-14 中高影响措施双人审批以及 PW-15 的平台投诉证据访问，只有在对应治理模块另行批准和实现时适用，不把这些模块带入本次首期范围。PW-16 只适用于实际收集和处理的数据类别，期限及依据须完成专业评审后配置。各项验收条件在本次评审通过后作为开发合同，执行证据按 G0～G11 门禁记录。

## 9. 已批准基线与实现前置项

| 决策项 | 已批准基线 | 实施阶段交付/专业评审 |
| --- | --- | --- |

#### 步骤 0：范围与规则基线（门禁 G0）

#### 步骤 1：技术契约与现状映射（门禁 G1）

**工作内容：**逐项核对现有组织/需求审核 API、数据表、状态转换、前端入口和 `foundation_audit` 实际覆盖；形成改造映射，禁止把现状误当成已满足需求。冻结实现所需关联契约：`review_case_id`、版本号、`appeal_case_id`、`finding_id`、`task_id`、`event_id`、`request_id` 和 `correlation_id`；确定哪些动作关联事项、哪些是平台级授权/查询事件。完成权限矩阵到服务端 API/资源的映射，审查跨组织监察查询的专用读取边界、事件数据最小化、失败事件通道和审计完整性核对方案。数据库变更沿用后端统一 Flyway 序列。

#### 步骤 2：审计可靠性底座（门禁 G2）

**工作内容：**扩充审计写入接口和结构，记录人员/服务身份、当时授权、动作、对象/版本、结果/原因码、关联编号和时间；支持身份验证后进入/切换岗位上下文、成功/拒绝/失败、并发冲突、搜索/读取、材料访问及异步处理事件。成功业务变化与成功事件使用同一事务或可恢复的可靠交付；拒绝/失败事件不得随业务事务回滚丢失。实现幂等关联和恢复对账，区分业务请求重试与新增操作。建立全平台模块/事件覆盖目录，明确模块尚未实现、待接入、已接入或异常状态；实现不依赖主审计服务的故障告警/故障窗口记录。事件普通页面只追加，不提供编辑/删除路径；具体防篡改能力按技术评审结果陈述，不作未验证承诺。

**通过门禁 G2：**以自动化测试证明：成功状态与事件不会单边提交；业务拒绝/异常回滚后失败事件仍可查；请求重试不造成重复业务副作用；审计服务不可用时受保护写入和敏感读取失败关闭；恢复后可对账故障窗口；覆盖目录能展示尚未接入的模块。完整性核对能发现测试注入的缺失、重复或被改写记录。对应验收 PW-19～PW-22、PW-26。

**通过门禁 G3：**用真实测试授权路径证明：无平台岗位的账号、普通组织成员、已撤权账号均不能读队列/事项/材料或提交决定；岗位只可访问被授权动作；服务端撤权立即阻止后续请求；无默认超级管理员或客户端伪造上下文路径；初始授权过程可追溯。适用时证明双人授权与自审禁止。对应验收 PW-01～PW-03、PW-23～PW-24。该门禁通过前不开放审核或监察路由。

**通过门禁 G4：**用至少两个互不相关事项和一个多版本事项验证：新旧版本可正确追溯；申请方动作进入相应事项历史；不同申请不会因同一组织而串案；后续处理账号能看到已授权的前序理由、当前有效版本和未结问题，但不能读取未授权内部意见或敏感原件；纠错只生成新记录并引用旧记录。对应验收 PW-05、PW-08、PW-17～PW-18、PW-26。

**通过门禁 G5：**并发测试证明只产生一个有效认领；成功认领重试幂等；其他人不能读取该任务材料或结论；释放/恢复均回原队列且没有人工派单；冲突账号不能认领、读取或提交；旧版本不能提交结论；申诉复核人未参与原处理。没有无冲突复核人时保持待复核，不自动通过。对应验收 PW-04～PW-05、PW-11～PW-14。

**通过门禁 G6：**通过允许/拒绝、撤权失效、越权跨组织、恶意/伪造文件、脱敏、日志不泄漏、访问逐次留痕等测试；无安全扫描/存储/权限证据的材料不可供审核。对专业评审尚未完成的材料类型保持关闭，不用“监察需要”豁免。对应验收 PW-09、PW-15、PW-19；PW-15 中投诉案件办理仍不因此进入首期范围。

**通过门禁 G7：**从新申请到补正、版本更新、再审、决定及申请方查看结果完整走通；无权限/回避/旧版本拒绝；格式齐全但未核实真实性不能显示核验通过；外部核验失败显示待核实；状态、历史和审计事件一致。后端 API 测试、隔离 PostgreSQL 集成测试与 Web 角色验收均通过。对应验收 PW-01～PW-10、PW-17～PW-19。

#### 步骤 8：需求审核与发布门禁切片（门禁 G8）

**工作内容：**对每个需求修订版本建立可核验事项关联；实现队列、认领、核验、补正、审核决定、对外反馈和 Web 页面。审核结论必须绑定实际检查的需求版本；用工方对已提交版本的关键字段修改按已批准规则触发新版本及必要复审。沿用 BP-03 已批准的暂停/撤回门禁：暂停或撤回后拒绝新增应标，旧审核页不得批准新版或已失效版本；审核通过不替代发布规则，也不提前实现 BP-04 以后的功能。

**通过门禁 G8：**自动化验证旧版本结论被拒、修订生成可追溯新版本、暂停/撤回后无法新增应标、发布只作用于允许的有效版本；跨组织数据隔离和当前报价等非本功能数据不被监察/审核页面额外暴露；Web/API/数据库状态、事项历史和事件一致。对应验收 PW-01～PW-05、PW-08、PW-10～PW-12、PW-17～PW-19。

#### 步骤 9：监察查询、覆盖与发现闭环（门禁 G9）

**工作内容：**实现 `/platform/audit` 查询、事项完整历史、`/platform/audit/coverage` 全模块覆盖状态、`/platform/audit/findings` 监察发现回应队列。专用审计读取服务跨组织检索已接入记录，不切换租户上下文；统一按组织、事项、版本、处理人/岗位、动作/结果及时间筛选。监察发现可关联证据、回应和复核，显示“待核查/未确认”状态；无人为某人指派，后续人员仍从岗位队列自主认领。监察员仅追加记录；敏感内容展开和导出走独立审批，监察员本人的访问和授权操作可由其他监察员查看。

**通过门禁 G9：**监察员能看到已接入的跨组织历史及访问事件，普通组织账号和审核岗位不能调用该查询；覆盖页准确列出所有模块及未实现/待接入/异常项；发现不自动成为违规结论或业务变更；监察员不能审批自己的访问、授权或导出；监察查询本身留痕。对应验收 PW-19～PW-25。

#### 步骤 10：全链路安全与业务验收（门禁 G10）

**工作内容：**按[后端说明](../../../../backend/README.md)使用隔离 Podman PostgreSQL 测试环境完成 Flyway 全序列、模块集成、隔离和并发测试，确认 `TEST_DATABASE_URL` 指向独立 `_test` 库；在 Web 工作台使用专用合成账号与数据执行浏览器端到端验收。测试覆盖角色越权、跨组织读取、认领竞态、重复提交、审计事务失败/恢复、版本串案、敏感资料访问、通知披露边界及撤权。后端在 `backend/` 运行 `mvn -Pintegration clean verify`；前端按 [Web 管理端说明](../../../../frontend/web-admin/README.md)运行 `npm run type-check`、`npm run lint`、`npm run build`；浏览器验收使用仓库 Playwright 工作流。集成测试会清理测试库表，严禁把开发库或生产库配置为测试目标。所有失败都记录为缺陷并修复后复验，不通过删除断言或缩小数据集规避。

**通过门禁 G10：**所有首期适用的 PW 条件均有自动化/人工证据，测试数据库确为隔离 `_test` 数据库，跨组织隔离、审计持久性和认领并发无未解决阻断问题；后端完整 Maven `verify`、前端三项检查、关键页面浏览器验收及迁移升级验证通过。PW-14 中高影响措施审批和 PW-15 中投诉案件访问仍按范围说明排除，不能伪报通过；PW-16 按实际采集和启用的数据类别验证，不设未经专业确认的期限值。未完成的期限评审不阻断无关自动化测试，但若某类材料的处理依据/期限属于启用前置要求，则 G11 不得通过。

#### 步骤 11：试点准备与单独启用决定（门禁 G11）

**工作内容：**准备仅含合成数据的试点流程、账号授权/撤销演练、故障监控、审计核对与恢复演练、值守和问题上报办法；完成相关运营、法律、隐私与安全评审，并记录未开放材料类型、留存规则、外部服务和功能限制。确认平台工作人员理解岗位、回避、认领、监察发现和错误更正流程。

**通过门禁 G11：**G0～G10 均通过；生产使用所需的授权责任、资料处理依据、法定适用要求和运行保障已由各自责任人确认；有权负责人基于实际测试证据另行批准明确的试点对象、功能范围和启用方式。未经该项单独决定，部署到测试环境或完成验收均不代表真实平台审核/监察能力已启用。

### 10.3 交付状态与证据记录

每个门禁记录：范围/版本、负责验收角色、执行环境、测试数据类型、命令或场景、结果链接、未通过项及关闭证据。状态只使用“未开始、进行中、待验收、通过、未通过、阻断、超出范围”等可区分值；不以一个总的“完成”覆盖具体门禁。测试环境、预生产验证、试点启用和生产正式启用分别记录。需求或范围发生变化时，先修订本稿并评估受影响门禁，再执行实现，不静默扩大访问权限或留存范围。
