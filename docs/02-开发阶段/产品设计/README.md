# 产品设计 → 研发交接入口

- 整理日期：2026-10-23
- 文档状态：交接索引与评审工作底稿；不代替产品负责人对待定规则的批准。
- 接收对象：架构、前后端、测试、数据与交付人员。

## 1. 先确认项目是什么

项目已从面向单家劳务中介的管理 SaaS 转向**劳务供应链交易与履约协同平台**。用工方发起需求、劳务公司竞争性应标并承担约定履约，平台协同需求、供给、排班、考勤、工时、结算和对账；工资、返费等管理能力服务于交易链路。现有代码的“基础能力已完成”不等于新平台业务流程已经交付。

当前 [PRD](PRD-v0.1.md) 仍是待评审草案，完整履约、资金流程与独立 App 属于已确认的产品范围，但**不代表每一项详细规则已获批、具备上线条件或已实现**。业务依赖顺序不能解读成“只交撮合 MVP、资金以后再说”。商业保理相关能力仅是[未来可选战略](产品战略路线与可选增值渠道-v0.1.md)，不能混入当前开发任务或现行收费。

## 4. 交接时必须一起提供

1. **需求卡**：PRD 的 FR 编号、用户/组织角色、触发与前置条件、主流程/异常流程、输出/不可变记录、验收证据和对应专项文档；从[追踪矩阵](需求追踪与交接门禁-v0.1.md)开始拆分。
2. **规则卡**：每个会影响字段、权限、金额、状态或对外表述的规则，标记“已确认方向 / 部分批准 / 建议待评审 / 待定 / 未来可选”，附来源链接、决策人、待决问题。仅已批准的可直接配置为现行收费。
3. **跨端/跨组织合同**：标明数据创建方、读取方、确认方、可修改时点、版本与审计记录；接口、表结构和 UI 由技术设计细化，产品稿不规定具体技术实现。
4. **验收与发布卡**：正向、驳回、撤回、重复请求、权限越界、结果未知及对账异常场景；分别记录开发验收与真实业务启用前的外部机构、合同、数据授权等门槛。

未落实的材料由产品经理牵头补充业务判定标准和验收，项目经理维护决策负责人、风险、依赖和评审结论，技术负责人确认实现方案与工作量，测试负责人将可观察结果转成用例。**文档中的建议和项目经理的拆任务动作本身均不构成审批**。
