## 🎯 项目概览

### 业务背景

**行业痛点**：
劳务中介公司目前依靠**微信群 + Excel表格**管理业务，存在以下问题：
- 招聘渠道难管理（不知道谁推荐了谁，撞单纠纷多）
- 工资计算靠手工（容易算错，经常扯皮）
- 返费结算混乱（经纪人不信任，经常来闹）
- 数据分散难统计（要做报表得翻几十个Excel）

**解决方案**：
开发一套**多租户SaaS系统**，将业务流程线上化、标准化。

### 业务模式（四方平台）

```
┌─────────────┐
│  用工企业   │ ← 需要工人
│  (工厂)    │
└──────┬──────┘
       │
       ↓ 用工需求
┌─────────────┐
│  劳务公司   │ ← 系统主要用户（我们的客户）
│ (中间服务商) │
└──────┬──────┘
       │
       ↓ 派单招聘
┌─────────────┐
│  招聘渠道   │ ← 内部专员 + 外部经纪人
│ (推荐求职者) │
└──────┬──────┘
       │
       ↓ 推荐
┌─────────────┐
│  求职者/员工 │ ← 找工作的人
└─────────────┘
```

### 核心业务流程

```
1. 用工企业发布用工需求 → 劳务公司接单
2. 劳务公司发布招聘岗位 → 招聘渠道推广
3. 求职者报名（扫码） → 记录渠道归属（防撞单）
4. 劳务公司安排面试 → 面试通过后入职
5. 员工到工厂上班 → 工厂记录考勤工时
6. 劳务公司计算工资 → 发工资给员工
7. 劳务公司结算返费 → 发返费给招聘渠道
8. 劳务公司与工厂结算 → 收取服务费
```

### 系统价值

| 角色 | 痛点 | 系统解决方案 |
|------|------|------------|
| **劳务公司** | 微信群管理混乱、手工算工资易错 | 线上管理、自动计算、数据可追溯 |
| **招聘渠道（经纪人）** | 不信任返费计算、要钱不及时 | 实时查看预计返费、自动计算达标 |
| **员工** | 工资条不透明、工资晚发不知道 | 小程序查工资、工资条推送 |
| **用工企业** | 对账麻烦、考勤数据难核对 | 线上对账、考勤数据互通 |

### 多租户设计

所有业务表都必须加 `tenant_id` 字段：

```sql
CREATE TABLE xxx (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL COMMENT '租户ID',
  ...其他字段...
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at TIMESTAMP NULL COMMENT '软删除时间',
  INDEX idx_tenant_id (tenant_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

**重要**：
- 所有SQL查询都必须带 `WHERE tenant_id = ?`
- 可以用MyBatis Plus的租户插件自动注入
- 数据隔离是安全红线，必须100%保证

## 🔐 核心技术难点

### 难点1：渠道归属与撞单规则

**业务场景**：
- 经纪人A在10月1日推荐了张三
- 经纪人B在10月5日也推荐了张三
- 问：张三应该归属哪个经纪人？

**撞单规则**：
- 7天内重复报名，归属第一个推荐的经纪人
- 需要根据身份证号或手机号判断是否为同一人

**技术实现**：
```java
// 伪代码
if (existsApplicantWithin7Days(idCard)) {
    throw new BusinessException("该求职者7天内已报名，归属渠道：XXX");
}
```

**数据库设计**：
```sql
-- 报名表需记录渠道来源
CREATE TABLE recruit_applicant (
  id BIGINT PRIMARY KEY,
  tenant_id BIGINT NOT NULL,
  name VARCHAR(50),
  id_card VARCHAR(18) UNIQUE, -- 唯一索引，防撞单
  phone VARCHAR(11),
  channel_id BIGINT COMMENT '渠道ID（谁推荐的）',
  apply_time TIMESTAMP COMMENT '报名时间',
  ...
  INDEX idx_id_card_time (id_card, apply_time)
);
```

### 难点2：工资自动计算

**业务场景**：
工资计算公式复杂，需要支持多种计算规则：
- 计时工资：底薪 + 加班费 - 扣款 + 奖金
- 计件工资：单价 × 产量
- 混合模式：底薪 + 计件

**工资计算公式**：
```
应发工资 = 底薪 + (正常工时 × 时薪) + (加班工时 × 加班时薪) + 奖金 - 扣款
实发工资 = 应发工资 - 借支扣款 - 社保个人部分
```

**技术实现**：
- 使用策略模式支持多种计算规则
- 计算结果必须精确到分（使用`BigDecimal`，不用`double`）
- 必须记录计算明细，方便追溯

**关键代码**：
```java
public BigDecimal calculateSalary(Employee emp, Workhour workhour, SalaryPolicy policy) {
    BigDecimal baseSalary = policy.getBaseSalary(); // 底薪
    BigDecimal normalPay = workhour.getNormalHours().multiply(policy.getHourlyRate()); // 正常工时
    BigDecimal overtimePay = workhour.getOvertimeHours().multiply(policy.getOvertimeRate()); // 加班工时
    BigDecimal bonus = calculateBonus(emp, workhour); // 奖金
    BigDecimal deduction = calculateDeduction(emp); // 扣款
    BigDecimal advanceDeduction = getAdvanceDeduction(emp); // 借支扣款
    
    return baseSalary.add(normalPay).add(overtimePay).add(bonus)
           .subtract(deduction).subtract(advanceDeduction);
}
```

### 难点3：返费自动计算与达标判断

**业务场景**：
- 返费政策：员工在职满30天，给经纪人返¥500
- 达标条件：在职满30天 + 无请假 + 无违纪

**技术实现**：
```java
// 每天凌晨跑定时任务，检查是否有员工达标
@Scheduled(cron = "0 0 1 * * ?")
public void checkRebateAchievement() {
    List<Employee> employees = employeeService.getEmployeesWorkingFor30Days();
    for (Employee emp : employees) {
        if (isQualifiedForRebate(emp)) {
            createRebateRecord(emp);
        }
    }
}
```

**达标判断逻辑**：
- 在职时间 ≥ 30天（从入职日期到今天）
- 状态为"在职"
- 近30天无请假记录（可选）
- 近30天无违纪记录（可选）

### 难点4：考勤数据导入与解析

**业务场景**：
工厂提供的考勤表格式千奇百怪：
- 有的是按员工一行，一列一天
- 有的是按天一行，一列一个员工
- 有的是按打卡记录流水

**技术实现**：
1. **模板配置**：为每个企业配置考勤表模板
2. **智能解析**：根据表头识别格式
3. **数据清洗**：处理异常数据（如姓名不匹配、日期格式错误）

**建议**：
- 提供标准模板给客户下载
- 导入前先预览，让用户确认
- 导入失败要有详细的错误提示

### 难点5：多端数据同步

**业务场景**：
- 管理员在Web后台修改了员工信息
- 员工在小程序立即要能看到

**技术实现**：
- **方案1**：短轮询（前端每10秒请求一次）
- **方案2**：WebSocket推送（实时推送，但增加服务器压力）
- **方案3**：Redis发布订阅 + 消息推送

**推荐**：
- 关键数据用Redis缓存，前端读缓存
- 数据变更时清除缓存 + 推送通知
- 不需要实时的数据用短轮询

## 📏 开发规范

### 代码规范

**后端（Java）**：
- 遵循阿里巴巴Java开发手册
- 使用Lombok减少模板代码
- Controller层只做参数校验和转发
- Service层写业务逻辑
- 不允许在Controller层直接操作数据库

**前端（JavaScript/TypeScript）**：
- 遵循ESLint + Prettier规范
- 组件命名用大驼峰（PascalCase）
- 变量命名用小驼峰（camelCase）
- 常量用全大写+下划线（UPPER_SNAKE_CASE）

### 接口规范

**RESTful API**：
```
GET    /api/employees          # 查询员工列表
GET    /api/employees/:id      # 查询员工详情
POST   /api/employees          # 新增员工
PUT    /api/employees/:id      # 修改员工
DELETE /api/employees/:id      # 删除员工
```

**统一响应格式**：
```json
{
  "code": 200,
  "message": "success",
  "data": { ... },
  "timestamp": 1697520000000
}
```

**错误码规范**：
- `200` - 成功
- `400` - 参数错误
- `401` - 未登录
- `403` - 无权限
- `404` - 资源不存在
- `500` - 服务器内部错误

### Git规范

**分支管理**：
```
main          # 主分支（生产环境）
develop       # 开发分支（测试环境）
feature/xxx   # 功能分支（开发中）
hotfix/xxx    # 紧急修复分支
```

**Commit规范**：
```
feat: 新增员工管理模块
fix: 修复工资计算精度问题
docs: 更新API文档
style: 代码格式化
refactor: 重构返费计算逻辑
test: 增加单元测试
chore: 更新依赖版本
```

### 数据库规范

**命名规范**：
- 表名：小写+下划线，如`employee_basic`
- 字段名：小写+下划线，如`created_at`
- 索引名：`idx_字段名`，如`idx_tenant_id`
- 主键统一用`id`，类型`BIGINT`

**必备字段**：
```sql
id BIGINT PRIMARY KEY AUTO_INCREMENT,
tenant_id BIGINT NOT NULL COMMENT '租户ID',
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
deleted_at TIMESTAMP NULL COMMENT '软删除时间'
```

## ⚠️ 技术风险与应对

### 风险1：工资计算精度问题

**风险描述**：
使用`double`存储金额会有精度丢失，导致工资算错。

**案例**：
```java
double salary = 2490.5;
double deduction = 100.3;
double result = salary - deduction; // 可能是 2390.1999999999998
```

**应对方案**：
- ✅ 使用`BigDecimal`存储和计算所有金额
- ✅ 数据库字段用`DECIMAL(10,2)`
- ✅ 前端显示时格式化到分

### 风险2：并发场景下的撞单问题

**风险描述**：
两个经纪人同时推荐同一个人，可能绕过撞单检查。

**应对方案**：
- ✅ 在`id_card`字段加唯一索引
- ✅ 使用Redis分布式锁
- ✅ 报名时先检查再插入（数据库层面保证）

### 风险3：返费计算错误

**风险描述**：
达标判断逻辑复杂，容易算错，导致经纪人不信任系统。

**应对方案**：
- ✅ 返费计算结果必须记录明细（哪些员工达标、金额多少）
- ✅ 经纪人可以在小程序查看明细
- ✅ 提供"重新计算"功能（修改政策后）

### 风险4：多端数据不一致

**风险描述**：
Web端修改数据后，App端没有及时更新。

**应对方案**：
- ✅ 使用Redis缓存，修改时清除缓存
- ✅ 关键数据变更推送消息通知
- ✅ 前端做乐观锁（版本号机制）

### 风险5：考勤数据导入失败率高

**风险描述**：
工厂提供的考勤表格式不规范，导致导入失败。

**应对方案**：
- ✅ 提供标准模板下载
- ✅ 导入前预览数据，让用户确认
- ✅ 导入失败提供详细错误信息（第X行第X列）
- ✅ 支持部分导入（导入成功的先入库）

### 风险6：App上架审核不通过

**风险描述**：
iOS App Store审核严格，可能因为各种原因被拒。

**应对方案**：
- ✅ 提前了解审核规则
- ✅ 不要在App中出现"测试"、"Demo"等字样
- ✅ 准备好测试账号和测试数据
- ✅ 预留1-2周审核时间

### 风险7：小程序审核不通过

**风险描述**：
微信小程序涉及金融、招聘类目，审核可能不通过。

**应对方案**：
- ✅ 申请正确的类目（人力资源服务）
- ✅ 不要在小程序中出现"贷款"、"借支"等敏感词
- ✅ 借支改叫"预支工资"
- ✅ 准备营业执照、资质证明

### 风险8：性能问题

**风险描述**：
数据量大时（如1万员工、100万考勤记录），查询变慢。

**应对方案**：
- ✅ 关键表加索引（`tenant_id`, `created_at`, `status`等）
- ✅ 大表分页查询，默认每页20条
- ✅ 列表查询只查必要字段，不查`TEXT`字段
- ✅ 使用Redis缓存热点数据
- ✅ 考勤、工资等历史数据按月分表
